集群维护、升级和交接

学习目标演练受控节点维护；在可丢弃集群验证升级前检查；交付运维清单，不以重建集群冒充升级测试
本页目录1. cordon、drain 与实际容量2. PDB 限定一部分主动中断3. 维护失败时先解释阻塞4. 升级需要兼容矩阵5. 集群状态恢复与应用数据恢复分开6. 交接需要操作入口与决策责任7. 本阶段验收

应用上线后，节点、控制器、API 和证书仍需要维护。集群维护的目标不是“所有命令无错误”，而是在明确影响范围内完成变更，并能解释业务结果、失败处理和恢复责任。

前置是两份健康 API 副本、可用业务检查和恢复材料。本章只在可丢弃的本地集群演练；本地节点删除与重建不能冒充生产集群升级验证。

1. cordon、drain 与实际容量#

cordon 通常阻止新的普通 Pod 被调度到节点；drain 尝试驱逐符合条件的工作负载，并受相关规则影响。已有 Pod、DaemonSet、本地临时数据和不可驱逐对象需要分别处理。

先查看实际节点与 Pod 分布，再选一台工作节点：

kubectl --context kind-ticketdesk get nodes
kubectl --context kind-ticketdesk -n ticketdesk get pods -o wide
kubectl --context kind-ticketdesk -n ticketdesk apply -f k8s/operations.yaml

本例数据库是带本地卷的单实例。如果选中其所在节点，可能遇到存储与调度限制。应先识别这个影响，不能用强制删除参数把限制隐藏起来。

2. PDB 限定一部分主动中断#

配套 PDB 要求 stable API 至少保留一个可用副本。它主要影响符合规则的主动驱逐过程，不保证节点意外掉电时仍有容量，也不代替 Deployment 自己的滚动策略。

kubectl --context kind-ticketdesk -n ticketdesk get pdb ticketdesk
kubectl --context kind-ticketdesk drain '<选定的本地工作节点>' --ignore-daemonsets --timeout=120s

命令使用实际节点名，先评估 emptyDir 等数据的影响。若因为本地临时数据拒绝继续，只有确认该数据可丢弃时才选择相应参数；数据库 PVC 与 emptyDir 也不能混为一谈。

持续请求指定工单，记录驱逐、重新调度、就绪和业务响应。完成后执行对应节点的 uncordon。PDB 的条件和限制参考 Kubernetes 中断预算。

3. 维护失败时先解释阻塞#

drain 卡住可能是可用副本不足、其他节点资源不够、约束无法满足、存储不能迁移，或应用无法在新节点就绪。观察事件与控制器状态，再决定补容量、修复应用或调整维护计划。

不要把删 PDB、强制删除 Pod 或绕过驱逐规则作为默认解决方法。这些操作改变了保护条件，应由明确的影响判断支持。恢复后记录用户是否感知失败，而不是只看节点最终 Ready。

4. 升级需要兼容矩阵#

项目 升级前核对内容
控制面与节点 目标版本、允许的版本差异与升级顺序
kubectl 与自动化客户端 支持的服务端版本范围
CNI、CSI 与运行时 与目标集群的兼容及回退限制
CRD 与控制器 schema、转换、API 版本与数据迁移
应用配置 已弃用或移除的 API、探针与安全默认值
托管平台 平台允许的升级路径、维护窗口与责任

具体版本差异按 Kubernetes version skew policy 和所选组件文档核对，不能把一张长期不更新的数字表当作永久规则。

升级控制器 Chart 也可能涉及 CRD，但 Chart 升级动作未必按你希望的方式升级全部 CRD。事前导出受保护的配置与恢复材料，在实验环境检查转换和现有对象，而不是只观察新 controller Pod 启动。

5. 集群状态恢复与应用数据恢复分开#

etcd 或平台控制面备份保存某类集群状态；数据库与对象存储保存业务数据；Git 仓库保存期望配置；制品仓库保存运行内容。任何单独一份都不足以保证整个服务恢复。

重建 kind 再 apply 可以验证一部分环境重建，但无法证明真实控制面升级、原集群 API 存储迁移或数据恢复已成功。实验报告要给操作准确命名，并列出缺少的证据。

6. 交接需要操作入口与决策责任#

交接材料至少包含资源与所有者、版本矩阵、身份入口、日常检查、证书与备份、告警路由、维护窗口、恢复步骤和升级路径。秘密通过受控系统交接，不嵌入文档。

用一个小演练检验交接：让另一位维护者只根据说明定位某个请求、确认运行版本、判断一项告警并找到恢复入口。遇到需要口头补充的信息，回写到文档，而不是认为“对方不熟悉”就结束。

7. 本阶段验收#

提交一次受控节点维护时间线、业务结果、PDB 和存储边界、升级前核对表，以及恢复责任图。云、IaC、Kubernetes 和 GitOps 这几章至此形成第二个交付闭环。

下一篇从对象状态转向用户感知：为什么服务看起来都在运行，用户仍然说慢或失败？我们将用指标、日志与追踪来回答。
