CHAPTER 44 · 第 11 篇v0.3 阅读版

策略执行、运行约束与漏洞响应

学习目标拒绝一个明确违规工作负载，再发布合规版本；模拟漏洞修复，追踪受影响制品并保留审计证据
本页目录1. 三个位置执行不同检查2. 运行离线正反例3. 了解策略覆盖之外的部分4. Admission 与 Pod 安全5. 漏洞响应从受影响制品开始6. 例外和运行检测要能闭环7. 验收

团队约定镜像必须固定 digest、应用以普通用户运行，如果只写在文档里，就容易在紧急发布时被忽略。策略应在合适的位置执行，同时提供可解释的失败信息和有边界的例外流程。

本章配套包含离线工作负载检查器和明确的合成正反例。它验证若干配置条件，不访问镜像仓库，不验证签名，也不代替 Kubernetes admission。

1. 三个位置执行不同检查#

CI 中的检查适合尽早反馈；部署前的晋级门禁适合关联制品证据与目标环境；集群 admission 可在资源进入 API 时执行运行策略。运行期间还需要观察实际行为与新公开风险。

同一规则可以在多个位置提供不同价值，但要维护统一语义和版本，避免 CI 允许、集群拒绝却没有解释。紧急例外也应明确在哪一层生效和何时失效。

2. 运行离线正反例#

python3 security/check_workload.py security/fixtures/workload-allowed.yaml --allowed-prefix ghcr.io/learning-team/
python3 security/check_workload.py security/fixtures/workload-denied.yaml --allowed-prefix ghcr.io/learning-team/

预期第一条通过，第二条返回失败并列出不符合项。样例中的 digest 是明确的合成输入，不能拉取或部署。它证明的是字符串与工作负载约束判定，不证明镜像存在或来源可信。

规则要求限定仓库前缀、digest 格式、非 root、禁止权限提升、移除额外 capability，以及 CPU/内存请求与限制；还拒绝本教学范围中的 hostPath 和主机命名空间。

3. 了解策略覆盖之外的部分#

语法符合要求的 YAML 仍可能运行恶意或有漏洞的软件；仓库前缀正确也不等于构建身份正确。制品真实性需要第 43 章的验证，业务权限需要应用与数据库侧控制。

此检查器只解析列出的常见 workload 类型，不覆盖所有自定义控制器生成的 Pod，也不全面实现 Pod Security Standards。扩展时需要新的正反例与实际 API 验证，不能简单改名为“完整安全检查”。

4. Admission 与 Pod 安全#

Kubernetes Pod Security Admission 可以按命名空间配置相应模式与级别，用审计、告警和执行逐步了解影响。某些系统组件有不同运行需求，应按命名空间和责任边界设计，不能对整个集群盲目应用一个模板。

在独立实验命名空间设置策略，尝试创建一个明确违规的 Pod，确认被拒绝；再应用合规版本，确认能够运行。已有对象、控制器与新建 Pod 的检查时点要分别观察，不能仅看 Namespace 标签存在。

具体规则与版本约束参考 Pod Security Admission。生产接入之前先评估现有工作负载与必要例外。

5. 漏洞响应从受影响制品开始#

新的严重风险出现后，先用 SBOM 与部署记录找到受影响制品及环境，确认暴露与可达条件，决定修复、缓解和紧急发布优先级。不要只更新主分支依赖，却不知道旧镜像仍运行在哪里。

修复后生成新候选，重新执行相关测试、扫描和身份验证，再按受控策略晋级。紧急发布可以简化部分等待，但应保留关键证据、影响判断与恢复条件。

6. 例外和运行检测要能闭环#

例外记录具体对象、原因、负责角色、补偿措施和过期时间。过期后应重新阻断或触发明确复核，避免形成永久豁免。

运行检测关注实际异常，例如不应发生的外连、权限变化或异常进程。检测工具也会产生误报和成本，需要与身份、网络和应用日志关联，而不是把每个信号直接当成入侵结论。

7. 验收#

提交离线正反例结果、实际 admission 拒绝与允许结果的执行状态、一份风险修复时间线和过期例外处理。说明策略阻止了哪些具体行为，以及仍需要身份、制品和运行验证解决的部分。
