Service、DNS 与 Gateway API

学习目标通过 Envoy Gateway 访问服务；修复错误 selector 或路由；明确本地 port-forward 与公网负载均衡的验证差异
本页目录1. 从 selector 到 EndpointSlice2. DNS 与命名空间视角3. port-forward 适合局部排查4. Gateway API 的责任拆分5. 验证路由，而不只验证对象创建6. TLS、旧 Ingress 与迁移7. 故障练习与验收

Pod 被替换后，地址可能变化。如果调用方直接记住某个 Pod IP，控制器虽然修好了副本，用户仍可能访问旧地址。Service 提供稳定的访问抽象；入口网关再把外部 HTTP 请求按主机名与路径送到合适的服务。

前置是第 25 章的本地集群与健康 API。以下操作限定 kind-ticketdesk；外部云负载均衡不在本章实测范围。

1. 从 selector 到 EndpointSlice#

Service 用 selector 找到匹配的 Pod，再通过 EndpointSlice 等对象描述后端端点。实际转发由集群网络实现承担。Service 声明存在，不保证 selector 选对，也不保证后端已就绪。

kubectl --context kind-ticketdesk -n ticketdesk get service ticketdesk -o yaml
kubectl --context kind-ticketdesk -n ticketdesk get endpointslice -l kubernetes.io/service-name=ticketdesk
kubectl --context kind-ticketdesk -n ticketdesk get pods --show-labels

本例 Service 的端口 80 转发到 Pod 中名为 http 的容器端口 8000。名称、数字与 selector 要成套核对；只看 port: 80 无法推断应用实际监听了什么。

2. DNS 与命名空间视角#

同一命名空间内可以使用服务短名 ticketdesk；跨命名空间通常需要更明确的名称，例如 ticketdesk.ticketdesk.svc.cluster.local，集群域也可能经过定制。

DNS 解析提供地址信息，后续仍需要网络路径、端口与业务响应。CNI 负责 Pod 网络连接等基础能力，不同实现提供的策略、路由和加密功能也不同。不要把“所有 Pod 能互相访问”与“所有访问都符合权限要求”混成同一件事。

3. port-forward 适合局部排查#

kubectl --context kind-ticketdesk -n ticketdesk port-forward service/ticketdesk 8001:80

在另一个终端执行：

python3 scripts/smoke.py --url http://127.0.0.1:8001

这个访问通道适合本机实验与诊断，不能据此证明公网 DNS、TLS、LoadBalancer、网关路由或 NetworkPolicy 已经生效。port-forward 也不是用来承载生产用户流量的长期入口。

4. Gateway API 的责任拆分#

GatewayClass 描述使用哪个控制器类别；Gateway 定义监听与允许附着的路由范围；HTTPRoute 描述请求匹配与后端。控制器读取这些声明，配置实际的数据面代理。

对象或组件 本例作用
Envoy Gateway 控制器 解释声明并管理网关配置
GatewayClass 选择 Envoy Gateway 控制器
Gateway 接受 ticketdesk 命名空间中的 HTTP 路由
HTTPRoute 匹配 ticketdesk.local 并转向服务
Envoy 数据面 实际接收和转发用户请求

先按 Envoy Gateway 官方安装说明 选择与集群兼容的版本、安装所需 CRD 与控制器。本次核对的 quickstart 使用 v1.9.1；它是文档中的候选版本，不是本教程已经跑过的集成矩阵。

helm --kube-context kind-ticketdesk install eg oci://docker.io/envoyproxy/gateway-helm --version v1.9.1 -n envoy-gateway-system --create-namespace
kubectl --context kind-ticketdesk -n envoy-gateway-system wait deployment/envoy-gateway --for=condition=Available --timeout=5m
kubectl --context kind-ticketdesk apply -f k8s/gateway.yaml

执行 Helm 前确认当前 kube context，或显式增加 --kube-context kind-ticketdesk，避免把控制器装进其他集群。已有平台托管 Gateway API CRD 时，应按平台与控制器兼容说明处理其所有权，不重复接管。

5. 验证路由，而不只验证对象创建#

检查 Gateway 的 Accepted、Programmed 等条件，以及 HTTPRoute 的 Accepted、ResolvedRefs 等条件。条件为假时查看 reason/message；一份 YAML 被 API 接收，可能仍指向不存在的服务或不允许附着的父对象。

kubectl --context kind-ticketdesk -n ticketdesk get gateway,httproute -o yaml
kubectl --context kind-ticketdesk -n envoy-gateway-system get service -l gateway.envoyproxy.io/owning-gateway-name=ticketdesk

找到实际 Envoy Service 名称，转发其 80 端口到本机 8081，再使用正确主机头请求：

curl -i -H 'Host: ticketdesk.local' http://127.0.0.1:8081/health/ready

这里仍是本机通道，只验证经过 Envoy 的路由路径。公网 LoadBalancer 的地址、外部访问策略与证书需要另做检查。

6. TLS、旧 Ingress 与迁移#

HTTPS listener 需要正确证书引用、匹配域名、信任链与续期流程。证书文件更新不等于代理已加载新证书；应从实际用户入口检查握手结果，再验证过期与续期告警。

Ingress API 与 ingress-nginx 控制器是不同对象。官方公告给出了社区 ingress-nginx 于 2026 年 3 月退役的安排，本教程因此用 Gateway API 与维护中的控制器作为主线；这不表示 Kubernetes 的 Ingress API 或所有 NGINX 产品都被移除。参阅官方退役说明。

7. 故障练习与验收#

在自己的实验配置中把 Service selector 的 component 改错，观察 EndpointSlice 与响应，再恢复；另将 HTTPRoute backend 名称改为不存在的服务，观察引用解析条件。两种故障发生在不同层，记录各自的最短诊断路径。

交付从请求主机名到网关、Service、端点和 Pod 的对应表，附成功与失败证据。恢复后重新查询同一工单。删除练习控制器时先确认是否有其他路由依赖它，不直接清空共享 CRD。
