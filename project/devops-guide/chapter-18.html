CHAPTER 18 · 第 5 篇v0.3 阅读版

部署配置、环境差异与发布验证

学习目标在声明的目标环境部署制品；运行正向和反向冒烟；拒绝缺失配置；记录本次和上次版本
本页目录1. 给环境明确职责2. 配置也是发布输入3. 首次部署和替换应用不同4. 验证从进程延伸到业务5. CI runner 不能凭空到达你的主机6. Linux VM 路线如何对应7. 发布单与完成条件

流水线通过说明某个候选在测试条件下工作过。部署则把这个候选带到具体环境，面对真实的配置、身份、网络和数据。部署动作结束后仍需要验证，才能判断这次变更是否完成。

本章目标环境是你自己的本机 Compose 实验环境，应用监听 127.0.0.1。独立 Linux VM 的 systemd 文件是延伸材料，不与 Compose 同时占用同一端口。个人网站上发布的是这套静态教程，不是公开的 TicketDesk 后端。

1. 给环境明确职责#

环境 主要用途 数据与访问特点
开发 快速修改与调试 人工实验数据，可频繁重置
CI 临时环境 自动验证一次变更 隔离、短生命周期、自动清理
测试或预发布 验证目标部署条件 尽量接近目标配置，使用合适的测试数据
生产 提供真实服务 有业务责任、访问控制和恢复要求

环境名字不会自动带来隔离。两个叫“test”和“prod”的进程，如果共享同一数据库账号和库，仍可能相互影响。为环境分配明确的资源、身份和数据边界，比多建几个配置文件更重要。

2. 配置也是发布输入#

镜像固定后，数据库地址、端口、功能开关和秘密仍会改变运行行为。发布记录至少关联镜像 digest、非秘密配置修订和秘密版本标识。不能只记录“更新镜像成功”。

本项目用 .env 提供本地实验配置，lab.py init 自动生成密码，已存在时不覆盖。环境变量优先于文件中的同名值，所以终端中遗留的 APP_IMAGE 或 APP_PORT 也会影响命令。出现“我明明改了文件但没有变化”时，要检查配置来源与优先级。

python3 scripts/lab.py init
docker compose config --quiet

不要把完整展开配置贴到公开日志。数据库连接串包含密码，不应通过 /version 返回。服务启动时缺少关键配置，应该明确失败或拒绝就绪；使用一个看似可用的默认生产地址会把错误变成更隐蔽的数据风险。

3. 首次部署和替换应用不同#

首次建立实验环境：

python3 scripts/lab.py up

这个入口包含构建、数据库准备、迁移和业务检查。若使用已发布制品，则按第 16 章提供真实 digest，执行 up --image。

数据库已完成所需迁移，只替换应用版本时：

CANDIDATE_IMAGE='<填写本人已验证的真实镜像引用>'
python3 scripts/lab.py deploy --image "$CANDIDATE_IMAGE"
python3 scripts/lab.py check --ticket-id 1

用自己的已有工单 ID 替换 1。部署脚本只在业务检查通过后更新 .lab/release.json；失败候选不会成为恢复目标。它不提供零停机发布，也不替你执行数据库迁移。单实例替换期间可以出现短暂中断，这应写进实验与发布说明。

.lab/release.json 是本地恢复辅助信息，记录最后通过验证的镜像与时间；它不是完整发布审计系统。源码、配置、迁移、操作者、观察窗口和前一版本还需记录在发布单中。

4. 验证从进程延伸到业务#

检查 TicketDesk 的方法 仍不能证明什么
进程存活 /health/live 数据库可用
依赖与 schema 可访问 /health/ready 所有业务操作正确
版本身份 /version 部署平台使用的 digest 一定正确
正向业务 新建、读取、更新工单 非法输入一定被拒绝
反向业务 短标题应返回 422 所有攻击与边界都已覆盖
既有数据 查询指定旧工单 全部历史数据都完整

scripts/smoke.py 可以对显式给定的测试地址执行业务检查。它会写入验收工单，所以在任何共享环境运行前应为测试数据确定标识、清理方式和权限范围。不要把写操作伪装成无副作用的探测。

python3 scripts/smoke.py --help

通过脚本帮助确认参数，再对自己的实验地址执行。不要在尚未获得授权的公共地址上试跑创建与更新请求。

5. CI runner 不能凭空到达你的主机#

GitHub 托管 runner 里的 localhost 指 runner 自己，不指你的电脑、云主机或个人网站服务器。要部署到目标环境，必须有明确的网络路径、目标身份和适合的执行方式。

常见选择包括目标端主动拉取已发布制品、受控的远程部署任务、专用 runner，或者后续章节中的 GitOps。每种方式都应明确：谁能发起、凭据有效多久、能修改哪些资源、网络不可达时如何报告，以及失败后谁负责恢复。

本阶段没有配置公网 SSH、长期部署密钥或自动登录你的个人服务器。先在本机完成闭环，后续再把相同的版本与验收规则迁移到真实环境。

6. Linux VM 路线如何对应#

ops/ticketdesk.service 展示 systemd 管理进程的方式。使用前要在 VM 创建独立服务用户、安装项目与 Python 环境、设置受保护的配置文件，并提供可访问的 PostgreSQL。文件中的路径是约定，需要按部署目录核对。

VM 路线与容器路线拥有相似责任：确定制品或依赖版本、运行用户、配置来源、启动与停止、日志、健康检查和恢复。不同之处在于打包、隔离和平台操作。不要把复制一个 unit 文件描述为完整部署。

7. 发布单与完成条件#

使用资料页的发布记录模板，填写目标环境、候选与上一健康版本、配置修订、迁移计划、维护窗口、恢复动作和验收结果。计划中的值与实际发生的结果分开写，失败时也保留记录。

本章完成意味着你可以从发布单重建“部署了什么、部署到哪里、怎样判断结果”。真正的故障恢复将在第 20 章验证。没有目标环境访问条件时，保留“未执行”状态，不用预期输出填补证据。
