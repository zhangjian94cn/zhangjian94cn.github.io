CHAPTER 27 · 第 7 篇v0.3 阅读版

配置、密钥和持久化

学习目标更新配置并验证生效；恢复有状态数据访问；解释 PVC、备份和高可用之间的区别
本页目录1. ConfigMap 与 Secret 的用途2. 更新对象不等于更新进程3. PV、PVC、StorageClass 与 CSI4. StatefulSet 提供身份，不提供数据库集群5. 验证重建与数据保留6. 轮换需要应用与数据库协调7. 本章验收

应用镜像可以复用，但环境标识、数据库凭据和数据卷有各自生命周期。把它们全部塞进 Deployment，既难维护，也容易把更新行为理解错。本章分开验证配置注入、秘密更新和持久数据。

前置是第 25 章本地环境。所有数据为虚构工单；目录 k8s/base/ 管理 API，k8s/postgres.yaml 是独立的教学数据库配置。

1. ConfigMap 与 Secret 的用途#

ConfigMap 保存非秘密配置，本例使用 ENVIRONMENT。Secret 用于传递秘密材料；它的 base64 表示是编码，不是保密算法。谁能读取 Secret、控制面是否按策略加密、日志和备份如何处理，都属于额外责任。

本例由 scripts/k8s_secret.py 在本机 .lab/k8s-db.env 生成实验密码和连接串，然后通过文件创建 Secret。文件权限为 0600，已经存在就保留，避免每次重跑都破坏数据库连接。

python3 scripts/k8s_secret.py
kubectl --context kind-ticketdesk -n ticketdesk create secret generic ticketdesk-db --from-env-file=.lab/k8s-db.env

第二行用于首次创建，重复执行出现已存在时应检查已有状态，不应该为了让命令成功就删除秘密并生成新密码。Secret 不随正文下载，也不写进 GitOps 仓库。

2. 更新对象不等于更新进程#

通过环境变量注入的值在容器启动时确定。修改 ConfigMap 后，现有进程通常继续使用旧环境；本例需要重启工作负载并等待新副本就绪。

kubectl --context kind-ticketdesk -n ticketdesk patch configmap ticketdesk-config --type merge -p '{"data":{"ENVIRONMENT":"configuration-experiment"}}'
kubectl --context kind-ticketdesk -n ticketdesk rollout restart deployment/ticketdesk
kubectl --context kind-ticketdesk -n ticketdesk rollout status deployment/ticketdesk

通过 /version 对比 environment 字段。实验后把声明中的值改成你希望长期保留的状态，或重新应用原 base 并滚动重启；不要留下无法解释的手工漂移。

卷挂载的配置文件有不同更新机制，应用也必须支持重新加载；使用 subPath 等方式时还存在额外边界。不能把环境变量、普通挂载和应用热加载当成同一种能力。

3. PV、PVC、StorageClass 与 CSI#

PVC 表达工作负载对存储的请求；PV 表达可供绑定的持久卷；StorageClass 描述如何提供某类存储；CSI 驱动负责与实际存储系统集成。一个 Pending 的 PVC 可能是在等待供应、绑定条件或消费者调度。

kubectl --context kind-ticketdesk get storageclass
kubectl --context kind-ticketdesk -n ticketdesk get pvc
kubectl --context kind-ticketdesk -n ticketdesk describe pvc data-postgres-0

本例请求 1Gi，依赖默认 StorageClass。没有默认供应能力时，配置不会凭空产生磁盘。访问模式、回收策略、扩容、快照与跨节点挂载行为取决于底层系统，必须以实际驱动和卷类型验证。

ReadWriteOnce 常被误解成“只能一个 Pod 使用”；它通常表达单节点读写挂载限制。若需要更强的单 Pod 约束，应核对适合的模式及驱动支持，不能靠名字推断业务互斥。

4. StatefulSet 提供身份，不提供数据库集群#

数据库实例具有稳定名字 postgres-0，对应 PVC data-postgres-0。Pod 被替换时，可以继续使用关联卷；数据库自身仍要正确启动、处理事务并恢复一致状态。

把 replicas 从 1 改为 3，并不会自动得到一个可用 PostgreSQL 主从集群。三个独立数据库目录没有复制、主从选举、写入路由与一致性管理。生产路径应选择合适的托管服务、经过验证的 operator 或自建方案，并明确维护责任。

本例为了观察对象关系使用单实例数据库，账号也按教学需求简化。这些选择不应被描述成生产推荐架构。

5. 验证重建与数据保留#

创建一张带独特标题的工单，记录 ID、状态与优先级。只删除本地 postgres-0 Pod，观察 StatefulSet 重建与卷重新挂载；数据库和 app 就绪后，再查询原记录并比较业务字段。

这个实验验证的是 Pod 替换后数据仍可读取，不是跨可用区恢复，也不是备份。kind 节点本身位于本机容器中，删除整个集群可能同时丢失节点内的存储。不要把本地 PVC 当成独立灾难恢复副本。

6. 轮换需要应用与数据库协调#

只改 Secret 中的 password，不会自动修改已有 PostgreSQL 账号密码。正确轮换要考虑数据库身份生效、旧连接、新连接、工作负载更新与回退窗口。

较稳妥的设计是预先支持新身份或双凭据过渡，验证新连接后逐步切换，最后撤销旧身份。具体过程取决于数据库能力和访问策略，不能在通用模板中假定所有系统支持同时接受新旧密码。

演练中记录秘密的版本标识、时间和验证结果，不记录秘密值。撤销旧身份后，还应证明旧凭据确实失效；新服务正常只是轮换验收的一半。

7. 本章验收#

交付配置变化前后的版本响应、PVC 与实际存储关系、数据库 Pod 重建后的工单对照，以及一份轮换计划。没有运行真实存储驱动或轮换，就保留未执行状态。

参考 Kubernetes 持久卷 与 Secret。后续数据恢复章节还会验证备份时间点、恢复顺序和业务内容。
