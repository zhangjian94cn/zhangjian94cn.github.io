CHAPTER 31 · 第 8 篇v0.3 阅读版

滚动、蓝绿、金丝雀与功能开关

学习目标实作滚动发布和一个受控流量实验；观察错误率后停止晋级；说明何时必须人工处置
本页目录1. 四种手段分别改变什么2. 观察滚动发布的容量与失败3. 先把候选流量区分出来4. 给晋级设置停止条件5. 蓝绿与数据兼容6. 功能开关也要有生命周期7. 恢复、清理与验收

选定候选制品之后，还需要决定如何把流量交给它。不同发布策略改变了容量、观察、流量控制与恢复方式，但都不能消除数据库不兼容或错误业务规则。

本章使用 ticketdesk 本地命名空间，不是前章 Argo CD 管理的 ticketdesk-stage。这样可以观察手工控制；若在 GitOps 管理环境练习，必须先处理协调权和回写流程。

1. 四种手段分别改变什么#

手段 主要变化 代价与前置
滚动发布 逐批替换实例 新旧版本共存、额外容量、探针
蓝绿发布 两组环境之间切换入口 需要接近双份容量与可靠切换
金丝雀发布 先给候选一部分受控流量 流量分配、版本可区分与观察门禁
功能开关 在已部署程序中控制能力开放 开关权限、默认值、清理与组合测试

增加副本数不会自动形成金丝雀策略，部署成功也不等于功能已经向全部用户开放。先说明控制对象，再选择工具。

2. 观察滚动发布的容量与失败#

base 使用两个副本、maxSurge 为 1、maxUnavailable 为 0。理想情况下先增加一个候选，再逐步替换旧实例；如果节点没有余量，更新可能停在等待调度。

kubectl --context kind-ticketdesk -n ticketdesk rollout history deployment/ticketdesk
kubectl --context kind-ticketdesk -n ticketdesk get replicasets
kubectl --context kind-ticketdesk -n ticketdesk rollout status deployment/ticketdesk --timeout=180s

把候选镜像引用改成自己明确不存在的实验标签，可以观察拉取失败和 rollout 超时。Deployment 报告进度问题，并不意味着 Kubernetes 必然自动切回旧模板。恢复动作需要具体控制器、脚本或操作者承担。

3. 先把候选流量区分出来#

k8s/canary.yaml 创建独立候选 Deployment 与 Service，stable/canary 的 selector 互不重叠。默认使用相同教学镜像，只用环境标识区分路径，适合先观察路由；测试真正版本时必须替换为真实候选 digest。

kubectl --context kind-ticketdesk -n ticketdesk apply -f k8s/canary.yaml
kubectl --context kind-ticketdesk -n ticketdesk rollout status deployment/ticketdesk-canary
kubectl --context kind-ticketdesk apply -f k8s/traffic-split.yaml

需要第 26 章 Gateway 已运行。路由配置把相对权重设为 stable 90、canary 10。经网关多次请求 /version，记录返回的 environment 和候选身份；有限样本不会保证恰好 10% 请求落在候选上。

这不是按用户稳定分组的实验，也不能据此验证会话黏性。不同协议、长连接、重试和客户端分布都会影响实际观测，规则语义参考 Envoy Gateway 流量拆分。

4. 给晋级设置停止条件#

在放量前定义观察窗口、有效请求、最小样本、错误和延迟条件，以及谁可以继续或停止。候选与稳定版本需要可区分，否则汇总指标可能掩盖候选异常。

例如教学规则可以是：候选出现预期外 5xx 或关键工单验收失败，就暂停继续放量，先把路由恢复为只到 stable，再调查。阈值应按业务与样本确定，本书不把一个百分比宣称为通用标准。

本例没有自动晋级控制器。路由改为 90/10 只实现流量分配，观察与恢复由实验操作者按发布单执行，不应写成“已实现自动金丝雀回滚”。

5. 蓝绿与数据兼容#

可以把两个独立 Deployment 当成蓝与绿，先直接验证绿，再切换 Service 或网关后端。切换并不保证所有连接瞬间转向新环境，旧连接与在途请求仍需要处理。

新旧两组若共享数据库，需要兼容同一时刻的数据结构和业务语义；若使用两份数据库，则需要另外解决数据同步与一致性。双份应用容量无法单独回答数据怎样回退。

6. 功能开关也要有生命周期#

一个开关至少有名称、默认值、适用环境、负责团队、修改权限、审计和计划移除时间。测试打开、关闭、配置缺失及依赖失败的行为，避免代码只有其中一条路径被长期使用。

为工单新功能增加开关时，优先选择可兼容的增量能力。开关关闭不能自动恢复已经执行的数据变化；涉及写入的功能还需考虑回退后旧程序如何理解新数据。

7. 恢复、清理与验收#

重新应用 k8s/gateway.yaml，使 HTTPRoute 回到稳定后端，验证业务，再删除本次 canary Deployment/Service。不要在仍有候选流量时先删除候选服务。

交付滚动更新观察、90/10 路由与实际采样、停止条件、恢复时间线和旧工单验证。说明哪些动作是自动的、哪些是人工的，以及候选和稳定版本共有的数据库限制。
