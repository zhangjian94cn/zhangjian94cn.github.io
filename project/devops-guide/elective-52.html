复杂 Kubernetes 环境与服务网格

学习目标从“集群维护”或“服务网格”选一个代表案例，给出必要性论证和故障演练
本页目录先判断是否需要集群底座仍然存在双向 TLS 和授权是两件事最小策略与应用范围三类请求验证故障与诊断路径维护代价与独立验收

当多个服务之间需要统一身份与加密，应用各自维护证书可能变得困难。服务网格能接管部分流量和身份处理，同时引入代理、控制面、证书轮换和新的故障路径。本专题只深入一个案例：在独立实验命名空间中验证 Istio sidecar 模式的严格双向 TLS。

先判断是否需要#

前置是 网络、策略 和 集群维护。还需要一个与所选 Istio 版本兼容的实验集群、已安装并验证的控制面和 sidecar 注入流程。不同安装模式与版本不应混用；本章 YAML 是策略样例，不负责安装完整网格。

若只有一个 API 与数据库，网络边界、TLS 和工作负载身份已经满足要求，增加网格未必划算。多集群也不是高可用的自动答案：身份信任、路由、数据复制、区域依赖和故障切换都要另行设计。

集群底座仍然存在#

托管或自建决定控制面由谁运行；CNI 决定网络及 NetworkPolicy 是否执行；CSI 影响卷供应、挂载和恢复；集群引导、节点更新和证书生命周期决定环境能否持续维护。网格不会替代这些层，更不会备份 PostgreSQL 数据。

升级前先在相同版本组合验证 CNI、CSI、网格代理与 API 兼容性。记录控制面、数据面和插件版本，逐批升级，并保留可观察的验证窗口。跨多个组件同时大幅升级，会增加无法归因的故障。

双向 TLS 和授权是两件事#

双向 TLS 让连接两端验证证书并加密传输；授权回答已确认身份的调用者是否可以执行某个请求。只打开 mTLS，不等于某团队的服务不能调用另一团队所有接口。还需要范围明确的授权策略和业务对象授权。

在 sidecar 模式中，请求经过工作负载旁边的代理。必须确认测试流量确实经过代理，并记录客户端和服务端的工作负载身份。仅看应用返回 200 或网络抓包中没有明文，无法单独证明身份授权正确。

最小策略与应用范围#

先在独立 mesh-lab 命名空间放置已注入 sidecar 的实验服务与客户端，再评审如下策略：

apiVersion: security.istio.io/v1
kind: PeerAuthentication
metadata:
  name: require-mtls
  namespace: mesh-lab
spec:
  mtls:
    mode: STRICT

STRICT 要求适用连接使用 mTLS。它的模式语义以 Istio PeerAuthentication 为准。应用前确认当前 kube context 与命名空间；不要把命名空间省略后误放到网格根命名空间，扩大策略影响。

该 YAML 不应直接施加到主线 TicketDesk 全部资源：PostgreSQL、迁移 Job、入口代理和探针可能尚未完成网格接入。应先列出调用依赖，再逐项检查。将整个业务迁入网格属于后续集成任务。

三类请求验证#

请求 需要证明的结果 证据
已入网格且被允许的客户端 业务成功，身份正确 应用结果、代理连接身份与策略
未入网格的明文客户端 在适用路径上被拒绝 失败阶段、服务端策略、无业务写入
已入网格但无业务权限的客户端 被授权策略或业务授权拒绝 身份已确认但权限不满足的记录

前两项验证 PeerAuthentication；第三项需要另外编写和验证 AuthorizationPolicy 或业务授权，单靠本章策略不会拒绝它。把负例拆开，避免误把网络不通当权限控制成功。

故障与诊断路径#

先让实验服务一个副本没有注入 sidecar，观察它与其他副本行为差异。检查 Pod 容器、代理就绪、证书、控制面连接、服务选择器和路由。再比较经过网格和直接端口访问的路径，不要立刻重启全部控制面。

如果执行严格策略后合法业务全部失败，先恢复实验中的上一份策略以缩小影响，再定位未接入的调用方。不能长期设置任意明文例外后仍宣称已完成严格 mTLS。保留例外原因、范围、到期时间与修复任务。

维护代价与独立验收#

代理增加 CPU、内存和延迟；控制面与证书需要监控和升级；排障多了一层连接。先测量资源开销与关键请求延迟，再判断收益是否覆盖成本。团队需要知道什么时候查应用、什么时候查代理，以及谁维护网格。

提交必要性说明、版本矩阵、三类请求证据、故障恢复过程与资源对照。练习：为什么“开启 mTLS”不能满足“只有账单服务能读取账单”的要求？参考 答案。对于主要困难在节点、存储和控制面恢复的团队，先深化主线第 32、39 章，比立即引入网格更有价值。
