CHAPTER 17 · 第 5 篇v0.3 阅读版

从 PR 检查扩展到完整流水线

学习目标只构建一次候选制品；后续使用同一 digest；测试失败时不进入部署；并发发布有确定行为
本页目录1. 把工作流分成检查和候选发布2. 一次构建的边界在哪里3. 成功路径和失败路径一起设计4. 缓存和制品的职责不同5. 并发控制不等于严格队列6. 权限与人工门禁放在正确位置7. 实验与验收

第 12 章让每个变更接受自动检查。现在要回答更长的一串问题：检查通过后构建什么，候选制品在哪里运行，失败时哪些步骤必须停止，发布记录怎样留下，谁能决定把它送入下一环境。

本章用项目中两份真实工作流解释阶段边界。它们已经编写，但尚未在 GitHub 托管 runner 上运行。请先读懂再在自己的仓库启用，并把实际运行链接加入验收记录。

1. 把工作流分成检查和候选发布#

ci.yml 在 PR 和主分支推送时检查代码；release.yml 在主分支手动触发，构建并发布通过验证的候选镜像。检查一个尚未合并的 PR，不意味着授权它发布软件包或进入生产。

阶段 主要输入 成功证据 失败后行为
接口检查 源码、依赖 pytest 结果 不进入候选构建
构建 确定的源码状态 本地候选镜像 不启动该候选
集成验证 同一候选、临时数据库 迁移与业务检查通过 不推送候选
发布制品 已通过验证的镜像 仓库 digest 不宣称已部署
目标部署 digest、环境配置 目标环境运行记录 按恢复计划处理

当前 release.yml 实现到候选制品发布，不包含访问生产主机的部署步骤。第 18、20 章在本机完成部署与恢复演练，后续云与 GitOps 卷再连接目标环境。

2. 一次构建的边界在哪里#

PR 检查可能构建一次临时测试镜像；主分支合并后又产生新的源码提交，因此发布阶段构建新的候选是合理的。“只构建一次”指选定某个发布候选之后，集成验证、推送和后续晋级复用该候选，而不是规定整个仓库一生只能构建一次。

配套发布流程先设置 APP_IMAGE 和 COMMIT_SHA，执行 docker compose build app。随后启动 app 时加 --no-build，迁移任务与应用使用相同镜像引用。业务检查成功后，推送这个本地镜像，再记录仓库返回的 digest。

推送前的本地标签和推送后的仓库 digest属于不同引用形式。流水线不能在检查之后又悄悄 rebuild；如果必须重建，应把它视为新候选并重新验证。

3. 成功路径和失败路径一起设计#

上面的交互是状态推演，不会执行 CI。它展示一个关键规则：失败应阻断依赖该结果的后续步骤，但日志收集和临时资源清理仍要有机会执行。

配套工作流在日志与清理步骤使用 if: always()。这不意味着任意清理命令都安全；只有本次任务创建的临时 Compose 项目才可以连卷删除。生产数据库、共享测试库和开发者本地数据不能套用同一清理策略。

检查失败还应让顶层任务失败。不要为了继续收集日志，到处加 || true 或 continue-on-error；否则界面变绿，实际风险却被隐藏。如果某个步骤允许失败，应明确它是可选信息还是阻断门禁。

4. 缓存和制品的职责不同#

缓存可以丢失、被淘汰或因 key 变化不命中。它用于加速依赖下载和构建，不是发布证据。制品是一次运行需要保存或交接的输出，例如测试报告、镜像、部署清单和版本记录。

本项目的发布工作流把镜像保存到 GHCR，把 digest 写入运行摘要；runner 上的 candidate-digest.txt 是临时文件，尚未通过 artifact 步骤长期保存。不要假设任务结束后还能访问 runner 工作目录。

后续添加报告上传时，应指定保留时间、访问范围和大小上限。包含凭据、客户数据或完整环境变量的调试输出不应成为永久制品。失败报告至少需要步骤名、源码身份和经脱敏的错误，避免只保留一句“任务失败”。

5. 并发控制不等于严格队列#

发布工作流使用固定的 concurrency group，并设置 cancel-in-progress: false，避免一个新运行直接取消正在执行的候选发布。这个配置不保证所有触发都按先来先服务顺序逐个完成；当前配置采用默认的单个 pending 行为，新请求可能替换已有待运行任务。若需要保留更多待运行项，可以评估官方提供的 queue 配置，但也要定义队列容量和发布顺序。参阅 GitHub 并发控制。

如果业务要求每个版本都发布，或者某个版本必须严格排在另一个之后，需要显式的发布编排与版本选择规则。不要把一个互斥开关误读成完整的发布队列。

此外设置任务超时，避免无人值守的流水线无限等待。在实验中让一个检查故意超时，观察后续门禁与清理行为，比仅阅读 YAML 更能发现流程缺口。

6. 权限与人工门禁放在正确位置#

PR 检查只读仓库。发布 job 额外申请包写入权限，凭据只在需要推送的步骤使用。第三方 Actions 固定到完整 Commit SHA，更新时重新评估来源和变更；固定引用并不代表永远不用更新。

将来部署生产时，把人工审核、目标环境权限和短期身份放在实际部署边界。一次代码评审不自动等于任何时间、任何环境的部署许可。来自不可信分支的内容也不能因为“CI 需要运行”而获得部署秘密。

参阅 GitHub Actions 安全使用指南 与 工作流语法。

7. 实验与验收#

在自己的练习分支让一个断言失败，创建 PR，记录检查失败位置以及未执行的步骤。修复后再次运行，记录通过结果。随后从主分支手动发布候选，检查是否只有一个被验证的候选被推送，以及摘要能否追溯到准确 Commit。

并发实验可以连续触发两次候选工作流，观察运行、等待、替换或取消状态，记录实际平台行为。实验只发布自己的练习包，不涉及生产。最终提交成功、失败、清理三条路径的证据，以及尚未实现的报告保留和目标部署说明。
