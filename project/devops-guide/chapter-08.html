CHAPTER 08 · 第 2 篇v0.3 阅读版

用 Bash 和 Python 编写可靠自动化

学习目标编写健康检查与备份调用脚本，输出结构化结果；重复运行无副作用，失败返回非零状态
本页目录1. 把脚本当成一个接口2. 一个最小 Bash 健康检查3. Python 更适合处理 JSON4. 重试必须有边界5. 幂等不是“命令看起来一样”6. 调用外部程序时保留参数边界7. 测试脚本的失败路径8. 实践与验收

把十条命令放进文件只是自动化的开始。可靠脚本还要知道在哪里执行、输入是否合法、失败如何传递、等待多久、重复运行会发生什么，以及怎样留下便于解释的结果。

本章使用健康检查作为例子。Bash 适合连接现有命令，Python 更适合结构化数据、复杂判断和可测试逻辑。

1. 把脚本当成一个接口#

脚本有输入、输出和退出状态。输入可以来自命令参数或明确的配置，输出可以是机器可读 JSON，诊断信息进入标准错误。成功返回 0，失败返回非零，调用者据此决定是否继续。

设计问题 好的约定
参数遗漏 给出简短用法并退出失败
目标不明确 显示环境和资源，拒绝危险默认值
依赖不存在 自检发现并指出安装或准备步骤
网络不响应 有连接和总超时
部分完成 说明完成到哪一步，保留诊断证据
重复执行 有可解释的幂等性或重复影响

例如备份脚本打印“完成”之前，至少应确认命令成功和文件存在；进一步的“恢复可用”还需要实际恢复与数据校验。

2. 一个最小 Bash 健康检查#

#!/usr/bin/env bash
set -euo pipefail

lab_url="${1:-http://127.0.0.1:8000/health/ready}"
if ! curl --fail --silent --show-error \
  --connect-timeout 2 --max-time 5 "$lab_url"; then
  printf 'Readiness check failed\n' >&2
  exit 1
fi
printf '\n'

变量被双引号包围，避免空格或特殊字符改变参数边界。curl --fail 让 HTTP 错误成为失败状态。显式判断使读者知道哪个结果控制流程。

set -e 在条件、管道和子 shell 中存在具体语义，并不是“任何错误都自动安全退出”的保证。对于关键步骤，仍应显式检查，并阅读目标 shell 文档。不要在网络发布脚本里写 || true 把失败统一吞掉。

3. Python 更适合处理 JSON#

下面只执行一次有超时的 GET，不会改变服务器数据：

import json
import sys
import urllib.error
import urllib.request

url = 'http://127.0.0.1:8000/health/ready'
try:
    with urllib.request.urlopen(url, timeout=5) as response:
        result = json.load(response)
    if result.get('status') != 'ready':
        raise ValueError('unexpected readiness payload')
except (urllib.error.URLError, ValueError) as error:
    print(json.dumps({'ready': False, 'error_type': type(error).__name__}))
    sys.exit(1)
print(json.dumps({'ready': True}))

脚本同时检查 HTTP 和响应字段。即使一个代理返回了 200 的错误页面，JSON 解析或字段检查也不会把它当成正确业务结果。Python 虚拟环境的隔离方法见 官方 venv 说明。

4. 重试必须有边界#

重试可以处理短暂失败，但也会增加依赖负载。至少要约定总时限、最大次数、间隔，以及哪些失败可以重试。连接超时与输入错误的处理不应相同。

GET 健康检查通常可以重复执行。创建工单的 POST 则可能在服务端已成功、客户端却没收到响应时被重发，造成重复工单。如果接口没有幂等键或其他去重机制，不能简单把所有写请求放进重试循环。

本项目的等待就绪采用有限次数轮询；业务冒烟会创建教学记录，所以每次检查会留下数据。这一点写在实验说明里，避免读者把它误认为完全无副作用的检查。

5. 幂等不是“命令看起来一样”#

幂等操作重复执行后，应保持约定的目标状态。例如“确保目录存在”可以重复；“再追加一行配置”通常会越来越多；“把密码随机生成后覆盖”则会破坏已有连接。

lab.py init 发现 .env 已存在时保留它，这是一种保护已有状态的设计。迁移器记录已经应用的文件和校验和，重复执行会跳过，发现旧迁移被修改则拒绝继续。它们都需要明确的状态信息。

6. 调用外部程序时保留参数边界#

import subprocess

subprocess.run(
    ['docker', 'compose', 'ps'],
    check=True,
    timeout=20,
)

把参数作为列表传入，可以避免将输入拼成 shell 代码。确实需要 shell 时，要另外处理引用与注入风险。不要为了简短，把工单标题、PR 标题或任意用户输入直接嵌入命令字符串。

凭据通常通过受控环境或文件传递，日志只记录必要的标识，不打印完整数据库连接串。错误报告应保留错误类别和操作阶段，而不是暴露秘密。

7. 测试脚本的失败路径#

健康检查至少测试四种输入：正常响应、HTTP 错误、超时、HTTP 200 但内容错误。你可以使用测试替身产生这些结果，先验证判断逻辑，再在真实服务上检查集成行为。

自动化测试应关心外部可观察结果：退出状态、输出字段、是否执行了不该执行的动作。只检查“某函数调用了某函数”，容易与实现一起出错。

8. 实践与验收#

阅读 scripts/lab.py，找出环境自检、就绪等待、业务检查、成功状态记录和清理入口。解释为什么发布目标只有在检查通过后才进入恢复记录。

独立练习：给健康检查增加最大等待时间和 JSON 结果，不自动重试创建工单。验收要求正常时返回成功，错误时返回失败，等待有上限，日志不含凭据，重复运行的影响已说明。
