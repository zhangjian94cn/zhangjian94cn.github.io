OpenTelemetry 与关联排障

学习目标追踪一次应用到数据库的请求；从慢请求进入 span，再关联日志；验证脱敏与采样配置
本页目录1. trace、span 与上下文2. 自动埋点、手工埋点与业务边界3. Collector 承担采集管道4. 构建可选观测镜像5. 跟踪一次创建与查询6. 采样决定能看见什么7. 验收与恢复

指标告诉你请求慢了，日志告诉你某次请求失败，却未必解释时间花在哪个依赖。分布式追踪把一次请求拆成有关联的 span，让你观察服务端处理、数据库访问与上下文传播。

本章在本地虚构数据上练习。配套额外提供观测镜像 Dockerfile、已解析的可选依赖和 Collector 配置；它们与基础镜像分开，避免让所有入门步骤都依赖追踪栈。真实跨数据库追踪尚待容器验证。

1. trace、span 与上下文#

trace 表达一次有关联的执行；span 表达其中某段工作，包含身份、父子关系、时间和属性。上下文随调用传播，使下游能把自己的工作放到同一条链上。

request ID 是项目的请求日志标识，不自动等于 trace ID。它们可以并存。启用有效 OpenTelemetry 上下文时，应用日志额外记录 trace_id 与 span_id，帮助从日志定位到同一条追踪。

2. 自动埋点、手工埋点与业务边界#

自动埋点可以围绕 HTTP 框架和数据库驱动建立常见 span，但不知道“审批通过”或“工单分类完成”代表什么。手工埋点适合补充明确的业务阶段，不应把每个函数调用都变成一条昂贵 span。

本例选择 FastAPI 与 psycopg 对应的 instrumentation，连接 HTTP 与数据库调用。使用方法参考 Python 自动埋点 与 psycopg instrumentation。

3. Collector 承担采集管道#

接收器接收信号，处理器做批处理、资源保护或必要变换，导出器发送到后端。本例使用 OTLP HTTP 接收追踪、内存限制、精确字段删除和批处理，再导出到本地诊断日志。

删除两个已知属性不能证明所有敏感字段都被清理。应首先限制源端采集，不默认捕获请求正文、认证头与用户数据；再使用受控样例检查完整导出内容。

Collector 不是永久追踪存储。本例的 debug exporter 用来观察链路，后续接入查询后端时，还要设计保留、访问、成本和服务可用性。

4. 构建可选观测镜像#

先按基础章节构建当前 ticketdesk:dev，再构建可选镜像：

python3 scripts/observability_init.py
docker build -f observability/Dockerfile.otel -t ticketdesk:otel-lab .
docker compose -f compose.yaml -f observability/compose.yaml up -d collector
docker compose -f compose.yaml -f observability/compose.yaml -f observability/otel-app.yaml up -d --no-build --no-deps app

初始化脚本保留已有配置，并为整个观测 Compose 文件补齐独立 Grafana 密码；即使只启动 Collector，Compose 也会解析该文件的必填变量。额外 overlay 设置服务名、Collector 地址与教学采样策略，基础指标仍由项目自身提供。数据库与迁移沿用已准备好的本地环境。

不要把同一份源码的普通镜像与观测镜像说成同一个制品。它们依赖和启动命令不同，需要分别记录身份与验证；实际生产通常在明确的发布构建中统一观测能力。

5. 跟踪一次创建与查询#

创建一张虚构工单，记录 HTTP 请求的 request ID。在 app 日志中查看有效 trace_id，再在 Collector 输出中观察接收情况。默认 basic 输出较简略；在完全虚构的本地实验中，可临时切换 debug verbosity 为 detailed，检查 span 关系，结束后恢复简略输出。

预期能观察 HTTP span 与数据库相关工作。若只有 HTTP，核对驱动版本和 instrumentation 是否加载；若没有 trace，依次检查应用埋点、采样、OTLP 协议、地址、接收器与导出器，不先断定请求没有发生。

还应确认查询参数或秘密没有意外进入属性。只有看到一份完整导出样例，才能判断当前配置实际采集了哪些字段。

6. 采样决定能看见什么#

全采样适合小规模实验，不适合直接套入所有生产流量。头部采样在早期决定保留哪些请求；尾部采样可以按更完整结果决策，但需要额外收集、缓存与一致路由等条件。

采样率变化会影响成本与诊断证据，不能把采样后错误 trace 的数量直接当成全部请求错误率。控制观测开销时，优先明确需要的属性、保留窗口和典型问题，再选择采样方案。

7. 验收与恢复#

提交一条请求的日志—trace 关联、HTTP 与数据库 span 解释、缺失信号的排查顺序，以及实际导出字段检查。恢复普通应用镜像时使用对应 Compose 配置，验证旧工单与新写入；只停止 Collector 而不检查应用导出行为，可能留下额外重试开销。
