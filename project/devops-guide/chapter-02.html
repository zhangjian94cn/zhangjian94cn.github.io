CHAPTER 02 · 第 1 篇v0.3 阅读版

准备实验环境并学会自检

学习目标完成环境自检，记录 OS、架构、资源、网络可达性；按输出修复一个安装问题
本页目录1. 选择一条环境路径2. 下载后，先认清目录3. 运行随书自检4. Python 环境要可以重新创建5. 处理配置、网络和端口6. 记录环境，减少“我这里没问题”7. 练习：区分三种失败8. 本章验收

相同命令在别人电脑上成功，在你的电脑上失败，通常不是因为命令“看运气”。操作系统、CPU 架构、解释器、权限、端口、网络和缓存都可能不同。本章建立一个可以说明这些差异的实验环境。

目标是准备 Python、Git、Docker 与 Compose，能够解释自检输出。后面的 Kubernetes、可观测性后端和云账号都按章节需要再加入。

1. 选择一条环境路径#

你的电脑 建议路径 需要注意
Linux 支持的发行版、Python 3.12+、Docker Engine 与 Compose v2 使用发行版对应的官方安装说明
Windows WSL2 中运行 Linux 命令，配合兼容的容器运行环境 分清 Windows 终端、WSL 终端和文件路径
macOS Python 与 Git，本地容器运行环境 systemd 实验另用 Linux VM；区分 arm64 与 amd64
企业内网电脑 使用组织允许的镜像源、包源和实验 VM 先记录访问限制，后续再迁移到自托管 CI

Docker Engine 安装说明按平台区分，见 Docker 官方安装入口。不要在不匹配的发行版上机械复制软件源命令，也不要为了绕过错误直接关闭证书验证。

建议先为轻量实验预留约 8 GB 主机内存和 25 GB 磁盘。它是起步预算，不是经过所有平台验证的最低要求。关闭不用的服务，再用实际观测确定是否需要更多资源。

2. 下载后，先认清目录#

从本站下载“TicketDesk 配套项目”，解压并进入 ticketdesk 目录。这里应该能看到 app/、migrations/、scripts/、compose.yaml、Dockerfile 和 README.md。

后文如无特殊说明，命令都在这个目录执行，终端采用 Linux/WSL/macOS 的 Bash 或兼容 shell。代码块不带 $ 提示符，便于复制；终端输出会另外展示。

pwd
ls
python3 --version
git --version
docker version
docker compose version

docker version 同时涉及客户端和服务端。只有 CLI 文件存在，不代表后台容器服务已经启动。docker compose version 用来确认 Compose v2 命令可用，不要与旧版独立的 docker-compose 混淆。

3. 运行随书自检#

python3 scripts/lab.py doctor

自检会返回一组布尔值，并在有必要条件缺失时以非零状态退出。当前检查 Python 版本、Git、Docker CLI、Compose 和 Docker 服务连接。它不会证明所有镜像都能下载，也不会自动修改你的系统。

输出或现象 首先检查 不应直接推断
python_3_12_or_newer: false 当前解释器位置和版本 系统完全没有 Python
找不到 Docker CLI 安装与 PATH 网络出了问题
CLI 存在但 daemon 不通 后台服务、socket 权限、运行环境状态 应用镜像坏了
镜像拉取超时 DNS、代理、仓库访问、账户限额 Dockerfile 有语法错误
端口被占用 已有服务和之前的实验 随意结束所有相关进程

在 Linux 上，Docker socket 权限具有重要安全含义。先理解组织允许的使用方式；不要把 sudo 或随意加入高权限组作为所有错误的通用答案。

4. Python 环境要可以重新创建#

创建项目专用虚拟环境，避免把教学依赖安装到系统解释器：

python3 -m venv .venv
.venv/bin/python -m pip install -r requirements-dev.txt
.venv/bin/python -m pytest -q

这里直接使用 .venv/bin/python，无需依赖终端当前是否激活环境。若使用原生 Windows PowerShell，对应解释器路径是 .venv\Scripts\python.exe；本书主要操作仍建议在 WSL 中进行。

虚拟环境本身不应加入 Git。把依赖清单记录下来，在另一个环境重新安装，比复制整个 .venv 更可靠。虚拟环境的行为与平台差异见 Python venv 文档。

5. 处理配置、网络和端口#

python3 scripts/lab.py init

这条命令在本机生成 .env，包含随机数据库实验密码和端口。已有文件会保留。密码不会打印出来，也不应复制到 Issue、截图或公共仓库。

默认应用地址为 127.0.0.1:8000，数据库映射到 127.0.0.1:55432。如端口冲突，在 .env 修改 APP_PORT 或 DB_PORT。修改后，用脚本启动和检查时会读取相同设置；手写的浏览器地址或 curl 命令也要相应调整。

配置代理时区分四种访问：浏览器访问文档、pip 下载包、Docker 服务下载镜像、运行中的应用访问依赖。为浏览器设置代理，并不必然使容器服务使用相同代理。记录哪一层失败，再修改那一层的配置。

6. 记录环境，减少“我这里没问题”#

在个人实验笔记中建立一张表：操作系统、CPU 架构、Python 版本、Docker/Compose 版本、镜像标识、项目版本、代理情况和最近一次成功启动时间。

不要把所有环境变量整段公开。printenv、docker inspect 和 docker compose config 可能显示敏感配置。需要求助时，只截取相关字段并遮蔽凭据。

本版验证页明确区分已经运行的 Python 接口测试，以及尚未在作者环境完成的 Docker、真实数据库和托管 CI 实验。你在本机跑通后，也应记录自己的环境，不能只写“成功”。

7. 练习：区分三种失败#

分别判断以下情况，并写出下一条检查动作：

  1. docker --version 成功，但 docker info 失败。
  2. 单元测试成功，但拉取 PostgreSQL 镜像超时。
  3. 应用启动日志正常，但浏览器访问另一个端口失败。

参考方向分别是：容器服务连接或权限、镜像获取链路、访问地址与端口映射。它们发生在不同层次，不能全部归因于业务代码。

8. 本章验收#

  • 能解释当前使用的终端、解释器和项目目录。
  • 自检通过，或准确记录尚未满足的条件及处理方法。
  • Python 接口测试可以执行，并知道它尚未验证真实数据库。
  • .env 留在本机，端口和网络依赖已明确。
