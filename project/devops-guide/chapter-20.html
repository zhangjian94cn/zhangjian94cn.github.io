CHAPTER 20 · 第 5 篇v0.3 阅读版

把发布、观察、故障和恢复串起来

学习目标完成一次成功发布及一次失败恢复；旧版本恢复服务，指定数据仍可读取，证据能串联到 PR
本页目录1. 建立一份能复查的基线2. 先理解三个观察入口3. 实验 A：配置故障与修复4. 实验 B：失败候选与应用回退5. 恢复之后继续观察6. 写一份不归咎个人的复盘7. 第一阶段最终验收

前面各章分别检查了代码、镜像、配置和数据。这一章把它们连起来：发布一个已知健康版本，建立观察基线，制造一个可控故障，选择恢复动作，再证明指定业务数据仍能使用。

所有故障注入仅面向你自己的本地 TicketDesk 实验环境，不接真实流量。整个容器实验尚未在本教程编写环境执行；以下是可操作的实验步骤和明确的预期，最终“通过”必须由你的实际结果决定。

1. 建立一份能复查的基线#

python3 scripts/lab.py up
docker image tag ticketdesk:dev ticketdesk:known-good
python3 scripts/lab.py deploy --image ticketdesk:known-good
python3 scripts/lab.py check
curl --fail-with-body http://127.0.0.1:8000/version

记录最后一次检查输出的 ticket_id，下文用 1 演示，需要替换成这个真实 ID。再保存该工单的标题、状态和优先级。known-good 是本机练习标签，仍然可能被覆盖；本实验不再修改它，正式发布使用第 16 章的仓库 digest。

保存版本响应、当前配置修订和日志时间。使用正式候选时，还应填入 Commit、构建记录和 digest；本机未提交源码构建得到的 dev/unrecorded 只适合练习，不能冒充完整追踪证据。

2. 先理解三个观察入口#

/health/live 检查应用进程能否响应；/health/ready 检查数据库及需要的 schema；/metrics 提供本例进程内的请求计数与时长累计。指标是教学实现，进程重启会清零，多进程间不聚合。总耗时除以次数只能得到均值；v0.3 增加的直方图可用于估算 p95，计算与边界见第 34 章。

结构化日志包含 request ID、路由模板、状态码和耗时。路由用 /tickets/{ticket_id} 这样的模板归一化，避免为每个 ID 产生一个指标标签。日志与指标都不应写入密码或整张工单的敏感内容。

curl --fail-with-body -H 'X-Request-ID: exercise-20' http://127.0.0.1:8000/tickets/1
docker compose logs --tail 50 app
curl --fail-with-body http://127.0.0.1:8000/metrics

用 request ID 在日志中定位这个请求，对比响应和日志状态。请求数存在不代表所有请求成功；平均耗时也可能掩盖少量极慢请求。第 33—36 章继续讲解指标、追踪与告警的配套配置及验证。

3. 实验 A：配置故障与修复#

交互只解释检查的含义。实际注入使用：

python3 scripts/lab.py fault
curl -i http://127.0.0.1:8000/health/live
curl -i http://127.0.0.1:8000/health/ready
curl -i http://127.0.0.1:8000/tickets/1
docker compose logs --tail 50 app

脚本把 app 的数据库主机名改为一个不存在的实验名称，数据库与数据卷不受修改。预期 live 仍能响应 200，ready 与依赖数据库的业务请求返回 503。记录注入开始、发现异常和开始恢复的时间。

根据症状解释原因：进程可用、依赖不可达，此时反复重启数据库没有直接依据。恢复正确应用配置：

python3 scripts/lab.py recover
python3 scripts/lab.py check --ticket-id 1
curl --fail-with-body http://127.0.0.1:8000/tickets/1

将旧工单各字段与基线对照。这是配置修复实验，不把它记作“旧代码回滚”或“数据库恢复”。三种动作在报告中使用准确名称。

4. 实验 B：失败候选与应用回退#

为了学习恢复路径，在本地有意绕过正常发布门禁，构造一个启动即退出的候选。这个故障镜像只存在本机，不推送到正式仓库。

新建临时文件 .lab/Dockerfile.broken：

FROM ticketdesk:known-good
CMD ["python", "-c", "raise SystemExit('intentional local startup failure')"]

构建并尝试部署：

docker build -f .lab/Dockerfile.broken -t ticketdesk:broken .
python3 scripts/lab.py deploy --image ticketdesk:broken
docker compose ps -a app
docker compose logs --tail 50 app

部署会等待就绪并最终失败，可能需要数十秒。预期脚本以非零码退出，失败候选不会写入 .lab/release.json。这时应用进程已经退出，HTTP 请求可能连接失败，而不是收到应用返回的 503。

执行 lab.py recover，它应选择上一次通过验证的 ticketdesk:known-good。再运行针对原工单的检查，保存运行镜像、版本响应和业务结果。如果镜像标签被覆盖、迁移已破坏兼容或数据被改变，恢复不一定成立，这也是前面建立回退边界的原因。

5. 恢复之后继续观察#

一次业务检查通过只是恢复的开始。为练习设定一个明确观察窗口，例如五分钟，周期性读取同一工单并检查错误日志，记录重启次数、错误率的观察范围和数据变化。五分钟是练习设置，不是所有生产服务的通用标准。

如果没有自动监控，就在报告中写明通过人工请求观察；不要写“告警自动发现”或“已验证服务等级目标”。恢复耗时从哪个时刻开始、到哪个条件结束也要定义，否则两次演练无法比较。

6. 写一份不归咎个人的复盘#

使用资料中的复盘模板，写清影响、时间线、证据、直接原因、检测缺口和改进项。每项改进有责任人角色、验证方式和优先级，而不仅是“加强意识”。

示例改进可以是：候选启动后先进行就绪和业务验证；配置变化进入评审；保留可用旧制品；恢复流程检查指定历史工单。区分已经实现的措施与计划改进，不要把同一个建议在每次复盘中原样重复却不验证。

7. 第一阶段最终验收#

验收项 应提交的证据
需求与代码 Issue、PR、Commit 与接受条件对应
自动检查 正常通过与故意失败的运行记录
制品身份 同一候选的构建、验证、digest 记录
数据兼容 迁移记录、请求兼容结果、未覆盖边界
两种恢复 配置修复与失败应用回退的独立时间线
数据保持 指定旧工单在恢复前后的字段对照
备份有效 实际恢复到新数据库后的业务内容比较

能够解释失败原因并保留证据，比把每格都填成“成功”更有意义。如果只完成了正文阅读，请标记为已读；完成本机容器实验、托管 CI 与独立复现后，再分别标记相应验收结果。下一阶段进入云资源、IaC 与 Kubernetes，把这个交付闭环迁移到更复杂的运行环境。
