云平台迁移与 Serverless

学习目标选一个目标平台迁移最小服务，比较费用、权限、可观测性和运行限制
本页目录前置与迁移边界从产品名回到能力适配一个具体运行契约缩容到零不是没有运行约束先做受限的迁移验证函数方案与成本取舍验收与练习

容器能启动，并不表示它已经可以迁移到任意云。真正需要迁移的是运行契约：入口、身份、网络、状态、并发、超时、日志和发布行为。本专题选择把 TicketDesk 的 HTTP API 迁往 Google Cloud Run 的方案设计，作为托管容器案例；不要求开通付费资源。

前置与迁移边界#

先理解 云基础、应用配置 和 容量。实验需要一个已验证镜像、外置数据库、受限服务身份与可达网络。真实部署还需要云项目、账单、配额和目标区域。本版未执行云端部署，所有费用必须在你的当前区域核算。

选择 Cloud Run 是为了具体讨论一个运行契约，不表示它适合所有地区、合规要求或工作负载。若已有 AWS、Azure、阿里云或腾讯云环境，应按下列能力重新映射，而不是照搬命令。

从产品名回到能力#

能力 跨平台需要重新确认的问题
身份 工作负载怎样取得短期凭据；谁有部署和调用权限
网络 数据库是否私有；出入站路径、DNS 和流量计费在哪里
执行 HTTP 容器、函数、批任务分别受什么生命周期约束
状态 数据库、对象存储、临时文件如何区分
发布 版本、流量切换、回退与 Secret 版本怎样关联
观察 日志和指标怎样查询；费用、保留与跨区限制是什么

厂商的 IAM policy、角色继承、默认网络和监控标签并不通用。OpenTofu 可以描述不同 provider 的资源，但不能把这些语义差异自动消除。用一份能力表和实测证据比单纯追求“完全不依赖厂商”更可行。

适配一个具体运行契约#

Cloud Run 服务容器需要监听平台配置的端口和 0.0.0.0；运行本地文件不是持久数据。入口 TLS 与容器内部连接的处理也有平台约定，具体依据见 Cloud Run 容器运行契约。

TicketDesk 当前监听 0.0.0.0:8000，可以将目标容器端口明确设为 8000；若改为读取 PORT，应新增启动参数实现与测试，不能仅添加环境变量就假定 Uvicorn 会自动使用。构建时还要确认目标平台支持的镜像架构，不能直接部署本机仅有的其他架构镜像。

数据库不能与 API 一起装进短生命周期容器。把数据库放到适合的托管或独立服务，注入连接凭据并验证私有网络可达。迁移在单独、受控的任务中执行；每次实例扩容时执行 schema 变更容易产生并发问题。

缩容到零不是没有运行约束#

自动扩缩容会改变连接数和启动行为。每实例连接上限乘以最大实例数，可能超过数据库容量；必须把实例并发、最大实例数、连接池和数据库余量一起估算。当前 TicketDesk 为教学简化，每次数据库操作建立连接，云端之前应测量并决定是否加入池化。

长时间后台任务不能依赖一次 HTTP 请求返回后仍能无限执行。选择平台提供的任务或队列机制，持久化任务状态并实现幂等，见 事件驱动专题。本地临时文件、进程内计数和缓存也不能当跨实例共享状态。

先做受限的迁移验证#

记录候选 digest、容器端口、资源、最大实例数、数据库连接预算、调用身份和日志保留。默认保持受限调用；当前 API 缺少业务认证，不能因为平台提供公网 URL 就允许任意用户操作工单。

在目标预发布环境分别验证：授权请求成功、未授权请求被拒绝；冷启动后的首次请求；并发下的连接数；实例替换后数据仍存在；错误配置不会被误判成功；回到旧版本与相容配置后业务恢复。保存结果，之后再考虑流量晋级。

这里没有提供“一键部署并公开”的脚本，因为账户、区域、网络和身份是方案的一部分。读者交付的是已填完整的部署计划和在自己受控环境的结果，而非缺少这些条件的通用命令。

函数方案与成本取舍#

函数适合边界清晰、由事件触发的任务，但将整个 FastAPI 服务换成函数，需要处理请求适配、依赖大小、执行时间、并发和数据库连接，不能只改部署名称。迁移前先用独立的小任务证明收益。

比较请求量、运行时长、保留实例、网络、数据库和观测总成本；托管服务减少了部分运维工作，但仍需维护应用和运行策略。低流量省下的计算费用可能小于数据库固定费用，稳定高负载也可能有另一种成本曲线。

验收与练习#

提交能力映射、运行契约检查表、最小权限设计、成本假设、迁移/回退顺序与真实执行范围。练习：最大 20 个实例，每实例最多 10 个数据库连接，数据库留给应用 120 个连接，怎样调整并验证？参考 答案。重点是把限制变成可验证参数，不是记住某个厂商的产品列表。
