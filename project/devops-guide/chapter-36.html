设计可行动的告警和排障手册

学习目标注入延迟或依赖错误，告警能够触发、定位、恢复；观察短暂抖动是否产生噪声
本页目录1. 从用户症状出发定义行动2. 理解 pending 与 firing3. 分组、抑制、静默分别解决什么4. 本地触发与恢复实验5. 真实接收渠道另做端到端验收6. Runbook 从最小判断开始7. 验收

一个告警是否有用，取决于接收者能否理解影响并采取动作。把所有资源波动都通知值班人员，会逐渐消耗信任；只有面板而没有接收和处理流程，也无法形成可靠响应。

前置是第 34 章的采集与真实业务流量。配套规则用于本地学习：目标失联、创建工单持续出现 5xx。默认 Alertmanager 接收器只用于本机观察，没有配置或发送任何外部通知。

1. 从用户症状出发定义行动#

“创建工单持续失败”比“CPU 超过某个数字”更接近用户影响。资源信号仍然重要，可以用于诊断、容量预警和某些明确故障，但不应把原因猜测当成唯一症状。

一条告警至少包含名称、影响对象、触发条件、持续时间、严重程度、负责角色、排障入口与恢复条件。标题帮助接收者做第一步判断，详细说明提供版本与诊断链接，而不是把完整日志塞进通知。

2. 理解 pending 与 firing#

规则表达式成立后，配置的 for 要求它持续一定时间，才进入 firing。抓取间隔、计算间隔与 for 共同决定发现延迟；短暂恢复或数据缺失的行为需要依据系统规则实际观察。

配套目标失联规则要求 up == 0 持续一分钟。业务错误规则观察两分钟窗口，并要求条件持续一分钟；实验阈值只用于学习，不是生产统一标准。语法和状态参考 Prometheus 告警规则。

没有业务请求时，错误率表达式未必提供有意义结果。目标失联、没有流量、请求失败是不同情况，应由相应信号和解释处理，不能简单把空值转成 0 后宣布正常。

3. 分组、抑制、静默分别解决什么#

分组将相关告警合并，避免同一事件产生大量重复消息；抑制在明确关系下减少伴随告警；静默用于有范围与期限的临时通知控制。它们一般不修复问题本身。

为维护窗口设置静默时，限定环境、对象、时间和原因，避免误覆盖其他服务。严重事故中一个根因触发很多症状，也不能在没有依赖证据时随意抑制全部用户影响。

4. 本地触发与恢复实验#

确认应用正常被抓取，然后只停止 app，观察 Targets、Prometheus Alerts 和 Alertmanager 页面。记录从停止、首次失败采样、pending 到 firing 的时间，再启动应用并执行健康与业务检查。

docker compose stop app
docker compose start app
python3 scripts/lab.py check --ticket-id 1

停止与恢复之间需要实际观察窗口，不应把三行一次粘贴后立即宣称告警触发。原工单 ID 用自己的记录替换。这个练习验证规则和本地路由，不验证真实通知送达。

数据库故障实验则保持 app 可抓取，注入本地错误配置，再按有上限的节奏发送创建请求，使错误信号被采集。恢复后确认错误率逐步回落，窗口中历史错误不会瞬间消失。

5. 真实接收渠道另做端到端验收#

接入自己的邮件、消息或事件平台时，使用对应受控凭据，指定实验接收者和时间，验证通知触发、内容、确认、升级和恢复消息。不要仅凭 Alertmanager 接受配置就声称值班人员会收到通知。

本教程不预置第三方收件地址，也不把任何真实 token 放进配置。默认本地接收器为空是明确的功能边界，实际接收能力由读者在授权渠道中补齐。

6. Runbook 从最小判断开始#

资料中的运行手册按“适用范围—影响—最小检查—决策—动作—恢复验证”组织。先核对环境与最近变更，再选择检查步骤。恢复需要同时验证关键业务与指定已有数据。

手册不能只有一串危险命令，也不应要求值班者先读懂整个系统。对会修改数据、暂停协调或扩大容量的动作，写明适用证据、边界与停止条件。值班者遇到不确定情况时，知道找谁比盲目继续更重要。

7. 验收#

提交一次短暂抖动与一次持续异常的对照、告警状态时间线、恢复过程和实际接收验证范围。记录误报、漏报和行动是否清楚，删除没有行动价值的重复通知。

后续 SLO 章节会使用错误预算描述紧迫性；它补充业务目标与时间范围，不是把所有阈值告警一键换成另一套固定数字。
