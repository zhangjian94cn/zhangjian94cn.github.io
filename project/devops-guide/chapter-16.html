CHAPTER 16 · 第 4 篇v0.3 阅读版

镜像仓库、版本和制品身份

学习目标发布镜像，按 digest 拉取；从运行版本追到 Commit 和构建记录；证明改 tag 不改变已固定的部署身份
本页目录1. tag 用于命名，digest 用于固定内容2. 建立可追踪的四个字段3. 用配套流水线发布候选制品4. 部署时使用真实 digest5. 同一制品跨环境晋级6. 扫描结果如何进入决策7. 验收与练习

同事问：“线上到底跑的是哪一份代码？”回答 latest 不足以定位问题。同一个标签可以在不同时间指向不同内容，Git Commit 也不能单独证明某次镜像构建用了哪些基础层和依赖。本章建立源码、构建记录、镜像身份和运行版本之间的关联。

前置条件是已能构建本地镜像，并拥有自己的 GitHub 仓库和可用的 GHCR 包发布权限。没有仓库凭据也可以学习概念与完成本地检查；不要用别人的 token 跟做。仓库发布在本阅读版中尚未执行。

1. tag 用于命名，digest 用于固定内容#

OCI 镜像制品包含配置和文件系统层，manifest 描述这些对象；多平台镜像还可能通过 image index 关联不同平台的 manifest。仓库是存储和分发这些内容的服务。

tag 是可读的引用，例如 v0.2、Commit SHA 或 stable。它是否允许覆盖，取决于仓库策略；“看起来像版本号”不意味着自动不可变。digest 是按内容计算的标识，拉取 repository@sha256:... 可以固定所指的 manifest 或 index。

上面的 A/B 是教学符号。真实 digest 应从仓库或推送结果读取，不能把示意字符串当成可拉取地址。固定多平台 index 后，实际运行的平台子镜像仍取决于目标架构，因此发布记录还应包含平台。

2. 建立可追踪的四个字段#

字段 来源 用来回答什么
Commit SHA Git 的确切提交 源码是什么
构建记录 CI 运行页面及日志 谁在什么环境构建、通过什么检查
镜像 digest 推送结果或仓库 分发的制品究竟是哪一个
运行版本 /version 与部署记录 当前实例声称运行哪个版本

/version 是应用提供的声明，不能独立替代运行平台的镜像检查。将两者对照：部署平台使用预期 digest，应用返回预期 Commit，业务检查通过，才形成较完整的证据链。

Commit 标签也不能自动覆盖“工作区带着未提交修改”的问题。人工构建前检查 git status；正式制品从干净的受控 CI 工作区创建。

3. 用配套流水线发布候选制品#

把 ticketdesk/ 的内容放在独立仓库根目录，确认 .github/workflows/release.yml 存在，默认分支为 main。在 Actions 中手动运行候选发布工作流。

工作流会执行接口测试、构建候选镜像、启动数据库与迁移、运行同一候选的业务检查，成功后推送 GHCR。镜像名称使用仓库路径的小写形式，标签使用 Commit SHA。结果摘要应包含实际的 digest 和源码 Commit。

如果 Actions 或组织策略不允许包写入，发布会失败。检查失败步骤、仓库权限和包关联，不能把全仓库或组织管理员权限当成默认修复。参阅 GitHub 发布容器镜像。

本地拉取私有镜像需要另行完成自己的认证。用密码标准输入等受支持方式传递凭据，退出共享环境前移除不再需要的登录状态；不要把凭据写进教程命令、Git 或截图。

4. 部署时使用真实 digest#

以下第一行的值需要从本人的流水线摘要复制，尖括号是说明文字，替换后再执行：

CANDIDATE_IMAGE='<复制真实的 ghcr.io/所有者/仓库@sha256:...>'
docker pull "$CANDIDATE_IMAGE"
python3 scripts/lab.py up --image "$CANDIDATE_IMAGE"
curl --fail-with-body http://127.0.0.1:8000/version

首次启动用 up --image，它会准备数据库并迁移；数据库已准备好后的应用替换可用 deploy --image。后者不会自动执行新迁移，需要按第 19 章的计划单独处理。

用 Docker pull 文档 核对 digest 拉取行为。不要把 docker image inspect 的本地 .Id、某个平台 manifest digest 和仓库 index digest不加区分地写进同一字段。

5. 同一制品跨环境晋级#

测试通过候选 digest A 后，预发布和生产应该引用 A，并注入各自的运行配置。如果每个环境重新构建，即使源码相同，也可能因为基础镜像、依赖解析或构建参数不同得到新内容；之前的验证不再完整覆盖这个新制品。

把环境差异放到部署配置中，同时记录配置修订。秘密值不写入发布单，只记录秘密项名称及受控版本标识。若前端构建必须嵌入环境相关地址，应先承认它会产生不同制品，再设计对应验证，不能口头宣称“只构建一次”。

6. 扫描结果如何进入决策#

扫描用于发现已知风险，不等于证明镜像安全。至少记录扫描器版本、漏洞库更新时间、目标 digest、受影响组件、可用修复和处理决定。新漏洞可能在镜像发布后才公开，需要周期性重新评估。

本阶段提供检查清单，没有集成或声称运行过漏洞扫描器。后续软件供应链卷再接入实际扫描、SBOM、签名与来源证明，并验证阻断策略。这里先避免两个坏习惯：仅凭漏洞数量比较镜像，以及把没有发现问题写成“没有安全风险”。

7. 验收与练习#

完成一份发布记录，包含真实 Commit、构建链接、digest、平台和 /version 响应。另选一个自己的实验标签，记录它指向的内容，在推送新内容后再次观察；确认已固定的旧 digest 仍指向原对象。仅在自己的练习仓库做标签覆盖，不动正在使用的发布标签。

思考：删除旧镜像制品后，发布单中仍保留 digest，是否一定还能回退？答案取决于制品是否仍可获取、运行平台是否有缓存，以及依赖和数据库是否兼容。制品保留策略也是恢复能力的一部分。
