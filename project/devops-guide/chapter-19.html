CHAPTER 19 · 第 5 篇v0.3 阅读版

数据库变更与回滚边界

学习目标加字段后让新旧应用短时共存；制造迁移失败；选择安全的恢复动作，说明哪些数据变化不能自动撤销
本页目录1. 迁移是有顺序的状态变化2. 为什么增加字段也要考虑兼容3. 做一个可控的迁移失败实验4. 三种恢复动作分别回答什么5. 备份必须通过恢复验证6. 本章验收

应用镜像通常可以换回旧版本，数据库却持续接收用户写入。把程序回退到昨天，不会让今天创建的工单自动回到昨天的状态。发布涉及 schema 或数据变化时，恢复计划必须同时考虑新旧程序和已有数据。

本章只在本地实验数据库执行。项目已包含建表和增加优先级两次迁移；下载后首次运行会应用它们。因此“增加 priority”用于分析现有设计，不应再次创建同名列或声称刚完成了一次从旧系统升级的实验。

1. 迁移是有顺序的状态变化#

app/migrate.py 读取排序后的 SQL 文件，在 schema_migrations 中记录文件名与校验和。已经应用的文件内容变化时，脚本拒绝继续；修复通过新增迁移表达，而不是偷偷改写历史。

项目在事务中取得 PostgreSQL advisory lock，避免这个迁移入口并发执行同一批迁移。锁有超时，SQL 也有执行时间限制。它保护的是遵循相同约定的迁移任务，不会阻止所有其他客户端进行任意数据库操作。

docker compose exec -T db psql -U ticketdesk -d ticketdesk -c 'SELECT name FROM schema_migrations ORDER BY name;'
docker compose run --rm --no-deps migrate

第二次执行应识别已应用文件，不重复建表。记录实际退出码和迁移表。幂等的迁移入口仍不意味着任何 SQL 都天然可以重复执行。

2. 为什么增加字段也要考虑兼容#

本例新增 priority，提供默认值 normal，并约束允许的取值。旧客户端不发送该字段时，当前 API 仍能创建工单；接口测试已经覆盖这一点。

这只验证“旧请求形状与新 API”的兼容，不等于已经验证“旧应用二进制与新数据库”的兼容。后者需要真正保留一个旧应用快照，在新 schema 上运行并检查读写。本阅读版没有提供独立旧版快照，不把这个场景标为已通过。

常见的 expand/contract 思路是先增加可兼容的结构，让新旧版本都能工作，再逐步迁移数据和读写路径，确认旧版本不再依赖旧结构后，最后删除旧字段或旧行为。收缩步骤通常会改变回退边界，应单独安排。

直接把正在被使用的列重命名或删除，可能在新旧实例短暂共存时使旧程序立即失败。默认值、约束验证、索引构建和大表更新也有锁与执行时间成本，不能只在空表上试过就推断线上影响。

参考：PostgreSQL 修改表结构。

3. 做一个可控的迁移失败实验#

先完成备份，确认只有本地实验数据。在练习分支新建 migrations/003-demo-failure.sql：

CREATE TABLE migration_failure_probe (id integer);
SELECT 1 / 0;

这个例子故意在事务中失败，用来观察前面的建表是否一并撤销。构建独立候选，避免覆盖正在运行的应用标签：

APP_IMAGE=ticketdesk:migration-failure docker compose build app
APP_IMAGE=ticketdesk:migration-failure docker compose run --rm --no-deps migrate

预期迁移命令非零退出。确认临时表和迁移记录都没有留下：

docker compose exec -T db psql -U ticketdesk -d ticketdesk -c "SELECT to_regclass('public.migration_failure_probe');"
docker compose exec -T db psql -U ticketdesk -d ticketdesk -c 'SELECT name FROM schema_migrations ORDER BY name;'
python3 scripts/lab.py check --ticket-id 1

把 1 换成自己的旧工单 ID。实验后删除尚未应用的 003-demo-failure.sql，保留失败日志，不将这个故意失败的文件合并到主分支。没有执行过或执行结果不同，就如实记录；不要预填“回滚成功”。

4. 三种恢复动作分别回答什么#

动作 修改对象 适用例子 必须先确认
应用回退 运行镜像 新版代码错误 旧版兼容当前 schema 与数据
配置回退或修复 环境配置 数据库主机名写错 目标配置正确，秘密版本仍有效
数据库恢复 持久数据 数据损坏或误删除 可用恢复点、可接受数据损失、切换方案

本项目 lab.py recover 重新部署最后通过业务验证的镜像，并修复实验数据库主机名。它不执行逆向 SQL，不恢复备份，也不撤销已经成功写入的工单。

备份恢复可能丢失备份时间之后的写入。RPO 描述可接受的数据损失范围，RTO 描述恢复时间目标；它们需要业务约定与演练测量，不能由脚本名字自动保证。

5. 备份必须通过恢复验证#

在应用无其他写入的实验窗口运行：

python3 scripts/lab.py backup
python3 scripts/verify-backup.py

备份使用 PostgreSQL 自定义格式逻辑转储。验证脚本把最新备份恢复到一个新建的临时数据库，对比工单行的完整业务内容，最后删除这个临时数据库。它不会覆盖原库。

比较要求源库从备份起不再发生业务写入，否则备份和当前源库不同可能是正常的时间差。执行验证前不要再运行会创建工单的 lab.py check；也不要打开页面继续提交数据。

手动练习可以把具体备份路径交给 lab.py restore --file。该命令恢复到新的数据库，保留供检查，只输出行数并提示继续核对。行数相同不是字段正确的充分证据；需要检查指定工单、状态、标题、时间等。

这个练习不覆盖角色、完整权限、外部对象、超大数据库性能或持续归档恢复。生产恢复方案将在后续可靠性卷扩展。参考：PostgreSQL 逻辑备份。

6. 本章验收#

提交迁移清单、失败事务证据、旧请求兼容的测试结果、备份文件记录与实际恢复对比。明确标注尚未执行的旧二进制共存、锁竞争、大表和真实恢复时间测试。

最后写一个判断题的解释：新应用成功写入一种旧程序无法理解的状态后，仅换回旧镜像是否足够？答案取决于数据兼容性；即使表结构没变，业务语义也可能已经越过安全回退边界。
