测试策略与质量门禁

学习目标为业务风险选择测试层次；加入一个会失败的测试再修复；数据库集成测试可独立重复运行
本页目录1. 为每个风险选择合适的测试2. 阅读一个真正有含义的断言3. Fixture 让前置条件可重复4. 本项目的反向与兼容测试5. 故意破坏一个行为，再修复6. 数据库集成与发布冒烟7. 覆盖率与不稳定测试8. 本章验收

测试的价值来自它能够发现哪些错误。一个百分比或绿色图标，不能告诉你数据库 SQL 是否正确、代理配置是否正确，或用户能否真正创建工单。本章从风险出发选择测试层次。

配套项目已经提供 API 合约测试，可以先运行，再阅读它们为什么这样设计。

1. 为每个风险选择合适的测试#

测试层次 适合发现什么 在 TicketDesk 中的例子
单元测试 小范围规则和边界条件 标题规范化、状态校验
API 合约测试 请求、响应、状态码与接口兼容 无优先级字段的旧请求仍成功
数据库集成测试 SQL、schema、事务与真实依赖 迁移后创建和查询数据
端到端测试 多个组件组合后的用户路径 页面填写后能看到保存结果
冒烟测试 发布后关键能力是否基本可用 版本、就绪、创建、查询、更新

同一种业务行为可以在不同层次验证，但不必在所有层次重复相同细节。便宜且精确的测试放在靠前位置，昂贵的全链路测试覆盖最重要的路径。

2. 阅读一个真正有含义的断言#

def test_create_read_update(client):
    response = client.post('/tickets', json={
        'title': '验证发布过程',
        'priority': 'high',
    })
    assert response.status_code == 201
    ticket_id = response.json()['id']
    assert client.get(f'/tickets/{ticket_id}').json()['title'] == '验证发布过程'
    assert client.patch(
        f'/tickets/{ticket_id}', json={'status': 'done'}
    ).json()['status'] == 'done'

这里不仅检查“接口返回 200”，还检查创建使用 201、结果能被查询、业务字段与更新结果正确。它描述外部行为，便于在内部实现改变后继续验证。

实际测试还应按风险划分案例，避免一个超长测试失败后难以定位。完整文件见配套 tests/test_api.py；测试客户端的使用方法参考 FastAPI 测试文档。

3. Fixture 让前置条件可重复#

测试需要确定的数据起点。配套 fixture 为每次测试创建新的内存仓储，结束后移除依赖覆盖，防止前一个测试的数据影响后一个。

这种替身使接口测试更快、更容易定位失败。但它不会执行 app/store.py 中的 SQL，因此无法发现错误表名、迁移缺失或真实数据库约束差异。

Fixture 的生命周期与隔离方式可以查阅 pytest 官方说明。选择更大的共享作用域之前，要先考虑状态是否会泄漏，以及并行测试是否冲突。

4. 本项目的反向与兼容测试#

目前测试覆盖：过短标题、过长标题、纯空白标题、非法优先级、不存在的工单、非法状态、旧请求缺省值，以及请求 ID 与指标标签。另有存活不依赖数据库、缺少数据库配置时就绪失败的案例。

这些测试来自明确风险，而非为了增加数量。指标标签测试会检查 /tickets/987654 被归一为 /tickets/{ticket_id}，避免每个 ID 产生一个新标签序列。它既测试功能，也保护运行成本。

.venv/bin/python -m pytest -q
.venv/bin/python -m pytest -q tests/test_api.py -k invalid

第二条命令选择匹配名称的案例，便于定位。完整检查仍应覆盖约定集合，不把单个测试成功当成全部通过。

5. 故意破坏一个行为，再修复#

在专用功能分支把默认优先级从 normal 改成 high，运行测试。旧请求兼容测试应失败。阅读断言的期望值和实际值，再根据需求判断是实现错误还是需求发生了正式变化。

如果需求没有变化，就修复实现；如果需求确实变更，应同时更新验收、文档、兼容策略和测试。不能把断言改到“刚好通过”当成解决问题。

这个练习证明测试能够抓到你关心的回归。只有从未失败过的绿色测试，还不足以说明门禁真的有效。

6. 数据库集成与发布冒烟#

真实集成路线使用 Compose 启动 PostgreSQL、应用迁移、运行服务，然后调用 lab.py check。它会通过 HTTP 创建、查询和修改数据。备份验证还会恢复到新的数据库并比较工单内容。

应明确测试数据的生命周期。API 冒烟会写入记录，生产场景需要专门账号、隔离对象和清理策略；这里限定为本地虚构数据。数据库恢复比较需要暂停写入，或以备份时间点的固定基准为准。

当前作者环境已执行的是内存仓储接口测试，实际容器集成状态列在“版本与验证”页。读者需要运行集成流程来取得自己环境中的证据。

7. 覆盖率与不稳定测试#

代码行执行过，不代表断言检查了正确结果。高覆盖率可能遗漏重要业务组合；较低覆盖率也不代表核心路径完全没有保障。覆盖率适合帮助找未触达区域，不能替代风险分析。

不稳定测试会消耗信任。排查应关注时间、随机数据、共享状态、网络依赖和并发条件。临时隔离需要负责人、原因和恢复期限，不能无限重跑直到偶然成功。

8. 本章验收#

为一个业务变更列出风险与测试对应表；运行正向、反向和兼容测试；故意引入一个错误并观察失败；解释内存替身没有覆盖的数据库行为。

下一章会让同样的检查在 PR 中自动执行，并保留可供评审者查看的结果。
