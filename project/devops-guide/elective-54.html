数据任务与事件驱动系统

学习目标为工单增加一个异步处理任务，证明重试不重复产生业务效果且失败可追踪
本页目录前置与代表任务为什么确认时机重要运行可复现示例从主线接入队列：事务型发件箱重试、死信与回补数据质量与 schema 演进故障验收与成本

为工单增加异步统计后，同一事件可能因消费者崩溃被重复投递。简单地“处理一次就确认”无法保证结果只增加一次。本专题用一个可离线运行的 SQLite 教学消费者演示：事件去重和业务效果放进同一事务。它不需要消息队列服务，也不宣称提供完整队列系统。

前置与代表任务#

先掌握 数据库事务、恢复 和 事件处置。配套代码在 extensions/async_demo.py，测试在 tests/test_async.py。代表任务是消费 ticket.created 事件，把指定分类的统计数量加一。主线 HTTP API 尚未自动发布这些事件；从数据库到消息队列的接入是下面讨论的独立环节。

事件至少包括稳定 event_id、类型、schema 版本、工单 ID 和分类。重试必须复用同一事件 ID。不能每次重试随机生成新 ID，否则消费者无法识别重复。

为什么确认时机重要#

若先确认消息再写业务数据，进程崩溃可能丢失效果。若先写业务数据再确认，确认之前崩溃会导致重投。后者可以配合幂等处理恢复，因此“至少一次投递 + 业务幂等”是需要认真设计的组合。消息系统自己的确认机制不自动覆盖外部数据库事务。

本例在同一个数据库事务内：尝试写入已处理事件表，检查重复 ID 的 payload 摘要，更新分类计数，然后提交。重复事件且内容相同返回 duplicate；同 ID 内容不同拒绝，避免数据生产方复用标识却悄悄改变业务。

运行可复现示例#

在 TicketDesk 项目目录执行：

python3 -m extensions.async_demo
python3 -m pytest -q tests/test_async.py

演示使用内存数据库，处理同一事件两次，输出一次 applied、一次 duplicate，分类计数仍为 1。测试额外在业务写入后、提交前抛出模拟异常；检查事务回滚后重试能正确处理一次。它们不连接主线 PostgreSQL，也不会给真实客户发送消息。

如果把业务效果换成发邮件，SQLite 事务无法撤回已经发出的邮件。需要外部系统支持幂等键，或记录可重试的发送任务并处理不确定状态，不能套用本例就宣称外部副作用严格一次。

从主线接入队列：事务型发件箱#

假设 API 先写工单再发布消息，两步之间崩溃会漏发；若先发消息再提交工单，消费者可能看到不存在的工单。事务型发件箱（outbox）在同一数据库事务写工单与待发送事件，后台分发器读取并投递，再记录状态。

分发器投递成功但还没标记时仍可能重复，因此消费者幂等依然必要。表中应有事件 ID、schema、创建时间、尝试次数、下一次重试时间和状态；清理历史记录前确认去重窗口是否仍覆盖可能重放的事件。多个消费者并发时，要让数据库唯一约束和事务保证一致性，而不是只靠进程内集合。

重试、死信与回补#

情况 处理方式 需要观察
短暂连接失败 有上限的退避与抖动重试 次数、延迟、积压年龄
非法 schema 或缺少字段 拒绝并进入可审查失败记录 原因、来源、修复责任
处理结果不确定 查询幂等状态再决定 是否已有业务效果
历史数据回补 限速、分批、可暂停，复用稳定 ID 新旧业务一致性、队列压力

死信队列不是垃圾桶。应能定位失败原因、修复后有控制地重新投递，并避免一次性倾倒全部历史失败导致生产过载。重放数据也要考虑保留、删除和隐私约束。

数据质量与 schema 演进#

事件传递成功不代表数据正确。校验必要字段、值域、时间范围和关联工单；监控重复率、非法事件率、处理延迟和最终统计差异。生产者添加可选字段通常更容易兼容，重命名或改变字段含义则要版本化并给消费者迁移窗口。

本例只支持 schema 1，遇到其他版本明确失败。它没有自动迁移事件的能力；这是有意保留的契约边界。把未知版本当成已处理，会造成难以发现的数据损失。

故障验收与成本#

验收至少包含重复投递不重复计数、提交前崩溃没有半份效果、同 ID 不同内容被拒绝、未知 schema 被拒绝。真实队列接入后再增加消费者退出、重投、积压和死信恢复实验。你将新增 broker、消费者、调度、保留与值班成本，不能只衡量 API 响应变快。

练习：为什么消费者“写入效果后再写去重表”且不使用同一事务仍会重复？参考 答案。实现依据可查 SQLite 事务，真实消息确认语义另查所选 broker 的官方文档，例如 RabbitMQ confirms。
