CHAPTER 48 · 第 12 篇v0.3 阅读版

综合项目——发布一个变更并处理一次故障

学习目标在约定环境从起始快照完成变更；通过毕业验收；提交完整证据包和一页架构决策说明
本页目录起点、环境与范围需求与验收先写下来从需求走到同一份制品发布与业务验证一次受控故障数据恢复与安全检查证据包与评分依据演示顺序与后续学习

毕业项目不是再安装一套工具，而是证明一个需求能够经过评审、测试、构建、部署、观察、故障处理和恢复，最后留下可复核证据。本章选择 TicketDesk 的“按工单状态过滤”作为独立业务变更。当前基线尚未实现这个过滤功能，避免直接运行现成代码却误以为完成了变更练习。

起点、环境与范围#

起点是本版下载的 TicketDesk，先保存源码提交和下载文件校验值。选择一条完整路径：基础路径使用本地 Compose；进阶路径使用独立 kind 集群与 GitOps 设计。先把基础路径做闭环，再选择集群路径。使用合成工单，暂停并发写入后才能做严格备份对比。

演练不需要真实客户数据，也不需要生产权限。运行端到端步骤需要 Docker；进阶另需 kubectl、Helm 和满足前文要求的集群。书中提供的静态检查结果不能代替你在目标环境中的执行记录。

需求与验收先写下来#

为 GET /tickets 增加可选 status 查询参数。无参数时保持原行为；合法状态使用项目已有状态枚举，过滤结果只包含对应状态；非法值返回明确客户端错误；排序和返回结构保持兼容。不要顺便改变分页、认证或数据模型，以免无法解释失败来自哪里。

先阅读 app/main.py 中当前列表端点与更新状态端点，再为三个条件编写测试：混合状态只返回目标集合、无参数行为不变、非法参数被拒绝。现有单元测试替换了数据库依赖，不能证明 SQL 过滤真的生效，所以还要在真实 PostgreSQL 上建立不同状态数据后验证结果。

从需求走到同一份制品#

  1. 建立分支和验收清单，记录变更理由与不涉及的行为。
  2. 先运行基线测试，再实现失败测试及最小修改。SQL 使用参数绑定，不拼接用户输入。
  3. 提交 PR，说明兼容性、验证结果和回退办法；评审代码、测试与部署影响。
  4. 构建镜像，保存 commit、镜像标识与构建日志。推入受控 registry 时记录 digest。
  5. 预发布与后续环境使用同一 digest。环境配置单独记录，不能换环境后重建“相同版本”。

基础实验可按 配套项目 的 lab.py 路径使用本地镜像引用，但报告必须注明没有完成远程 registry 晋级。已经具备 registry 条件的读者，按 制品章节 验证远程 digest；不要用本地 image ID 冒充仓库 manifest digest。

发布与业务验证#

先在解压的项目目录运行已有基线流程：

python3 scripts/lab.py init
python3 scripts/lab.py up
python3 scripts/lab.py check

这些命令应完成服务启动和创建、读取工单的业务检查。随后按第 17—18 章的发布流程部署自己的候选镜像，再用 HTTP 客户端检查 GET /tickets?status=open 等实际已支持的状态。不要仅检查 /health/live：存活不代表数据库可用，更不能证明过滤条件正确。

保存请求输入、HTTP 状态、去标识化结果和候选版本。检查 /version 的 commit、配置环境与实际部署记录一致。观察错误率和延迟时，明确窗口和样本数；十个成功请求只能证明一次有限的冒烟验证。

一次受控故障#

先确认已保存成功版本，然后用现有脚本注入应用数据库地址错误：

python3 scripts/lab.py fault
python3 scripts/lab.py recover
python3 scripts/lab.py check

不要一口气复制三行后才开始观察。先执行 fault，记录发现时间、业务失败、readiness 状态、日志及影响判断；提出至少两个假设，并写明哪条证据支持数据库连接配置异常。然后才执行 recover，验证旧成功镜像与正确配置被恢复，已有工单仍可读写。

这个故障主要验证配置恢复，不会自动演练所有镜像回退、数据库迁移回退和灾难恢复。若同时改了 schema，必须另外评估旧应用是否兼容。事件记录区分“执行了恢复命令”和“业务确认恢复”的时间。

数据恢复与安全检查#

按 备份章节 创建备份并恢复到新数据库；使用校验脚本比较稳定数据集。保留备份开始结束时刻、记录数、恢复用时与失败原因。只有恢复到新目标并读取业务数据，才构成恢复证据。

安全部分先执行 第 42 章 的模拟门禁和 第 44 章 的工作负载检查，证明负例会失败。具备真实镜像和签名条件后，再追加该 digest 的扫描、SBOM 和身份校验。不能把虚构 digest 的策略 fixture 放进真实发布记录，也不能用“扫描命令可运行”代替“目标制品通过策略”。

证据包与评分依据#

交付物 能回答的问题 不足的证据
需求与 PR 为什么改，边界是什么，谁评审 只有最终截图
测试与数据库验证 正反例、兼容性和真实查询是否满足 只说“测试通过”
发布记录 commit、digest、配置、环境是否关联 可变 tag，没有解析结果
运行与故障时间线 用户影响、诊断、缓解、恢复如何确认 只有一段错误日志
恢复校验 数据完整性和恢复目标是否满足 只存在备份文件
安全与就绪差距 哪些门禁执行，哪些条件未满足 将未执行项写成通过

用 templates/capstone-evidence.md 汇总，并写一页架构决策：为什么选择当前方案、还缺什么、什么时候需要改变。验收允许存在明确的生产差距，但不允许丢失关键数据、无法定位制品、负例门禁无效或把模拟结果冒充真实结果。

演示顺序与后续学习#

建议演示先展示需求和预期，再展示失败测试、变更、候选制品、业务验证和故障恢复，最后解释证据缺口。评审者随机选一个记录追溯到原始输出，检查能否复现。不同机器的时间和标识会变化，因此以判定条件为准，不要求照抄示例输出。

练习：让另一位读者仅凭你的证据包复现，记下他不得不询问的地方；把这些补入说明。参阅 综合项目答案与评分提示。主线到此完成，接下来可按实际需求选择 八个专题，将已经建立的交付原则迁移到其他平台与工作负载。
