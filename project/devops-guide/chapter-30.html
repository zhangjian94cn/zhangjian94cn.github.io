CHAPTER 30 · 第 8 篇v0.3 阅读版

用 Argo CD 实践 GitOps

学习目标环境 PR 合并后部署指定 digest；修改集群产生漂移，观察所配置策略；演示变更撤回后的重新协调
本页目录1. 应用源码与环境期望分别保存什么2. Application 与 AppProject 的职责3. 同步状态和健康状态分别看4. 先手动同步，再有意识地自动化5. 做一次可解释的漂移实验6. 通过版本记录恢复期望状态7. 本章验收

前面由操作者执行 apply，集群中的状态可能逐渐偏离仓库。GitOps 把期望状态保存在可审阅的版本记录中，由协调器持续比较并按配置同步。它增加了反馈与执行机制，也增加了一个必须保护和维护的部署身份。

前置是可以渲染的第 29 章环境配置、一个自己控制的 Git 仓库，以及安装好的 Argo CD。配套 gitops/ 使用不可达的文档示例地址，必须替换成真实仓库再运行；教程没有创建或访问你的环境仓库。

1. 应用源码与环境期望分别保存什么#

应用仓库存源码、测试与构建说明；环境仓库存目标环境选择的镜像 digest、配置与资源声明。两者可以位于不同仓库，也可以按边界组织在同一仓库，关键是变更权限与发布责任明确。

CI 构建并验证候选后，创建环境变更 PR，把预发布引用更新到该候选 digest。环境 PR 合并表达发布决定，Argo CD 再读取仓库并协调集群。仓库变更不应携带数据库密码或私钥。

2. Application 与 AppProject 的职责#

Application 指定仓库、修订、路径和目标集群/命名空间；AppProject 限定允许的来源、目标与资源类型。Argo CD 自己访问集群和仓库的凭据仍需要平台侧管理。

本例 AppProject 只允许一个填写后的环境仓库、ticketdesk-stage 命名空间和 API 所需的四类资源。Namespace、数据库、Secret 与迁移由独立引导流程提供，避免默认获得整个集群的管理范围。

kubectl --context kind-ticketdesk -n argocd apply -f gitops/project.yaml
kubectl --context kind-ticketdesk -n argocd apply -f gitops/application.yaml

执行前先在两个文件中替换同一个真实仓库地址，并确认 path 与仓库结构一致。参考 Argo CD 安装入口 固定部署版本，保存安装清单与权限审阅记录。

3. 同步状态和健康状态分别看#

Synced 主要说明实际资源与期望配置的比较结果；Healthy 根据资源健康规则判断对象状态。二者都不能单独证明业务创建与更新工单正确。

检查至少分为：仓库修订是否正确、目标 digest 是否正确、对象是否同步、资源是否健康、业务检查是否通过。若前四项正常但写入失败，继续查数据库身份、schema 和业务约束，不要让一个绿色状态覆盖用户失败。

4. 先手动同步，再有意识地自动化#

示例默认关闭 automated.enabled、prune 和 selfHeal。先审阅差异并手动同步一次，确认范围正确，再选择自动策略。

选项 控制什么 启用前的问题
automated 是否按策略自动同步 哪类仓库变更已代表部署许可
selfHeal 是否纠正某些集群侧漂移 紧急手工修复怎样暂停与回写
prune 是否删除不再出现在期望中的资源 删除影响、数据与资源所有权是否明确

它们不是同一个开关。自动同步并不自动等于允许删资源；自愈也不等于应用业务自我修复。具体行为以 Argo CD 自动同步文档 为准。

5. 做一次可解释的漂移实验#

在专用 stage 环境中，手工改变 Deployment 副本数，观察差异。关闭 selfHeal 时记录差异如何保留；开启后再试，观察控制器何时恢复声明值。每次只改变一个条件，并确认 HPA 没有同时管理该字段。

实验不是用来证明所有手工操作都应该立刻撤销。真实事故中可以采用先暂停受影响协调、实施受控缓解、验证业务、把认可状态回写 Git、再恢复同步的流程。暂停期间的责任人和结束条件也应记录。

6. 通过版本记录恢复期望状态#

准备一个旧版本与当前 schema 兼容的 digest。对错误的环境变更创建 revert 或新的修正提交，经过相应流程后让协调器应用这个新期望，再验证旧工单与新写入。

直接在集群里换回镜像，而仓库仍要求错误版本，可能被协调器重新覆盖。恢复业务不只是执行 rollout undo，还要让控制源、实际状态和发布记录一致。

数据库迁移不应因为镜像回退而自动逆向执行。若使用同步 hook 或 wave 管理迁移，应明确依赖、重试、失败阻断和 Job 身份；先在独立实验中验证，再接入生产。

7. 本章验收#

提交应用与环境的身份链、AppProject 范围、一次同步和一次漂移实验、一次通过 Git 修正期望状态的恢复记录。私有仓库凭据只提供必要读取范围，部署身份不与日常应用身份共享。

最后解释：仓库暂时不可访问时，已经运行的应用会怎样，新的同步会怎样？把运行数据面与控制面故障分开思考，答案入口见练习与答案。
