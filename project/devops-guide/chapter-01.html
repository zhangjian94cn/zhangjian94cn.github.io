DevOps 如何让需求稳定到达用户

学习目标对照一个“提交后上线失败”的故事画出交付链，找出等待点、信息断点和责任人
本页目录1. 先定义什么叫交付成功2. DevOps 具体改变什么3. 小批量与快速反馈怎样降低不确定性4. DevOps、SRE 与平台工程怎样配合5. 贯穿全书的工单服务6. 实践：画出你自己的交付链7. 常见误区与思考题8. 本章验收

业务同事提出一个很小的要求：“工单增加一个优先级。”开发半天写完，测试等到周五，发布又等运维排期。上线之后旧数据报错，大家开始讨论应该由谁回退。真正困难的部分，发生在代码写完之后。

本章从这次变更出发，认识软件交付的全过程。读完后，你应能画出项目的交付链，指出其中的等待和风险，并为后面的实验选择一条适合自己的学习路径。

1. 先定义什么叫交付成功#

提交进入 Git 仓库，说明代码被记录。测试通过，说明选定的行为在测试条件下成立。容器启动，说明进程开始运行。这些都是证据，但每一个证据覆盖的范围不同。

对工单用户来说，成功意味着：能创建工单、优先级能保存、旧工单仍能打开、响应时间可接受。对维护团队来说，还需要知道运行版本、发现异常、恢复服务以及保护数据的方法。因此，交付目标必须同时描述业务结果和运行条件。

交付环节 团队要回答的问题 留下的证据
需求 谁遇到了什么问题？怎样算解决？ 用户故事、验收条件
变更 改了什么？为什么这样改？ Issue、Commit、PR、评审
验证 哪些行为已确认？哪些风险仍在？ 测试结果、检查报告
构建 交付的文件究竟是哪一份？ 制品、版本、镜像 digest
发布 把什么交给了哪个环境？ 部署记录、配置、审批
运行 用户现在能否完成任务？ 业务请求、日志、指标
改进 为什么出了问题？如何减少再次发生？ 复盘与改进任务

你可以把这张表当成全书的目录地图。工具会变化，这些问题一直存在。

2. DevOps 具体改变什么#

DevOps 关注开发与运行之间的协作和反馈。开发人员需要理解代码上线后的表现，运维人员需要参与可运行性设计，测试和安全人员把专业判断尽早放进流程。团队共同对服务结果负责，同时保留清楚的专业分工。

例如，优先级字段会影响数据库结构。若评审时就请维护人员检查兼容性，可能选择先增加带默认值的列，再上线应用。若直到发布窗口才发现旧应用无法工作，解决成本就会大得多。

常见的 CALMS 框架可以帮助检查团队能力：Culture 是协作文化，Automation 是自动化，Lean 强调减少浪费，Measurement 强调测量，Sharing 强调知识共享。它们需要落实成工作行为：评审可以被复用、失败能够公开讨论、重要步骤能够重复执行、告警有处理人、知识能离开个人电脑。

3. 小批量与快速反馈怎样降低不确定性#

一次变更包含十个互不相关的功能，失败时就有十组可能原因。把它们拆成独立、兼容的小变更，便于审查、验证和恢复。这里的“小”不是机械限制代码行数，而是让一个变更的意图和影响可以被理解。

工单优先级可以分成三次兼容交付：先扩展数据库结构，再加入 API 行为，最后在页面显示。每次都有独立验收，并能在后续步骤暂缓时维持现有能力。相关研究与实践背景可阅读 DORA：小批量工作。

但拆分也有成本。如果两次变更必须同时上线才正确，就不能只凭形式拆开。应先重新设计兼容关系，再决定交付单位。

4. DevOps、SRE 与平台工程怎样配合#

视角 主要关注 在本项目中的体现
DevOps 需求到运行的协作、自动化与反馈 PR 检查、发布记录、运行反馈
SRE 用工程方法管理可靠性 SLO、容量、事件响应、减少重复劳动
平台工程 为内部开发者提供可用的公共能力 服务模板、默认流水线、自服务环境

一个小团队可以由几个人兼任这些职责。团队扩大之后，平台团队可以维护公共能力，但业务团队仍需理解自己服务的运行结果。平台提供按钮并不会自动转移全部责任。

本书先让你经历交付过程，再介绍更复杂的平台与治理。有关 SRE 实践的进一步阅读见 Google SRE Workbook。

5. 贯穿全书的工单服务#

我们使用一个小型工单 API，数据保存在 PostgreSQL。它提供创建、查询和修改状态的功能，另有健康检查、版本、日志和基础指标。配套页面可以操作虚构工单。

这个应用刻意保持业务简单。你不需要先写一个完整前端，也不需要一开始搭建 Kubernetes。第一卷先完成 Git、测试、构建、部署和恢复；后续卷再增加基础设施、集群、观测与治理能力。

配套示例是教学实现，当前没有登录和访问授权，因此只绑定本机地址。后续生产改造需要单独设计身份系统、容量、连接池与运行支持，不能把本地演练直接当成生产服务。

6. 实践：画出你自己的交付链#

选择最近做过的一个变更，记录以下信息：需求进入时间、开始开发时间、评审时间、测试完成时间、发布完成时间和第一次获得用户反馈的时间。如果没有真实项目，就使用“工单增加优先级”的虚拟案例。

把每个步骤分成“实际处理”和“等待”。等待可以来自排期、权限、环境、信息不完整或跨团队交接。选出一个最影响交付的等待点，写出一个可以验证的改进，例如把环境申请表变成带自检的模板，而不是笼统地写“提高效率”。

不要用这个练习给个人排名。等待通常由系统条件共同造成，改进也需要团队共同完成。

7. 常见误区与思考题#

“已经装了 CI 工具，所以实现了 DevOps。” 检查流程是否真的在使用：失败是否有人处理，版本是否可追溯，发布后是否能观察用户结果。工具安装记录不能回答这些问题。

“自动化越多越好。” 自动化会重复你的规则。规则不明确时，脚本也可能更快地重复错误。先解释正确行为，再将可重复部分交给自动化。

思考题：如果 API 测试全绿，但用户创建工单仍失败，可能缺少哪三类验证？把答案与“网络入口、配置差异、数据库迁移、身份权限、真实用户路径”等因素比较，说明每一项应该在哪个环节发现。

8. 本章验收#

  • 能用自己的话说明需求、代码、制品、部署与运行结果之间的关系。
  • 完成一张有责任和证据的交付链表。
  • 找出一个等待点，提出可观察效果的改进。
  • 选择基础主线、运维强化或负责人阅读路径。
