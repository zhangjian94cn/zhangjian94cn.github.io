CHAPTER 04 · 第 1 篇v0.3 阅读版

把需求写成可以验收的小变更

学习目标将“增加工单优先级”拆成可交付任务，写正常、异常与兼容性验收条件
本页目录1. 先理解用户要完成的事2. 写可观察的验收条件3. 功能要求与运行要求一起进入设计4. 任务怎样拆分才有交付价值5. 建立一个有用的 Issue6. 用 ADR 留下重要取舍7. Definition of Done 怎样发挥作用8. 独立练习与验收

“增加优先级”听起来明确，实际包含很多未回答的问题：默认值是什么，旧工单怎么办，谁能够修改，排序是否变化，旧客户端是否还能提交？如果这些问题到发布时才出现，流水线再快也会返工。

本章把一句需求整理成可交付的变更。你不必购买任务管理软件；Markdown、Issue 和 PR 已足以完成练习。

1. 先理解用户要完成的事#

以工单负责人为例，他需要先处理影响更大的问题。因此可以写成：“作为工单负责人，我希望标记工单优先级，以便在处理队列中区分紧急程度。”

这句话建立了角色、动作和价值，但仍不是完整规格。下一步要说明范围。本次只增加字段和展示，不改变排序、不引入通知、不建立审批。限制范围可以让团队先验证字段是否有用，而不是把所有可能的功能一次做完。

配套项目包含已经实现的基础优先级，便于你运行整条主线。本章把该功能当成一个设计案例。独立练习可以选择“按状态过滤列表”，避免把参考实现原样提交当成自己的功能开发。

2. 写可观察的验收条件#

编号 条件 验证方式
优先级取值 只允许低、普通、高三种 接口正向与反向测试
默认行为 未提供字段时使用普通 旧请求格式兼容测试
持久化 创建后重新查询值不变 数据库集成测试
旧数据 原有工单可读取且有合理默认值 迁移前后对照
展示 页面能显示实际优先级 浏览器用户路径
发布 能识别运行版本，失败有恢复方法 发布和恢复演练

“体验良好”“系统稳定”不能独立作为验收条件。应该写清目标用户、操作、结果、环境和观察窗口。性能指标还应说明资源、数据量与工作负载，否则不同结果无法比较。

你可以使用 Given/When/Then 结构，例如：给定一个不带优先级字段的旧客户端请求，当它创建工单时，应成功创建，并返回 normal。这段文字后来可以直接指导测试。

3. 功能要求与运行要求一起进入设计#

功能要求描述系统做什么。运行要求描述它在什么条件下完成，以及出问题时如何处理。对于本次变更，后者包括字段兼容、迁移时长、观测、权限和恢复方式。

不需要给每个小功能写庞大文档。可以用一个简短检查表询问：是否改变数据，是否改变接口，是否增加依赖，是否需要新的权限，是否有不可逆动作，是否需要额外运行信号。任何“是”都应有相应说明。

4. 任务怎样拆分才有交付价值#

按“数据库组做数据库、后端组做后端、前端组做前端”拆分，容易只得到局部完成状态。更有用的切分，是让每一步都保持可运行。

第一步增加兼容列：旧应用继续工作，新列有默认值。第二步让 API 接受并返回优先级：旧请求仍可使用。第三步增加页面输入和展示：页面与 API 保持一致。最后再根据反馈考虑排序。

拆分后要画出依赖。页面依赖 API；API 依赖已存在的数据库字段。发布顺序需要与这个依赖一致，而 Git 合并顺序并不自动保证数据库迁移已经执行。第 19 章会具体演练。

关于小批量的背景与收益，可参考 DORA 的相关能力说明。本项目的拆分方式还取决于当前兼容约束。

5. 建立一个有用的 Issue#

一条完整 Issue 应包含：用户问题、目标、范围、验收条件、已知限制、关联设计和验证方式。任务标题应能独立理解，例如“为工单 API 增加可选优先级字段”，而不是“优化一下”。

需求：旧客户端不改请求格式，也能继续创建工单。
本次范围：新增 priority，默认 normal；不改变列表排序。
验证：缺省值、合法值、非法值、旧数据查询。
数据变化：先增加带默认值的新列。
恢复：应用可回到旧版，新列暂时保留。
完成证据：测试报告、迁移记录、运行版本和业务请求。

模板应帮助思考，而不是要求每条小任务都填满大量无关字段。本书在配套资料中提供 Issue、PR、发布与复盘模板。

6. 用 ADR 留下重要取舍#

架构决策记录（ADR）用来解释“为什么选择这个方案”。它可以只有一页：背景、选项、选择、后果和重新考虑的条件。

本项目的示例决策是：基础阶段先使用 Compose。背景是学习者只有一台电脑，目标是理解交付。收益是减少集群管理前置；代价是不能直接验证多节点故障域和生产高可用。重新考虑的条件是应用数量、部署频率或隔离要求超出单机能力。

不要只写“业内流行”或“性能最好”。可评审的理由必须与约束连接。你将在第 47 章用同样方法比较更完整的部署方案。

7. Definition of Done 怎样发挥作用#

团队可以约定一次功能变更完成时具备：代码经过评审、关键测试通过、配置和迁移已说明、运行版本可识别、文档同步、恢复方法清楚。适用于所有变更的部分形成共同标准，特有条件留在需求中。

“开发完成”“测试完成”“已部署”“用户验收”也应分别记录。一个状态字段可以展示摘要，但底层证据不能混在一起。稍后 CI 会提供自动检查证据，PR 会承载评审，发布记录会承载环境事实。

8. 独立练习与验收#

为“按状态筛选工单列表”写一条 Issue。至少覆盖合法状态、非法状态、空结果、默认查询、与现有接口的兼容，以及分页是否属于本次范围。再写一页 ADR，说明为何第一版是否加入分页。

验收时请一位未参与设计的人阅读。如果他仍需要猜测输入、输出或完成条件，就继续修改。下一篇开始学习系统、网络和脚本，让这些要求逐步变成可运行的实现。
