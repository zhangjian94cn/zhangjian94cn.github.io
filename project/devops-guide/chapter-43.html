CHAPTER 43 · 第 11 篇v0.3 阅读版

SBOM、来源证明与制品签名

学习目标为镜像生成 SBOM 与来源信息；验证签名和预期构建身份；不符合身份或内容校验的制品无法晋级
本页目录1. 三类证据回答不同问题2. 为候选生成组成清单3. 来源证明需要可信构建边界4. 验证签名时同时验证内容与身份5. 正向验证不够，还要故意验证错对象6. 晋级与保留策略7. 验收

镜像 digest 可以固定内容，但不能单独说明谁构建了它、用了哪些输入、包含哪些组件。供应链证据需要分别描述组成、构建过程与签名身份，再在晋级前验证预期属性。

前置是第 16—17 章的可追踪候选与第 41 章身份边界。本章给出接入方法和验证练习；基础发布工作流尚未执行 SBOM、签名或来源证明，不能把示例命令当作已经生成的证明。

1. 三类证据回答不同问题#

证据 回答的问题 不能单独证明什么
SBOM 识别到了哪些软件组成 没有漏洞、运行路径安全
Provenance 制品声称怎样、由谁、从什么输入构建 所有声明都可信、构建环境完全隔离
签名 某个密钥或身份对内容作了认证 签名者本来就应该被信任

证据应绑定实际 digest，并有明确生成者与验证者。把报告放在同一个目录里但没有身份关联，无法阻止报告与镜像被错误配对。

2. 为候选生成组成清单#

在安装并核对 Syft 的自己的环境中，以同一个候选引用生成 SPDX JSON：

syft "$CANDIDATE_IMAGE" -o spdx-json > .lab/sbom.spdx.json

检查文档中的组件、版本、包身份与生成工具信息，记录扫描对象是否包含运行镜像中的所有相关层。不同生成方式可能有不同覆盖范围，不能把“文件扩展名是 JSON”当成有效 SBOM 的证明。工具依据见 Syft 官方项目。

生成器、插件或远程依赖本身也进入供应链，因此需要版本与来源管理。SBOM 应随制品保留，后续发现风险时才能反查受影响版本。

3. 来源证明需要可信构建边界#

有用的 provenance 关联构建身份、源码修订、构建配置、输入材料和输出制品。若不可信步骤可以随意改写报告，报告就不能独立证明这些声明。

构建隔离、身份、不可变输入与证明生成位置共同影响可信度。不能因为生成了一份来源 JSON、SBOM 或签名，就宣称达到某个 SLSA 等级。按 SLSA v1.2 的具体要求逐项核对，并记录未满足项。

4. 验证签名时同时验证内容与身份#

以下示例针对使用 GitHub Actions OIDC 身份完成签名的候选。身份必须替换为自己实际受信任的工作流，不能任意接受签名中出现的身份：

cosign verify \
  --certificate-identity 'https://github.com/OWNER/REPO/.github/workflows/release.yml@refs/heads/main' \
  --certificate-oidc-issuer 'https://token.actions.githubusercontent.com' \
  "$CANDIDATE_IMAGE"

只有目标已通过对应流程签名，这条命令才可能成功；当前随书基础工作流没有这个签名步骤。接入时先在练习仓库配置明确身份与权限，再把验证加入独立晋级门禁。核对 Cosign 官方验证说明。

密钥式签名则需要维护可信公钥与私钥生命周期；无密钥方案仍需要信任根、身份策略与相关基础设施。使用透明日志等服务时，了解会记录哪些身份与制品元数据，再选择适合的发布方式。

5. 正向验证不够，还要故意验证错对象#

准备一个正确签名的练习制品，验证通过；再将预期身份改成另一个不应被信任的身份，预期失败；最后换成另一个没有对应证据的 digest，预期失败。

验证失败必须阻断晋级，不把 || true 放在签名检查后。不要从攻击者提供的证书中直接提取“应该信任的身份”，再用它验证同一证书；预期身份应来自受控策略。

6. 晋级与保留策略#

测试、扫描、SBOM、来源证明和签名都指向同一候选，部署目标也引用同一 digest。通过门禁后再发布环境变更，记录策略版本与验证结果。

删除旧制品或相关证明会影响回退与审计。保留策略需要结合恢复窗口与访问控制，避免为了节省少量存储而失去已知健康版本。同时要能撤销不再受信任的身份并重新评价相关制品。

7. 验收#

提交一份候选证据索引、信任根与预期身份规则、正向与两项反向验证，以及保留和撤销流程。尚未实际签名时，验收状态应为设计与命令准备完成，不能填入虚构签名、digest 或验证输出。
