CHAPTER 15 · 第 4 篇v0.3 阅读版

用 Compose 管理多服务环境

学习目标启动应用、数据库和代理；验证数据库重启后的行为、卷持久性及保留数据的停止流程
本页目录1. 四个服务有不同生命周期2. 服务名比临时地址稳定3. 启动、就绪与恢复是三件事4. 验证卷，而不是相信卷5. 观察数据库短暂不可用6. 可选代理与配置检查7. 本章提交物

TicketDesk 至少需要应用和数据库；学习反向代理时还需要 NGINX。分别手工启动、记住端口、创建网络和挂载数据目录很容易遗漏。Compose 把单机多服务的期望配置写到同一份文件中，让环境的创建和检查有共同入口。

本章承接第 14 章，在本机实验项目中运行。Compose 是本课程的入门部署方式；跨主机调度、高可用数据库和集群升级将在后续卷讨论。

1. 四个服务有不同生命周期#

服务 职责 预期生命周期
db 保存工单数据 持续运行，数据放在命名卷
migrate 执行 schema 迁移 一次任务，成功后退出
app 接收 HTTP 请求 持续运行，依赖可用数据库和正确 schema
proxy 反向代理 选修 profile 启动后持续运行

迁移退出为 0 是任务完成；应用退出则通常意味着服务不可用。同一个“Exited”字样，对不同服务有不同含义。不要给所有任务机械地加无限重启策略，否则一次成功的迁移也可能被反复启动。

项目脚本明确执行：启动并等待数据库、执行迁移、启动应用、验证业务。单独运行 docker compose up app 不会替你执行整个迁移流程，因此首次运行优先用脚本入口。

2. 服务名比临时地址稳定#

应用在 Compose 网络中连接 db:5432。db 是服务名，5432 是容器内数据库端口。本机通过映射端口 55432 访问数据库，二者处于不同网络视角。

python3 scripts/lab.py up
docker compose exec app python -c 'import socket; print(socket.getaddrinfo("db", 5432))'
docker compose ps

不要把容器 IP 抄进配置，也不要让 app 连接 localhost:55432。从 app 容器看，localhost 是自己；本机看到的端口映射不会自动成为容器内部访问其他服务的方式。

请求发起位置 目标 使用地址
本机浏览器 应用 http://127.0.0.1:8000
app 容器 数据库 db:5432
proxy 容器 应用 app:8000
本机数据库客户端 数据库 127.0.0.1:55432

3. 启动、就绪与恢复是三件事#

数据库容器正在运行，可能仍处于初始化阶段。pg_isready 检查数据库是否接受连接，但不证明业务表已经完成迁移。应用的 /health/ready 会尝试访问工单表及所需字段，更接近本项目的服务条件。

Compose 的 depends_on 配合 service_healthy 可以等待依赖满足启动条件。这个声明不能替应用处理运行期间的数据库中断，也不会因为某个健康状态变化就完成业务级恢复。

本例的短连接配有连接超时和查询超时。当数据库重新可用，后续新请求有机会恢复。真实连接池还需处理断链、连接回收和重试边界。创建工单这类写请求也不能无条件自动重试，否则可能创建重复记录。

官方说明：Compose 启动顺序与依赖就绪。

4. 验证卷，而不是相信卷#

先在页面创建一张含有独特标题的工单，记下 ID、标题和状态。下面命令用实际 ID 替换 1：

python3 scripts/lab.py check --ticket-id 1
python3 scripts/lab.py down
docker volume ls
python3 scripts/lab.py up
curl --fail-with-body http://127.0.0.1:8000/tickets/1

down 删除本项目容器和网络，默认保留命名卷。重建后查询同一 ID，并对比业务字段。脚本的 check 每次还会创建一张验收工单，这个写入是有意的；不要用记录总数不变作为它的验收条件。

不要在这个实验中添加 --volumes。只有明确放弃本地实验数据、已完成需要的备份时，才可以删除卷。CI 中的临时数据库每次新建、测试后删除，与需要保留学习数据的本机环境不同。

5. 观察数据库短暂不可用#

只在本地无真实用户的实验环境执行：

docker compose stop db
curl -i http://127.0.0.1:8000/health/live
curl -i http://127.0.0.1:8000/health/ready
docker compose start db
python3 scripts/lab.py check --ticket-id 1

预期存活检查仍返回 200，就绪检查在依赖失败后返回 503。数据库恢复后，业务验证应通过。记录状态变化与耗时；如果失败，先看数据库和 app 日志，确认不是端口、密码、迁移或权限问题。

不要马上删除卷“重来”。那会同时删除分析材料和数据，掩盖真正原因。优先做保留数据的恢复；只有实验计划明确要求重置时才清理持久数据。

6. 可选代理与配置检查#

docker compose --profile proxy up -d proxy
curl --fail-with-body http://127.0.0.1:8080/health/ready
docker compose --profile proxy logs --tail 30 proxy

8000 直连和 8080 代理都能访问，并不代表 TLS、域名或公网防火墙已经配置。本项目监听本机回环地址，适合实验。公开服务还需要身份认证、HTTPS、访问策略和运维责任，不能简单把监听地址改成全网后宣告生产就绪。

docker compose config --quiet 可以做基础配置校验。完整的 docker compose config 可能展开秘密值，不要把输出直接贴入 Issue。检查端口、镜像和挂载时优先只输出所需字段。

7. 本章提交物#

提交服务表、四种网络视角、停止与重建前后工单字段对照，以及数据库中断时 live/ready 的差异。若无法完成，提交失败步骤、退出码、经过脱敏的日志和当前数据是否仍在，而不是填入预期结果。
