CHAPTER 29 · 第 8 篇v0.3 阅读版

用 Kustomize 和 Helm 组织配置

学习目标自有应用形成两个环境；安装一个第三方 Chart；编写小型自有 Chart，与 Kustomize 比较变更可读性
本页目录1. 先找稳定的公共部分2. 渲染两个 Kustomize 环境3. patch 的范围越明确越容易评审4. 阅读最小 Helm Chart5. 安装与升级仍有运行责任6. CRD 与模板验证的边界7. 练习与验收

开发与预发布的 API 大部分配置相同，环境标识、副本数和制品身份又需要不同。如果复制整套 YAML，修复一个探针时容易漏掉另一份；如果把所有差异藏进复杂模板，评审者又看不清最终对象。

本章以“复用后仍然能审阅最终资源”为目标。前置是第 25—28 章，目录分别为 k8s/base、k8s/overlays 与 helm/ticketdesk。Kustomize 与 Helm 展示两种组织方式，不要让它们同时管理同名的实际对象。

1. 先找稳定的公共部分#

公共部分包括端口、探针、运行身份、基本资源要求和服务关系。环境差异包括副本数、环境标识、访问入口和具体制品引用。秘密值以及数据库生命周期不应因为“复用方便”被复制进每份配置。

方法 修改方式 适合观察的取舍
原始 YAML 直接编辑最终对象 最直接，重复较多
Kustomize 对 base 施加 overlay 与 patch 保留资源结构，需理解变换结果
Helm 将 values 输入模板后渲染 适合打包复用，需控制模板复杂度

工具不会替你决定什么属于环境差异。把整份对象嵌进一个 values 字符串，也不会自动得到可维护的配置。

2. 渲染两个 Kustomize 环境#

kubectl kustomize k8s/overlays/dev > /tmp/ticketdesk-dev.yaml
kubectl kustomize k8s/overlays/stage > /tmp/ticketdesk-stage.yaml
diff -u /tmp/ticketdesk-dev.yaml /tmp/ticketdesk-stage.yaml

预期开发环境命名空间为 ticketdesk-dev、一个副本，预发布为 ticketdesk-stage、两个副本；ENVIRONMENT 也对应变化。探针、运行身份和主要 Service 关系应保持一致。

overlay 只包含 API，不创建数据库、Secret 或 Namespace。部署前要在对应命名空间分别准备这些依赖，完成迁移，或接入已准备的独立数据库。两个环境不应该因为连接串相同而共用意外的数据边界。

3. patch 的范围越明确越容易评审#

配套 patch 指定 ConfigMap 名称和具体数据路径，修改环境标识。将来加入 digest 时，可以用 Kustomize 的 images 变换管理引用，评审时检查渲染后的 Deployment 是否确实使用目标制品。

选择器变更、Namespace 变换和名称前后缀有可能影响引用。不要只评审 patch 自身的三行文本；CI 同时保存或展示渲染差异，检查最终 label、selector、端口和 Secret 名称是否仍互相匹配。

4. 阅读最小 Helm Chart#

配套 Chart 包含元数据、默认 values 和 Deployment/Service 模板。数据库与 Secret 仍由独立流程管理。Chart 版本说明模板包变化，appVersion 描述应用版本信息，两者不能替代实际镜像 digest。

helm lint helm/ticketdesk
helm template ticketdesk-demo helm/ticketdesk --namespace ticketdesk-helm > /tmp/ticketdesk-helm.yaml

修改副本数或环境标识后再次渲染，比较最终 YAML。模板对现有 Secret 名称使用 required，缺失时应拒绝渲染；这能发现一部分输入问题，但不知道该 Secret 是否真的存在或密码是否有效。

同一个 Chart 允许提供 tag 或 digest，提供 digest 时优先使用它。生产晋级应输入已验证的真实 digest，不能靠 appVersion 的字符串判断运行内容。

5. 安装与升级仍有运行责任#

在已准备好依赖的独立实验命名空间，可以用 helm upgrade --install 应用 Chart。实际执行前先检查渲染结果、目标 context 和现有资源所有权，避免把 Kustomize 管理的同名对象直接交给 Helm。

Helm 的等待、超时与恢复选项影响发布过程，但并不保证数据库和业务语义一起回退。配套 Chart 没有自动迁移 hook，目的是保持数据发布顺序显式可见。

第 26 章安装的 Envoy Gateway 是第三方 Chart 例子：锁定版本，理解 CRD 与控制器升级责任，阅读默认暴露方式与资源需求。不能因为来自 Chart 仓库，就默认它符合当前集群的安全和兼容要求。

6. CRD 与模板验证的边界#

helm template 能检查模板展开，却可能无法发现目标 API 不存在。CRD 定义自定义对象的 schema，控制器实现行为；两者版本需要匹配。模板里出现某个 kind，并不意味着目标集群已经安装对应能力。

在真实目标执行 server-side dry-run 可以补充 API 与 admission 检查，但它仍不是业务测试。对于有状态变更，最终还需要运行、观察和恢复验证。

7. 练习与验收#

用两种方式把开发副本改成 2，并改变 ENVIRONMENT，要求渲染后的差异只出现在预期字段。再故意遗漏 existingSecret，记录 Helm 的失败。提交原始配置、渲染结果、环境差异和选择理由。

本例不追求给出唯一工具答案。自有小应用用清晰的 overlay 往往足够；第三方复杂软件通常已有 Chart。以变更可读性、接口稳定性和维护责任选择，参考 Helm 模板入门。
