CHAPTER 12 · 第 3 篇v0.3 阅读版

第一条 CI 流水线

学习目标PR 自动运行检查；错误提交失败，修复后通过；不可信 PR 得不到发布凭据
本页目录1. CI、持续交付与持续部署2. 先看几个基本对象3. 将项目放在正确的仓库位置4. 最小检查由哪些步骤组成5. 运行一次失败的 PR6. 为什么不把发布凭据交给 PR7. 托管 Runner 看不到你的 localhost8. 看懂失败与清理

当检查只依赖作者在提交前手动运行，团队就难以知道每次变更是否经过相同验证。持续集成（CI）把共同检查放进自动流程，让合并决策有一致的反馈。

本章先看 PR 检查的核心结构。配套完整 ci.yml 还预置了后续容器与备份实验，你可以先理解 Python 检查，再在第 17 章解释整条执行链。

1. CI、持续交付与持续部署#

CI 关注频繁集成代码，并自动验证变更。持续交付让经过验证的变更保持可发布状态，是否进入特定环境可以保留决策点。持续部署则在符合策略时自动进入目标运行环境。

因此，仓库有 CI 不表示每次 push 都应该直接上线。测试、制品、环境、身份和发布策略需要逐步连接。

2. 先看几个基本对象#

对象 含义 本项目中的例子
Workflow 一组由事件触发的流程定义 TicketDesk checks
Event 流程为什么开始 pull_request、push、手动触发
Job 在一个执行环境中完成的一组步骤 安装、测试、集成验证
Step 一个命令或可复用动作 安装依赖、运行 pytest
Runner 实际执行 Job 的机器或环境 托管 Ubuntu Runner
Result 自动流程留下的反馈 退出状态、日志、报告

准确语法与字段限制以 GitHub Actions 工作流语法为准。不要把 YAML 的缩进规则与流水线业务依赖混为一谈。

3. 将项目放在正确的仓库位置#

将下载的 ticketdesk 目录作为一个独立仓库根目录。GitHub 只会从该仓库根目录的 .github/workflows/ 识别工作流。把它留在另一个仓库的 examples/ticketdesk/.github/，不会自动成为根仓库工作流。

创建自己的远端仓库后推送代码。主分支若不是 main，需要同步调整工作流的分支条件。涉及发布权限的调整应有明确记录。

4. 最小检查由哪些步骤组成#

permissions:
  contents: read

jobs:
  verify:
    runs-on: ubuntu-24.04
    timeout-minutes: 15
    steps:
      - uses: actions/checkout@d23441a48e516b6c34aea4fa41551a30e30af803
        with:
          persist-credentials: false
      - uses: actions/setup-python@ece7cb06caefa5fff74198d8649806c4678c61a1
        with:
          python-version: '3.12'
      - run: python -m pip install -r requirements-dev.txt
      - run: python -m pytest -q

这是完整文件中的核心片段，需要结合文件顶部触发条件使用。第三方动作固定到已核对的完整提交 SHA；旁边的版本注释用于人阅读，执行身份由 SHA 决定。更新动作时要重新核对来源和行为。

使用只读仓库权限，checkout 后不保留多余凭据。与工作流信任和权限相关的约束见 GitHub Actions 安全参考。

5. 运行一次失败的 PR#

沿用第 11 章的练习：把默认优先级改成不符合验收的值，提交到 feature/change-default-priority 并创建 PR。检查应返回失败，日志指出相应断言。

修复后再提交，观察新的运行记录。旧失败记录仍有价值，它证明检查确实执行过，也帮助评审者理解修复过程。

随后在仓库支持的保护规则中，要求该检查通过才能合并。配置后用失败 PR 验证实际效果。仅有红色图标并不必然代表平台禁止合并，管理权限或保护规则可能改变行为。

6. 为什么不把发布凭据交给 PR#

PR 可以修改测试、脚本和工作流。来自不可信来源的代码一旦执行，就可能尝试读取环境或访问网络。因此检查环境和发布身份应该分离，不把运行任意 PR 的 Runner 同时当成生产部署机。

本项目 CI 没有生产秘密。独立发布工作流只允许手动从 main 发起，具有有限的镜像包写入权限；它仍需要代码评审和仓库设置配合。后续第 17 章将解释制品链路。

7. 托管 Runner 看不到你的 localhost#

云端 Runner 的 127.0.0.1 指向它自己。它无法因为你的电脑运行着 8000 端口，就自动访问那个服务。本书在 Runner 内创建临时实验环境，测试后清理。

如果将来部署到远程服务器，要另外建立网络连通方式和部署身份。不要在不了解权限边界的情况下，把可执行外部 PR 的自托管 Runner 直接装到业务主机。

8. 看懂失败与清理#

安装失败、测试失败、环境启动失败和冒烟失败，应分别保留日志。后续清理步骤使用 if: always()，是为了在前面失败时仍回收临时资源；业务验证步骤不能用这种方式绕过依赖关系。

完整工作流的容器部分需要 Docker 与镜像访问。作者环境尚未执行该托管流程，因此首次在自己的仓库运行时，应把实际 Runner、版本、结果与故障记录到实验报告。

本章验收是：正常 PR 成功，错误 PR 失败，日志能解释失败，必要的合并限制经过实际验证，检查过程没有获得不需要的发布权限。
