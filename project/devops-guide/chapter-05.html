文件、用户、权限与远程访问

学习目标使用受限用户管理应用文件；定位“文件存在但无法读取”，解释修复理由
本页目录1. 路径不只是文件名2. 读懂用户、组与权限位3. 一个可以恢复的权限实验4. 应用应该以谁的身份运行5. 标准输入输出让工具可以组合6. SSH 同时涉及两种身份验证7. 排障顺序与验收

应用报“Permission denied”时，直接使用 root 或把权限改成 777，可能让眼前的错误消失，却使你失去对访问边界的理解。本章从一个受限文件实验开始，建立排查文件权限和远程身份的方法。

实验在自己的项目目录进行。涉及系统用户、SSH 服务配置的操作，只在专用实验 VM 上执行，并保留当前可用连接。

1. 路径不只是文件名#

绝对路径从根目录开始，相对路径从当前工作目录开始。程序找不到配置时，先确认它实际在哪个目录运行。例如 systemd 的工作目录不一定等于你登录终端时的目录，容器内的 /app 也不是宿主机同名位置。

pwd
ls -la
ls -ld app scripts
stat compose.yaml

ls -ld 查看目录本身，ls -l 通常列出目录内容。stat 可以查看类型、权限、所有者和时间。排障时先观察，再修改，避免把文件不存在与没有权限混成一个问题。

2. 读懂用户、组与权限位#

文件的读、写、执行权限分别使用 r、w、x 表示。它们对目录的意义不同：目录的读权限允许列举名字，执行权限允许穿过目录查找已知路径，写权限与目录项的增加或删除有关。

对象 读 写 执行
普通文件 读取内容 修改内容 尝试作为程序执行
目录 列举目录项 改变目录项，通常还需配合执行权限 遍历路径与访问其中已知对象

因此，文件本身可读，不代表整条路径都可访问。一个父目录缺少执行权限，就可能阻止应用打开文件。ACL、挂载属性和额外安全机制还可能增加约束，不能只看最后三个数字。

id
ls -ld . app
namei -l app/main.py

namei 在部分系统中需要另外安装。没有它时，逐层检查目录，也能应用相同思路。

3. 一个可以恢复的权限实验#

在 ticketdesk 根目录执行：

mkdir -p .lab/permissions
printf 'demo=true\n' > .lab/permissions/config.txt
chmod 600 .lab/permissions/config.txt
ls -l .lab/permissions/config.txt

600 表示所有者可以读写，组和其他用户没有这些权限。然后去掉所有者读权限，再尝试读取：

chmod 200 .lab/permissions/config.txt
cat .lab/permissions/config.txt
chmod 600 .lab/permissions/config.txt

应使用普通用户实验。root 或具有额外能力的进程可能绕过某些检查，因此不能用 root 的成功读取证明普通服务账号也能读取。

这个实验只改变明确命名的演示文件。不要把同样命令扩展到整个系统目录，更不要为了方便递归修改项目外的权限。

4. 应用应该以谁的身份运行#

业务服务通常只需要读取代码和配置、连接数据库、写少量运行数据。把安装、部署、运行身份分开，有助于限制一次应用错误的影响。

例如代码由部署身份写入，应用身份只读；密钥只允许必要主体读取；日志写到标准输出，由运行环境收集。容器示例使用非 root 用户，systemd 示例则使用专门的 ticketdesk 用户。

权限设计也会影响更新。应用自己可以覆盖业务代码，看起来方便，但难以证明运行内容等于经过评审的制品。后面会通过不可变镜像和显式配置减少这种差异。

5. 标准输入输出让工具可以组合#

程序通常把正常结果写到标准输出，把诊断信息写到标准错误，再用退出状态表示成功或失败。它们是三个不同通道。

python3 scripts/lab.py doctor > .lab/doctor.json

这会保存标准输出，不能因为文件存在就断定检查成功；仍需查看退出状态和 JSON 内容。若你把标准错误也合并进去，就可能得到不能再解析的 JSON。

本书的业务日志采用结构化 JSON，便于按请求 ID 和状态筛选。对结构化数据优先使用 JSON 解析器；不要依靠随意切分空格来提取所有字段。

6. SSH 同时涉及两种身份验证#

远程连接要解决两件事：客户端确认连接的是目标主机；服务器确认登录者拥有对应凭据。SSH 主机指纹帮助解决第一件事，用户密钥或其他认证方式解决第二件事。

首次连接时，应通过可信渠道核对主机指纹。主机指纹突然变化可能是重装，也可能是连接到了不同机器，应该先核实原因。不要把删除 known_hosts 条目或关闭校验作为默认修复。

用户私钥留在本机并受权限保护，公钥放到目标账号授权位置。更换登录方式时先开一个新连接验证成功，再关闭旧连接，以免把自己锁在外面。使用组织批准的短期凭据或集中身份方式时，遵循实际平台的流程。

学习 Git 与 SSH 的连接方式时，可结合 Pro Git 的远程仓库章节阅读；协议、账号与仓库权限应分别理解。

7. 排障顺序与验收#

遇到权限问题时，依次记录：操作的真实路径、执行进程的 UID/GID、路径每一层的权限、目标文件所有者、挂载和额外安全约束。修复后用实际运行身份重试，而不只用管理员账号确认。

练习：解释为什么“文件 644，父目录 700”可能阻止另一个账号读取；再解释为什么应用不能读取配置时，不应首先尝试 777。

本章交付物是一份权限诊断记录，包含修改前状态、原因、最小修改和恢复后的验证。下一章将把程序放进服务管理器，观察身份与工作目录如何影响运行。
