CHAPTER 33 · 第 9 篇v0.3 阅读版

从用户问题选择运行信号

学习目标为工单创建失败设计观测问题清单；统一日志字段；避免把工单 ID 直接变成高基数指标标签
本页目录1. 先把一句抱怨拆成可查问题2. 日志、指标与追踪互相补充3. RED 与 USE 提供观察起点4. 字段与标签要有一致语义5. 用一条真实请求串联证据6. 数据治理是设计的一部分7. 练习与验收

“Pod 都是绿色，为什么用户仍然创建不了工单？”这说明平台对象状态没有覆盖完整用户旅程。观测的起点应是你想回答的问题，再选择日志、指标和追踪，而不是先安装所有面板。

本章可沿用 Compose，也可在已验证的集群中实践。输入是同一应用的版本、请求与运行记录，输出是一份能指导埋点和排障的观测设计。

1. 先把一句抱怨拆成可查问题#

以“创建工单变慢”为例：什么时候开始，影响所有用户还是某个入口，失败还是成功但慢，是否与某次发布相关，应用等待数据库还是消耗 CPU，结果是否最终写入？

问题 优先信号 需要的上下文
影响多大 请求量、错误、延迟指标 环境、服务、路由、时间范围
某次请求发生了什么 日志与追踪 request ID、trace ID、版本
哪个依赖消耗时间 span 与依赖指标 调用关系、状态、耗时
系统是否饱和 资源与队列指标 节点、进程、容量限制
是否与变更有关 发布记录 Commit、digest、配置修订

“多收一点以后也许有用”会带来成本、敏感信息与检索负担。每个新增字段都应能对应某个真实诊断问题。

2. 日志、指标与追踪互相补充#

日志记录离散事件，适合描述发生过什么；指标把状态和事件聚合成时间序列，适合快速发现范围与趋势；追踪描述一次请求跨组件的执行关系，适合定位关键等待。

监控常围绕已知问题设置检查，良好的可观测性则帮助从现有信号解释事先没有完全列出的故障。两者并非互斥，也没有“装了某个产品就自动获得可观测性”的开关。

3. RED 与 USE 提供观察起点#

面向请求服务，可以观察请求速率、错误与耗时，即 RED。面向资源，可以观察利用率、饱和与错误，即 USE。它们是帮助组织问题的方法，不代替对应用的理解。

CPU 利用率高但用户延迟稳定，与 CPU 利用率低却大量请求等待数据库，代表不同问题。队列长度、连接等待与内存压力可能比平均 CPU 更接近真实瓶颈。

为 TicketDesk 先选创建工单路径，再关联数据库连接、查询时间、应用资源与发布记录。不要从一开始就做一个包含上百条不知用途曲线的首页。

4. 字段与标签要有一致语义#

应用日志已经包含 UTC 时间、request ID、HTTP 方法、归一化路由、状态码与耗时。v0.3 在可选追踪启用且上下文有效时，增加 trace ID 和 span ID。版本与环境通过运行信息及采集上下文关联。

不要把完整 URL、工单 ID、用户邮箱或 request ID 直接放进指标标签。每一种标签组合都可能产生新的时间序列，高基数会增加存储和查询负担。需要精确定位单次事件时，把标识放在受控日志或追踪中。

同名字段也应单位一致，例如耗时明确为毫秒或秒；状态值明确来自应用、代理还是客户端。否则多个来源拼到一起，可能形成看似合理却含义错误的图。

5. 用一条真实请求串联证据#

curl -i -H 'X-Request-ID: observe-33' http://127.0.0.1:8000/tickets/1
docker compose logs --tail 100 app
curl --fail-with-body http://127.0.0.1:8000/metrics

替换工单 ID，记录请求时间与版本。在日志中找到对应 request ID，确认路由被归一成 /tickets/{ticket_id}；再查看指标是否增加于相应方法、路由与状态组合。

单进程教学指标在重启后清零，不能直接把累计值当成全生命周期业务总数。采集系统、速率函数、进程身份与保留策略需要共同解释这些变化。

6. 数据治理是设计的一部分#

默认不采集请求正文、密码、Authorization、Cookie 和真实用户数据。确需采集某类字段时，明确用途、范围、脱敏、访问者、保留和删除机制；采集端与处理端都应有相应约束。

采样会影响你能看到哪些请求。没有发现某条 trace，不一定意味着请求没发生；日志时钟不一致也可能制造错误的时间顺序。观测报告应保留采样、时钟与缺失数据的限制。

7. 练习与验收#

为“创建失败”“列表变慢”“新版本无流量”各写三条可验证的问题，给每条问题分配信号、字段与入口。检查现有项目是否真的提供这些数据，缺失项形成改进任务。

本章交付物是一份观测问题与信号映射、字段字典和一条请求证据链。下一章把指标送入 Prometheus，再用 Grafana 对比请求量、错误与延迟。
