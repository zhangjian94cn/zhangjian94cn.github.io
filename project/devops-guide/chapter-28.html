资源、权限和网络边界

学习目标拒绝越权访问；用正反例验证网络策略；通过负载解释伸缩和资源限制；记录依赖插件
本页目录1. requests 与 limits 表达不同责任2. HPA 依赖指标和容量3. 运行身份不应自动获得集群管理能力4. Pod 安全约束降低进程权限5. NetworkPolicy 需要真正执行它的网络实现6. 用正反例确认边界7. 验收与清理

多个团队共享集群后，一个程序无限消耗内存、一个身份能读取全部 Secret、一个命名空间能随意连接数据库，都可能扩大故障影响。资源、API 授权和网络访问需要分别约束，不能依靠一个 Namespace 解决所有隔离问题。

本章承接前述 kind 实验。HPA、NetworkPolicy 与权限检查各有独立前置；默认 base 不自动安装这些可选能力。

1. requests 与 limits 表达不同责任#

调度器根据资源请求和其他约束选择节点；限制用于运行期间的资源控制。CPU 和内存的处理也不同：CPU 可能出现限流，内存超限可能导致容器被终止，需要结合实际事件与指标判断。

本例 API 声明 50m CPU 与 64Mi 内存请求、500m CPU 与 256Mi 内存限制。这些是教学起点，不是从生产压测推导的容量结论。要观察真实工作负载，再决定合适的范围。

kubectl --context kind-ticketdesk -n ticketdesk describe deployment ticketdesk
kubectl --context kind-ticketdesk -n ticketdesk get pods

Pending 时先看调度事件；OOMKilled 时看退出原因和内存行为；延迟变大而 CPU 使用受限时再调查 CPU throttling。只看平均 CPU 低，可能遗漏内存、连接或下游瓶颈。

2. HPA 依赖指标和容量#

配套 k8s/hpa.yaml 以 CPU 利用率为示例，需要 Metrics API 可用，也依赖容器声明 CPU requests。没有指标时出现未知值，并不是“流量太少所以一切正常”。

kubectl --context kind-ticketdesk top pods -n ticketdesk
kubectl --context kind-ticketdesk -n ticketdesk apply -f k8s/hpa.yaml
kubectl --context kind-ticketdesk -n ticketdesk describe hpa ticketdesk

先让 top 查询可用，再进行有上限的实验负载。HPA 调整期望副本数，节点还需要可调度容量；数据库或外部配额也不会随应用副本自动增长。GitOps 与 HPA 同时管理 replicas 时，应设计字段所有权，避免两个控制器来回覆盖。

3. 运行身份不应自动获得集群管理能力#

TicketDesk 无须访问 Kubernetes API，ServiceAccount 关闭自动挂载 token。运维观察身份则通过 Role 与 RoleBinding 只读必要资源，不授予 Secret 读取或 Deployment 修改权限。

在有相应 impersonation 权限的实验管理员身份下应用 k8s/operations.yaml，再检查：

kubectl --context kind-ticketdesk -n ticketdesk apply -f k8s/operations.yaml
kubectl --context kind-ticketdesk -n ticketdesk auth can-i list pods --as=system:serviceaccount:ticketdesk:ticketdesk-observer
kubectl --context kind-ticketdesk -n ticketdesk auth can-i get secrets --as=system:serviceaccount:ticketdesk:ticketdesk-observer
kubectl --context kind-ticketdesk -n ticketdesk auth can-i delete deployments --as=system:serviceaccount:ticketdesk:ticketdesk-observer

预期分别为允许、拒绝、拒绝。若测试发起者无 impersonation 权限，需要通过适合的真实测试身份验证，而不是给所有身份 cluster-admin 来让检查通过。

4. Pod 安全约束降低进程权限#

base 以非 root 用户运行、移除额外 capability、禁止权限提升并将应用根文件系统设为只读。这些约束让一部分危险行为更难发生，但不是应用漏洞的替代修复，也不自动形成强租户隔离。

系统需要写入的位置通过明确卷提供，例如 /tmp。部署前检查依赖是否错误地把缓存、临时文件或日志写到应用目录，避免把只读错误误判成网络问题。

5. NetworkPolicy 需要真正执行它的网络实现#

k8s/policies.yaml 提供默认拒绝、应用到数据库、DNS、入口和比较客户端规则。只有支持并启用策略执行的 CNI 才能落实这些声明；不要假设默认 kind 环境具备对应能力。扩展实验应单独选择与集群版本兼容的 CNI，并按其官方流程安装验证。

允许应用连接数据库，需要源端 egress 与目标端 ingress 同时满足。多条策略的允许规则会组合，不能把其中一条 deny-by-default 当成覆盖所有其他允许规则的最高优先级规则。参考 Kubernetes NetworkPolicy。

本例还给两类比较客户端相同的 DNS 与目标端口出站许可：access=ticketdesk-reader 和 access=ticketdesk-other。只有前者获得 API 入站许可，便于把结果差异定位到 API 入站规则，而不是 DNS 是否被放行。

6. 用正反例确认边界#

在同一命名空间创建两个短生命周期测试 Pod，使用已有 Python 应用镜像执行带超时的 HTTP GET。两者除了 access 标签不同，命令、镜像与目标相同。允许客户端应成功，另一个应按策略被阻止；还需验证 DNS 在两者中均能解析。

确认 CNI 已执行策略且镜像已经载入本地集群后，可在干净的实验命名空间使用以下具体步骤。net-reader 和 net-other 必须是本次新建名称：

kubectl --context kind-ticketdesk -n ticketdesk apply -f k8s/policies.yaml
kubectl --context kind-ticketdesk -n ticketdesk run net-reader --image=ticketdesk:dev --image-pull-policy=IfNotPresent --labels=access=ticketdesk-reader --restart=Never --command -- python -u -c "import socket,urllib.request; print(socket.gethostbyname('ticketdesk')); print(urllib.request.urlopen('http://ticketdesk/health/ready',timeout=5).status)"
kubectl --context kind-ticketdesk -n ticketdesk run net-other --image=ticketdesk:dev --image-pull-policy=IfNotPresent --labels=access=ticketdesk-other --restart=Never --command -- python -u -c "import socket,urllib.request; print(socket.gethostbyname('ticketdesk')); print(urllib.request.urlopen('http://ticketdesk/health/ready',timeout=5).status)"
kubectl --context kind-ticketdesk -n ticketdesk logs net-reader
kubectl --context kind-ticketdesk -n ticketdesk logs net-other

若日志提示容器尚未启动，先检查 Pod 事件并等待启动，再读取。两者都应打印解析地址，只有 reader 应继续打印 200；other 的请求异常要结合 CNI 和策略证据判断。保存结果后，使用同一 context 与 namespace 删除这两个测试 Pod。

不要用 port-forward 验证 NetworkPolicy，也不要只观察“请求超时”就宣布隔离成功。还要确认健康对照成功、策略实际生效、请求走的网络路径以及没有残留的额外允许策略。

7. 验收与清理#

交付资源设置与观察、HPA 的指标依赖、三项权限结果、网络正反例和实际 CNI 版本。停止负载，删除本次比较客户端，按原计划恢复策略与伸缩配置。删除整个命名空间会同时影响数据资源，不能用作普通策略清理。

这三类边界共同缩小影响，但没有任何一个单独证明集群已经适合不互信租户。更严格场景还需结合节点、控制面、存储、身份和组织责任设计。
