CHAPTER 14 · 第 4 篇v0.3 阅读版

编写可维护的 Dockerfile

学习目标构建镜像并检查用户、依赖和启动行为；证明镜像层中没有实验凭据；比较构建时间与大小
本页目录1. 构建上下文决定能看到什么2. 为什么把依赖和源码分开3. 多阶段构建没有自动的瘦身保证4. 运行身份与可写位置5. 凭据分成构建时与运行时6. 做一次有记录的构建实验7. 完成条件

能构建成功只是起点。一个可维护的 Dockerfile 应让读者看清基础环境、依赖安装、应用复制、运行身份和启动命令，还应便于检查“这次构建为什么变了”。本章逐段解释配套项目，再做两项可测量的修改实验。

前置条件是第 13 章的容器环境可用。命令在 ticketdesk/ 中执行。本章列出的镜像标签是待验证的候选配置，尚未固定基础镜像 digest；请不要把它描述成已实现长期可重复构建。

1. 构建上下文决定能看到什么#

docker build --tag ticketdesk:dev .

最后的点是构建上下文，不是无意义的占位符。COPY 从这个范围内读取文件；上下文过大会增加传输和误带文件的风险。项目用 .dockerignore 排除本地环境、缓存、备份和 Git 元数据。Dockerfile 也只复制必要目录，没有用 COPY . . 把整个工作区装进运行镜像。

忽略文件只能降低误带的概率，不能替代检查。如果凭据被复制到某一层，再在后续层中删除，早先的内容仍可能存在于镜像制品中。凭据不应先进入层，再依赖删除补救。

2. 为什么把依赖和源码分开#

依赖阶段先复制 requirements.txt，再安装到 /packages；源码在后面的运行阶段复制。只改 app/main.py 时，依赖列表没有变化，有机会复用安装依赖的缓存。

ARG PYTHON_IMAGE=python:3.12-slim
FROM ${PYTHON_IMAGE} AS dependencies
WORKDIR /app
COPY requirements.txt .
RUN python -m pip install --no-cache-dir --target=/packages -r requirements.txt

构建缓存是节省时间的工具，不应承担正确性职责。清空缓存后，构建仍应成功。反过来，如果依赖文件没有固定版本，即使 Dockerfile 不变，重新解析依赖也可能得到不同内容。本项目固定了 Python 包版本，但仍需要把系统基础镜像和包文件哈希纳入后续验证。

3. 多阶段构建没有自动的瘦身保证#

运行阶段从相同基础镜像开始，只取走依赖产物和业务目录。这样构建工具与临时文件可以留在前一个阶段，运行阶段的职责更清晰。

FROM ${PYTHON_IMAGE}
WORKDIR /app
COPY --from=dependencies /packages /packages
COPY app ./app
COPY migrations ./migrations
USER 10001:10001
CMD ["python", "-m", "uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000", "--no-access-log"]

完整文件还设置 PYTHONPATH=/packages，否则安装位置未必在 Python 的模块搜索路径中。运行阶段保留 migrations，因为同一个镜像也会以迁移命令启动一个短任务。

多阶段的收益取决于你实际留下和排除了什么。本例没有在构建阶段安装庞大的编译工具链，因此不要预先宣称“体积降低 80%”。记录真实大小和两次构建耗时，再解释测量结果。

4. 运行身份与可写位置#

数字 UID 10001 不需要对应一个可登录的操作系统账号。镜像中的应用文件只要可读，普通用户就能启动；但它不能随意修改系统目录。Compose 进一步将根文件系统设为只读，并提供临时目录。

docker image inspect --format '{{.Config.User}}' ticketdesk:dev
docker run --rm --entrypoint python ticketdesk:dev -c 'import fastapi, psycopg; print("dependencies imported")'
docker compose exec app python -c 'from pathlib import Path; p=Path("/tmp/write-check"); p.write_text("ok"); print(p.read_text()); p.unlink()'

预期用户是 10001:10001，依赖能够导入，/tmp 写入成功。再尝试写 /app/write-check，预期只读挂载阻止写入。只读限制由 Compose 启用，直接 docker run 如果不加同样选项，行为可能不同；镜像配置和部署配置要分开看。

5. 凭据分成构建时与运行时#

安装私有依赖可能需要构建凭据，应用连接数据库需要运行凭据。它们的使用时间、授权范围和注入方式不同。

普通 ARG 与 ENV 适合非秘密的构建参数和默认值，不是秘密存储。项目把源码 Commit 写入标签和环境变量，因为这个信息本来就用于追踪；数据库密码则在运行时读取，没有写入 Dockerfile。

初学阶段先使用公开依赖。如果后续接入私有包，应采用构建器提供的 secret mount，并验证日志、缓存和产物；不要把 token 拼进下载 URL、Dockerfile 或命令示例。检查时使用明确的虚构标记，避免为了“验证泄露”打印真实凭据。

6. 做一次有记录的构建实验#

先记录当前 Commit 与工作区是否干净，再构建候选镜像：

git status --short
COMMIT_SHA="$(git rev-parse HEAD)" APP_VERSION=chapter14 docker compose build app
docker image inspect --format '{{.Size}} {{index .Config.Labels "org.opencontainers.image.revision"}}' ticketdesk:dev

在独立实验分支修改首页一行文案，再构建，观察依赖安装步骤是否使用缓存；随后只更改一个确有理由升级的依赖版本，观察缓存失效位置。不要为了实验随意选一个未知或已失效的版本。记录构建日志中对应步骤、总耗时、镜像大小、CPU 架构和网络条件。

这类测量没有跨电脑通用的标准答案。能够说明差异来自哪一层，比只报告快了几秒更有价值。完成后恢复实验变更或通过正常 PR 合并，避免把无意义的版本波动带入主线。

7. 完成条件#

本章的交付物是一份构建报告：输入源码、依赖版本、基础镜像候选、运行用户、缓存实验、大小与耗时，以及镜像中不存在实验凭据的检查过程。docker history --no-trunc 可帮助检查构建指令，但不能单独证明镜像全部层没有秘密；还需结合上下文、COPY 范围与制品检查。

本阅读版尚未完成真实镜像构建、层检查与基础镜像 digest 锁定，这些结果必须由后续容器验证补齐。参考：Docker 官方构建建议。
