Git 协作、分支与评审

学习目标用 `feature/add-ticket-priority` 提交变更，与另一分支制造冲突并解决；用 `fix/healthcheck-timeout` 演示修复；区分回退提交和重写历史
本页目录1. 工作区、暂存区和提交2. 分支是指向提交的名字3. 完成一次小变更4. 制造并解决一次冲突5. merge、rebase、revert 怎样选6. 评审需要看什么7. 密钥误提交怎样处理8. 本章验收

Git 保存变更历史，PR 让团队讨论和检查一个变更，发布记录再把代码与运行环境连接起来。把这三个角色分开理解，就不容易把“已 push”误当成“已上线”。

本章沿用 main、feature/... 和 fix/... 等常见命名。更多可视化阅读可以进入你个人网站的 Git 教程，本章重点放在交付协作。

1. 工作区、暂存区和提交#

工作区是你正在编辑的文件；暂存区描述下一次提交将包含什么；提交把一个快照和它的历史关系记录下来。远端是另一份仓库，push 才会把本地已有提交发送过去。

git status --short
git diff
git diff --cached
git log --oneline -5

编辑之后先看 diff，再有意识地暂存。把格式化、功能变更和无关删除混在一个提交里，会让评审者难以识别真正风险。

提交信息应描述意图，例如 feat: support filtering tickets by status。feat、fix 等前缀是一种团队约定，真正重要的是读者能理解发生了什么以及为什么。

2. 分支是指向提交的名字#

创建分支不会复制一个完整项目目录。它让你为一条工作历史设置可移动的引用。提交之后，当前分支指向新的提交；合并则记录两条历史如何结合。

主线建议使用寿命较短的功能分支，完成小变更后经过 PR 合并。长期分支会积累更多差异，增加同步和集成成本。Git Flow 适合某些需要长期维护多个发布线的团队，但会增加分支和合并规则；应根据发布方式选择。

核心模型与命令细节可以查阅 Pro Git 中文版。

3. 完成一次小变更#

先确认工作区没有未保存的无关修改，然后执行：

git switch main
git switch -c feature/add-release-note
printf '# 发布记录\n\n记录每次交付的版本与验证结果。\n' > release-notes.md
git add release-notes.md
git diff --cached
git commit -m "docs: add release record entry"

配置了自己的远端后，再推送该分支并创建 PR。不要把教程中某个示例账号的仓库地址当成自己的远端。git remote -v 可以帮助确认目标。

PR 描述包含变更原因、影响、验证和恢复方式。没有远端时，可以先在本地检查 diff 和运行测试，但应明确：你尚未验证托管平台的评审与保护规则。

4. 制造并解决一次冲突#

在专门的练习仓库中，令 feature/add-release-note 和 feature/add-health-note 从同一 main 出发，各自以不同内容创建 release-notes.md。先把一个分支合并到 main，再合并另一个，就可能出现同一路径的添加冲突。

冲突意味着 Git 无法自动决定结果，不表示哪个作者一定错误。打开文件，理解两种意图，编辑成最终应保留的内容，移除冲突标记，运行必要检查，再暂存并完成合并。

git status
git diff
git add release-notes.md
git commit

如果当前无法判断，git merge --abort 可以中止正在进行的合并并回到相应起点。它不是替代备份的通用撤销工具；操作前仍要理解工作区状态。

5. merge、rebase、revert 怎样选#

操作 主要作用 使用时关注
merge 合并两条历史，必要时产生合并提交 保留分支之间的关系
rebase 在新基底上重新应用提交，形成新提交身份 不要随意改写他人依赖的共享历史
revert 新增一个撤销既有变更的提交 共享分支中保留审计轨迹
reset 移动当前分支，按模式影响暂存区或工作区 理解未提交工作可能受影响的范围

已合并错误变更时，常见做法是通过新的修复或 revert PR 恢复代码意图。回退代码不等于数据库数据自动恢复，也不等于运行环境立即切换了版本。revert 的确切行为见 Git 官方文档。

6. 评审需要看什么#

评审者应先理解需求与验收，再看代码是否覆盖正常、异常、兼容和恢复路径。对于 Dockerfile、CI 工作流和部署配置，还要检查权限与运行影响。

仓库保护可以要求检查通过、评审批准和限制直接推送。功能是否可用取决于平台、仓库类型与套餐，设置后需要实际验证。写了一份 CODEOWNERS 文件，不必然表示所有相关变更都已经被强制审批。

第三方代码与工作流也属于供应链。不要在审查不可信 PR 时把生产凭据交给其任意脚本。相关平台风险在 GitHub Actions 安全参考中有说明。

7. 密钥误提交怎样处理#

把文件加入 .gitignore 只影响之后的跟踪判断，不能让已经进入历史的秘密失效。发现真实凭据泄漏时，先撤销或轮换，再处理历史、日志和访问范围。不能只删除当前文件就宣布风险消失。

本项目 .env、备份、虚拟环境和本地运行记录都在忽略规则中。提交前检查暂存区，尤其关注复制来的配置、错误日志和截图。

8. 本章验收#

提交一个小变更，留下评审意见与测试结果；在练习仓库解决一次冲突；说明共享分支中撤销代码的方式，以及它与运行版本和数据恢复的区别。
