CHAPTER 25 · 第 7 篇v0.3 阅读版

Kubernetes 架构、工作负载和探针

学习目标部署应用，观察副本恢复；分别诊断 CrashLoopBackOff、镜像拉取失败和就绪失败
本页目录1. 一次声明怎样变成进程2. 选择正确的工作负载对象3. 从可解释的顺序开始4. 三种探针分工5. 看懂三类常见失败6. 删除一个 Pod，观察协调7. 验收与下一步

Compose 把多服务放在一台机器上。Kubernetes 进一步通过 API 保存期望状态，让多个控制器持续尝试把现实调整到期望。学习它的关键是看懂“谁在协调什么”，而不是先记住大量 YAML 字段。

前置是容器、网络、发布与数据库迁移。配套 k8s/README.md 给出完整本地步骤；需要 Docker、kind、kubectl、默认 StorageClass 和足够运行三个本地节点的资源。本书没有在编写环境启动真实集群，命令结果仍需实际验证。

1. 一次声明怎样变成进程#

你向 API Server 提交 Deployment。对象被持久保存，控制器根据它维护 ReplicaSet；ReplicaSet 维护 Pod 数量；调度器为待调度 Pod 选择节点；节点上的 kubelet 与容器运行时启动容器并报告状态。

组件 主要责任 不自动负责什么
API 与状态存储 保存和验证对象状态 证明业务数据正确
控制器 反复比较现实与期望 解决所有依赖故障
调度器 根据资源与约束选择节点 给容量不足的集群凭空增加节点
kubelet 在节点落实 Pod 运行要求 替应用实现事务和幂等
应用 处理业务与运行协议 控制整个集群的资源策略

协调不是一次性的脚本步骤。删除由 Deployment 管理的 Pod 后，控制器通常会创建替代 Pod；删除 Deployment 则是改变期望本身。声明的副本数不等于任何时刻都有相同数量的健康实例。

2. 选择正确的工作负载对象#

Deployment 适合可替换的无状态应用实例；Job 表达有完成条件的任务；CronJob 表达调度任务；DaemonSet 用于在符合条件的节点运行实例。StatefulSet 提供稳定身份与存储关联，但不直接实现数据库复制和高可用。

本项目把 API 放进 Deployment，把迁移放进独立 Job，把教学数据库放进单副本 StatefulSet。迁移有锁与事务，仍应由发布流程有序触发，不能因为应用有三个副本就让三个实例各自随意迁移。

3. 从可解释的顺序开始#

在 ticketdesk/ 执行配套 README 的流程：构建镜像、创建专用 kind 集群、加载镜像、建立命名空间与本地秘密、启动数据库、等待迁移完成、最后应用 API 配置。

kind create cluster --name ticketdesk --config k8s/kind.yaml
kind load docker-image ticketdesk:dev --name ticketdesk
kubectl --context kind-ticketdesk get nodes
kubectl --context kind-ticketdesk get storageclass

镜像需要预先按 README 构建。Secret 由本机脚本生成虚构实验密码，不进入 Git；再次运行时保留既有密码，不能只更新应用端却不更新已初始化的数据库身份。

迁移完成后才部署应用：

kubectl --context kind-ticketdesk -n ticketdesk wait --for=condition=complete job/ticketdesk-migrate-v03 --timeout=120s
kubectl --context kind-ticketdesk apply -k k8s/base
kubectl --context kind-ticketdesk -n ticketdesk rollout status deployment/ticketdesk --timeout=180s

如果前面数据库或迁移尚未创建，这段不会独立成功。执行过程按 README 连续进行，不能把正文摘要当成跳过前置条件的快捷入口。

4. 三种探针分工#

startup probe 保护启动阶段；liveness probe 用于判断容器是否需要被重启；readiness probe 决定实例是否满足接收常规服务流量的条件。本例分别使用基本存活响应和访问数据库的就绪响应。

数据库中断时，如果 liveness 也检查数据库，可能导致所有应用一起重启，增加恢复压力。把依赖问题表达为未就绪，通常更容易保留诊断现场；是否如此设计仍要看应用是否能够自行恢复依赖连接。

探针有间隔、超时和失败阈值，状态变化不会立即完成。超时还需与应用的连接、查询预算配合。一次 readiness 成功，也不能替代创建和更新工单的业务验收。

5. 看懂三类常见失败#

kubectl --context kind-ticketdesk -n ticketdesk get pods -o wide
kubectl --context kind-ticketdesk -n ticketdesk describe pod '<实际 Pod 名称>'
kubectl --context kind-ticketdesk -n ticketdesk logs '<实际 Pod 名称>' --previous
kubectl --context kind-ticketdesk -n ticketdesk get events --sort-by=.metadata.creationTimestamp

ImagePullBackOff 先看镜像名称、拉取权限与节点是否有本地镜像；CrashLoopBackOff 先看进程退出原因与上一次日志；Running 但未 Ready 则检查探针与依赖。这些状态描述不同阶段，不能统一回答“把 Pod 删掉重试”。

本地 ticketdesk:dev 使用 IfNotPresent，后续重建同名标签时，节点可能仍保留旧内容。正式实验用独立候选标签或 digest，并明确加载与替换过程。

6. 删除一个 Pod，观察协调#

确认 API 已有两个健康副本，记录 Pod 名称、UID 和节点。只删除其中一个实际 Pod，再观察新 Pod 的 UID 与启动过程，并对同一工单持续查询。这个实验删除的是可替换 API，不是数据库或 PVC。

控制器补副本证明协调起作用，不证明零中断或数据高可用。副本可能共享节点，数据库仍是单点，流量路由也存在状态传播延迟。记录实际响应，不把对象数量当成用户体验。

7. 验收与下一步#

交付对象关系表、镜像身份、数据库与迁移顺序、三种探针的解释，以及一次 Pod 替换时间线。用 port-forward 对本地服务运行 scripts/smoke.py，确认旧工单仍可查询。

阅读 Kubernetes Deployment 核对控制行为。下一章将处理稳定访问入口，并解释为什么 Pod IP 不适合作为应用长期地址。
