沿一次请求理解网络和 TLS

学习目标从域名、连接、TLS 到应用逐层检查；用 NGINX 代理服务，解释 502 与证书不受信任的差异
本页目录1. 从地址到业务响应2. IP、端口与 localhost 的边界3. DNS、子网与防火墙各负责什么4. 反向代理把外部请求送到应用5. TLS 为什么会失败6. 502、504 与应用错误7. 独立练习

用户说“打不开”，可能指域名无法解析、TCP 连接失败、证书不受信任、代理找不到应用，或者 API 自己返回错误。本章沿一次请求分层排查，建立比反复刷新浏览器更有效的方法。

你需要一个已启动的 TicketDesk。网络工具在不同系统中可能需要单独安装，命令是否存在应在使用前检查。

1. 从地址到业务响应#

访问一个 HTTPS 地址时，客户端通常先解析域名，选择路由并建立传输连接，然后完成 TLS 握手，再发送 HTTP 请求。反向代理可能将请求转发给内部应用，应用再访问数据库。

这是概念演示：选择不同故障，观察哪一层能够通过。它不会访问你的网络。真实排查仍需要下面的命令和环境证据。

层次 问题 常用证据
名字 域名解析到了什么地址？ DNS 查询、解析器配置
路由与连接 能到目标地址和端口吗？ 路由、监听状态、连接超时或拒绝
TLS 身份与证书链能验证吗？ 证书主机名、有效期、信任链
HTTP 入口 请求到达了哪个虚拟主机和路径？ 状态码、代理日志
应用与依赖 业务逻辑和数据库能工作吗？ 应用日志、就绪检查、业务请求

2. IP、端口与 localhost 的边界#

IP 用于定位网络接口，端口帮助选择该主机上的服务。127.0.0.1 属于当前网络命名空间的回环地址。在宿主机终端、应用容器和云端 Runner 中，它们指向的对象不同。

TicketDesk 应用容器访问 PostgreSQL 使用服务名 db 和端口 5432；宿主机通过映射端口 55432 访问数据库。把容器内的数据库地址改成 localhost:55432，通常是在访问应用容器自己，不是宿主机 PostgreSQL。

curl -i --connect-timeout 2 --max-time 5 http://127.0.0.1:8000/health/live
docker compose ps

连接被拒绝常见于目标没有监听、端口错误或主动拒绝；超时可能与路由、过滤、服务负载等有关。仅靠其中一个现象不能确定最终原因。

3. DNS、子网与防火墙各负责什么#

DNS 把名字映射到记录，路由决定数据包下一跳，防火墙按规则允许或阻止通信。把域名解析正确，并不会自动打开目标端口。

在 Linux 可用 getent hosts 观察系统解析结果；安装了 dig 时可进一步查询 DNS 记录。排查时注意缓存、搜索域、分流 DNS 和不同网络的解析器。

子网与路由决定地址可达范围。后续云章节会把 VPC、子网、路由表和安全组串在一起。本章先建立职责边界，不需要背诵所有网络协议。

4. 反向代理把外部请求送到应用#

配套项目有一个可选 NGINX 服务：

docker compose --profile proxy up -d proxy
curl -i http://127.0.0.1:8080/health/ready

请求先到宿主机 8080，再进入代理容器的 80，代理转发到 app:8000。配置在 ops/nginx.conf。代理可以集中处理路由、TLS、日志和部分连接策略，但它不会自动修复下游应用。

proxy_connect_timeout 约束连接上游的等待，proxy_read_timeout 与读取上游响应有关，两者解决的问题不同。路径拼接还会受到 location 与 proxy_pass 是否携带 URI 的影响。准确语义见 NGINX proxy 模块文档。

如果应用重建后代理仍使用旧解析结果，可先在本地实验重启代理验证假设，再研究动态解析配置。应说明部署实现的限制，不能把偶然恢复当成已经找到根因。

5. TLS 为什么会失败#

TLS 一方面加密传输，一方面使客户端验证服务器身份。证书需要覆盖访问的主机名、在有效期内，并能连接到客户端信任的签发链。服务器时间与客户端时间也会影响判断。

curl -Iv --connect-timeout 3 --max-time 10 https://example.com

用一个允许访问的公开测试域名练习观察握手、证书和响应头。内部 CA 场景需要分发正确的信任根；自签证书适合特定实验，但客户端仍需明确如何信任。

curl -k 可以跳过证书验证，因而不能用于证明 TLS 身份验证正常。排查时即使临时使用，也应解释验证被关闭了什么，并恢复正常校验后才通过验收。

6. 502、504 与应用错误#

502 通常提示代理没有取得有效上游响应；504 常见于代理等待上游超时。它们帮助定位调查方向，但最终解释要结合实际代理配置和日志。

若直接访问 8000 正常而经 8080 失败，先检查入口和上游连接；两者都失败，则继续检查应用和依赖。若健康检查成功但业务失败，应查看具体业务路径，健康接口的覆盖范围可能不足。

缓存、负载均衡与 CDN 会增加更多层。缓存可能返回旧结果，负载均衡可能只把部分流量送到有问题的实例。排查时记录请求时间、版本、请求 ID 和目标路径，以便对齐多处证据。

7. 独立练习#

在实验副本中把 NGINX 上游端口改成未监听端口，重载或重启代理。分别请求应用与代理入口，记录差异，再恢复配置。不要修改正在服务其他项目的全局 NGINX。

验收报告要回答：故障在哪一层、哪些证据排除了数据库问题、为什么只看浏览器“失败”不足以定位。下一章会把这些有确定规则的检查编成脚本。
