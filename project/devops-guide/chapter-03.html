CHAPTER 03 · 第 1 篇v0.3 阅读版

运行工单服务，读懂一个应用

学习目标从提供的骨架启动应用，创建并查询工单，修改一个字段，提交可读的变更说明
本页目录1. 启动项目2. 一个请求经过哪些地方3. 用命令验证真实业务4. 认识项目文件5. 故意提交一个无效请求6. 创建第一条 Git 记录7. 停止、重启与数据检查8. 练习与验收

这一次先不讨论复杂架构。我们要让一条请求经过应用、写入数据库，再把结果读回来。你将获得一个能够验证的基线：后面每次修改，都可以与它比较。

前置条件是第 02 章的环境准备。所有命令都在解压后的 ticketdesk 根目录执行，默认使用本机端口 8000。项目文件可在“配套资料”页下载。

1. 启动项目#

python3 scripts/lab.py doctor
python3 scripts/lab.py up

up 的步骤是：准备本机配置、构建应用镜像、启动 PostgreSQL 并等待其健康、执行数据库迁移、启动应用、运行业务检查。第一次需要下载依赖，耗时与网络和缓存有关。

脚本只在业务检查通过后记录最近可用镜像。终端出现错误时，它会返回失败，而不是用最后一行“完成”掩盖前面的错误。若你没有 Docker 服务，这条路径不能执行；Python 接口测试仍可单独运行，但范围不同。

浏览器打开 http://127.0.0.1:8000。创建一条虚构工单，例如“实验环境证书更新”，观察它出现在列表中。本章对容器的使用只是操作预览，第 13—15 章会展开机制。

2. 一个请求经过哪些地方#

浏览器把填写的信息编码为 JSON，通过 HTTP 发给应用。FastAPI 先校验字段，业务接口再调用仓储层。仓储层使用参数化 SQL 写入 PostgreSQL，数据库提交事务后返回结果。最后应用把工单对象编码为 JSON，浏览器显示它。

边界 传入什么 谁负责什么
浏览器到 API HTTP 方法、路径、JSON 请求体 网络传输和接口约定
API 到输入模型 标题、描述、优先级 类型、长度、取值范围
API 到仓储 经过校验的数据 业务动作和数据访问分工
仓储到数据库 SQL 与独立参数 事务、约束、持久化
API 到浏览器 状态码和 JSON 响应 结果表达与错误处理

后面排障时，先判断问题发生在哪个边界。例如 422 通常说明请求没有通过输入校验；503 可能意味着依赖暂不可用。HTTP 状态码是线索，仍需结合响应内容与日志判断。

3. 用命令验证真实业务#

curl -i http://127.0.0.1:8000/health/live
curl -i http://127.0.0.1:8000/health/ready
curl -s http://127.0.0.1:8000/version

live 证明应用进程能响应；ready 还访问数据库，并确认应用所需字段可以查询；version 返回运行版本和提交信息。开发模式可能显示 dev 和 unrecorded，不能凭空把它解释为某个 Git 提交。

创建工单：

curl -i http://127.0.0.1:8000/tickets \
  -H 'Content-Type: application/json' \
  -H 'X-Request-ID: first-ticket' \
  -d '{"title":"实验环境证书更新","description":"仅用于教学","priority":"high"}'

预期状态码为 201，响应包含 id、title、priority 和 status。记录实际返回的 ID，不要假定它总是 1：启动检查本身也会创建验收工单。

curl -s http://127.0.0.1:8000/tickets
curl -i http://127.0.0.1:8000/tickets/1

第二条命令演示单条查询路径；实际实验应替换成你记录的 ID。对不存在的工单应返回 404。

4. 认识项目文件#

文件 作用 你会在哪些章节修改它
app/main.py HTTP 接口、校验、日志、健康与指标 测试、配置、观察
app/store.py PostgreSQL 数据访问 集成测试、性能与数据恢复
app/migrate.py 有校验和与并发锁的迁移入口 数据库发布
migrations/ 按顺序执行的数据库变化 schema 兼容性
tests/test_api.py 使用内存仓储的 API 合约测试 第 11—12 章
scripts/lab.py 环境操作与交付验收 基础实验和恢复
compose.yaml 本地多服务配置 容器与部署
.github/workflows/ GitHub 检查与候选制品发布 CI/CD

边界清楚比文件数量多更重要。把 SQL 放在独立仓储层，使接口测试可以替换存储；代价是这种测试没有验证 SQL，所以我们还需要真实数据库实验。

5. 故意提交一个无效请求#

curl -i http://127.0.0.1:8000/tickets \
  -H 'Content-Type: application/json' \
  -d '{"title":"x","priority":"urgent"}'

预期为 422。当前标题要求去除首尾空白后长 3—120 字，优先级只接受 low、normal、high。观察校验错误是否指出具体字段，修改后重发。

这就是一个最小的反向测试：我们不仅验证“正确输入成功”，也验证“错误输入没有被悄悄接受”。后面会将它放入自动测试。接口测试的技术入口见 FastAPI 官方测试教程。

6. 创建第一条 Git 记录#

如果解压后的目录还没有 Git 仓库，可以执行：

git init -b main
git status --short
git add .
git diff --cached --stat
git commit -m "chore: add ticketdesk teaching baseline"

先确认 .env、备份和虚拟环境没有进入暂存区。Git 如果要求作者信息，按自己的身份设置仓库级 user.name 与 user.email；示例不提供虚构作者。已有仓库则直接复用，不要重复初始化。

本章先获得一次可追溯的基线提交。Git 的模型、分支和评审在第 09 章系统讲解，官方中文参考是 Pro Git。

7. 停止、重启与数据检查#

python3 scripts/lab.py down
python3 scripts/lab.py up

重新启动后查询之前记录的工单 ID。默认停止操作会保留数据卷，因此记录应仍然存在。若你主动删除了卷，这个假设就不再成立。第 15 章会解释容器可删除而数据需要单独管理的原因。

8. 练习与验收#

创建一条高优先级工单，记录 ID、创建响应、运行版本和请求 ID。重启后重新读取它，再发一个无效请求。整理四项证据，说明每项覆盖了什么行为。

如果只有首页能打开，却不能创建工单，本章还没有完成。下一章会把这样的判断写成明确的需求验收条件。
