CHAPTER 24 · 第 6 篇v0.3 阅读版

用 Ansible 管理主机配置

学习目标在本地实验 VM 配置应用运行环境；第二次执行无无关改动；修改配置后只触发必要服务动作
本页目录1. inventory、playbook 与模块2. 逐段阅读配套部署任务3. handler 让重启跟随必要变化4. check 与 diff 各自能证明什么5. 把重复任务组织成 role6. 制造一次配置遗漏7. 验收与清理

OpenTofu 可以声明机器存在，却不意味着机器里已经有正确的 Python、应用文件和 systemd 服务。Ansible 适合把主机配置写成可重复执行的任务，并根据实际变化触发必要动作。本章用 VM 路线帮助理解资源供给与系统配置的分工。

前置是自己拥有的可丢弃 Ubuntu 24.04 类实验 VM、已核验的 SSH 主机身份和必要的提升权限。配套位于 automation/ansible/。它不会创建 VM；数据库与受保护的 /etc/ticketdesk/app.env 需要按第 18—19 章预先准备。

1. inventory、playbook 与模块#

inventory 说明有哪些目标及连接方式；playbook 说明对哪一组目标执行什么；module 实现文件、软件包、账号或服务等特定操作。它们使任务具备比任意 shell 命令更明确的状态语义。

先复制 inventory.example.ini 到自己受保护的本地清单，替换文档地址与登录用户。不要把 203.0.113.10 当成真实实验服务器，也不要关闭 SSH 主机密钥检查以跳过首次身份确认。

ansible-inventory -i inventory.local.ini --graph
ansible ticketdesk -i inventory.local.ini -m ansible.builtin.ping
ansible-playbook -i inventory.local.ini site.yml --syntax-check

Ansible 的 ping 模块检查远端执行条件，并不等同于 ICMP ping。连接失败时区分地址可达、SSH 身份、主机信任、Python 和权限，不先修改应用服务。

2. 逐段阅读配套部署任务#

任务创建无登录能力的 ticketdesk 用户，安装虚拟环境支持，把应用复制到版本目录，安装固定依赖，检查配置文件，再渲染 systemd 单元。该例把资源准备、文件、依赖、配置与服务动作分别表达。

版本目录形如 /opt/ticketdesk/releases/course-v03。修改应用时应使用新的发布身份，保留旧版本以供比较与恢复。例子复制本机源码，因此正式流程还应把来源改成经过验证、带校验信息的发布制品。

运行配置通过 /etc/ticketdesk/app.env 提供。文件应由有权限的管理流程创建，限制为服务所需身份可读，不包含在公开 inventory。playbook 只检查文件存在，不打印内容；数据库迁移也作为独立发布阶段处理。

3. handler 让重启跟随必要变化#

- name: Install systemd unit
  ansible.builtin.template:
    src: ticketdesk.service.j2
    dest: /etc/systemd/system/ticketdesk.service
    mode: '0644'
  notify: Restart ticketdesk

当模板内容实际变化，任务通知重启 handler。服务文件没有变化，不应为了“保险”每次都强制重启。配套在业务就绪检查前显式刷新已通知的 handler，避免检查到的仍是旧进程。

多个任务可以通知同一 handler，以减少重复服务动作。具体执行时机与通知规则参考 Ansible handlers。

4. check 与 diff 各自能证明什么#

ansible-playbook -i inventory.local.ini site.yml --check --diff
ansible-playbook -i inventory.local.ini site.yml
ansible-playbook -i inventory.local.ini site.yml

第一次 check 用于审阅预计变化；第二次执行真实变更；第三次检查幂等性。check mode 依赖模块支持和已有状态，首次安装时某些后续依赖尚不存在，不能把模拟结果当成运行验证。

--diff 会显示文件差异，因此秘密模板应禁用 diff 并按需要设置 no_log。保护日志也会减少排障信息，最好把秘密操作范围缩小，让非秘密的阶段与错误类别仍可观察。

预期第三次不再复制相同文件或重启无变化的服务。软件包缓存刷新等维护性动作需要单独解释；“所有 changed 永远为零”不是合理的跨环境承诺。

5. 把重复任务组织成 role#

当安装步骤稳定，并且至少有明确的复用场景，再拆成 role：默认参数、任务、模板、handler 和验证各有位置。role 的输入应表达业务能力，例如运行用户、发布目录和监听端口，而不是让调用者理解大量内部文件路径。

本版保留一个容易阅读的 playbook，练习是将它提取为 ticketdesk_app role，要求提取前后生成的 unit 和外部行为一致。不要一开始建立复杂角色框架，最后仍靠 shell 执行全部步骤。

6. 制造一次配置遗漏#

在独立实验 VM 上，暂时让配置路径缺失，再运行 playbook。预期断言拒绝继续启动服务，而不是使用一个猜测的数据库地址。恢复原配置后重新执行，再查询 /version 和业务接口。

另一个练习是仅修改非秘密的环境标识，观察服务是否按计划重启、版本接口是否反映新值。外部秘密文件变更没有自动进入本例 handler 通知链，需要明确的配置发布动作，不能假定所有外部变化都会被 Ansible 发现。

7. 验收与清理#

交付 inventory 的脱敏说明、playbook、预计变更与两次实际执行摘要、最终 unit、就绪及业务检查。VM 的创建与销毁仍由资源层管理；删除应用文件之前先停止对应服务，并保存需要的恢复材料。

本章实际 SSH 和 systemd 运行尚未在作者环境执行。能够读懂并进行语法检查只是第一层，远端权限、依赖安装、服务行为与幂等性需要自己的 VM 证据。
