CHAPTER 22 · 第 6 篇v0.3 阅读版

使用 OpenTofu 声明基础设施

学习目标默认用锁定的本地 Docker provider 创建实验资源；可选 AWS 实现；计划可读，创建后能验证，销毁对象明确
本页目录1. 声明对象与执行命令的区别2. 阅读配套 HCL3. 初始化、格式和静态验证4. 计划是需要阅读的变更说明5. 用平台事实确认结果6. 清理也需要审阅7. 练习与验收

手工点击创建网络很快，第二个人却难以知道参数、依赖和历史。基础设施即代码把期望状态保存为可评审的声明，再由工具比较现实与期望。本章先管理本机 Docker 资源，避免把学习 IaC 与付费云操作绑在一起。

前置是第 21 章和可用 Docker daemon。实验目录是 ticketdesk/infra/tofu/，只创建一个独立网络和一个空卷，不接管已有 Compose 数据。OpenTofu 与 provider 的实际运行验证状态见版本页。

1. 声明对象与执行命令的区别#

脚本通常说明按什么顺序做事；声明式配置先说明希望存在什么。OpenTofu 通过 provider 与具体平台通信，通过资源地址识别配置中的对象，并利用状态文件关联现实资源。

HCL 元素 职责 本例
provider 连接某类基础设施 API Docker daemon
resource 由当前配置管理的对象 网络与卷
data 读取已有对象的信息 后续可读取已有资源，读取不等于接管
variable 配置输入与约束 实验名称、Docker 地址
output 向操作者或下一流程输出信息 实际网络名与卷名
module 组合一组有边界的配置 可在复用需求稳定后提取

把所有内容拆成模块不是入门目标。先让一个小配置可以创建、验证、识别漂移和清理，再根据重复使用的边界组织模块。

2. 阅读配套 HCL#

main.tf 固定 Docker provider 到 3.6.2，并声明网络和卷。网络使用 internal = true，便于观察“资源已创建”和“可以访问互联网”是两个不同条件。

resource "docker_network" "lab" {
  name     = var.lab_name
  internal = true
}

resource "docker_volume" "lab" {
  name = "${var.lab_name}-data"
}

这是正文精简片段，完整文件包含标签和输入校验。docker_network.lab 是配置地址，不是 Docker 中的实际名称；修改资源地址可能需要迁移状态关联，不能仅当作变量重命名。

这里的网络和卷没有挂到应用，因此创建成功只验证资源管理流程。它不证明 TicketDesk 可用，更不证明云 IAM 或 VPC 已经验证。

3. 初始化、格式和静态验证#

tofu version
tofu init
tofu fmt -check
tofu validate

init 准备后端与 provider 等依赖；fmt 检查格式；validate 检查配置内部是否合法。它们各自承担一部分责任，不能替代连接真实平台后的计划与执行。

初始化产生的 .terraform.lock.hcl 应进入版本控制，用于记录 provider 选择与校验信息；.terraform/ 下载目录、state 和计划文件不进入源码。本版不伪造尚未下载的 provider 校验和，读者初始化后需保存自己的实际锁文件。

Docker Desktop 的 socket 可能不是 /var/run/docker.sock。查看自己的 Docker context，再通过 TF_VAR_docker_host 指定对应地址。不要为了解决本地连接问题把 Docker API 无认证地暴露到网络。

4. 计划是需要阅读的变更说明#

tofu plan -out=lab.tfplan
tofu show lab.tfplan
tofu apply lab.tfplan
tofu output

首次计划应只涉及本章的两个实验资源。阅读动作类型、资源地址和关键属性，确认没有意外删除或替换。已保存的计划用于执行被审阅的那次计划；环境或输入变化后，应重新生成并重新判断，不能把旧批准无限复用。

保存计划可能包含敏感值或状态信息，不应当作公开附件。机器输出中某个字段被标为 sensitive，也不自动意味着所有状态与计划存储都经过加密。语义参考 OpenTofu plan。

5. 用平台事实确认结果#

docker network inspect ticketdesk-iac
docker volume inspect ticketdesk-iac-data
tofu plan -detailed-exitcode

正常无变更的详细退出码为 0，有待应用变更为 2，执行错误为 1。CI 需要区分三者，不能把所有非零值都当成工具故障，也不能把有变更当成可以自动应用。

验收时记录网络的内部属性、标签、卷名称和计划结果。不要只保留终端最后一行的成功字样。第二次计划不应无原因地重复创建同一对象。

6. 清理也需要审阅#

先确认本章创建的卷始终为空，或其中数据已经不再需要，再读取销毁计划：

tofu plan -destroy
tofu destroy

交互确认前核对资源地址。已有容器正在使用网络或卷时，平台可能拒绝删除；这不是应该绕过的障碍，而是需要确认依赖关系的信号。不要使用全局 Docker 清理代替当前状态对应的销毁。

IaC 只能知道当前状态和配置管理的范围。它不会自动发现并清理账户中所有手工资源，也不会保证删除资源后业务数据仍能恢复。

7. 练习与验收#

将名称改为另一个符合校验的实验名，仅生成计划，判断哪些对象可能替换，暂不执行。再恢复配置，比较计划。提交 HCL、锁文件、创建与销毁计划、实际资源检查，以及关于“基础设施代码与应用配置分别管理什么”的解释。

本地 provider 帮助理解通用流程；云 provider 还需增加身份、区域、网络、费用和团队状态管理。下一章专门处理 state 与协作，避免把它视为可以随手删除的缓存。
