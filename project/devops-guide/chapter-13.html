CHAPTER 13 · 第 4 篇v0.3 阅读版

容器、镜像和隔离机制

学习目标运行、检查、停止应用容器；说明容器删除后什么保留；验证进程能接收停止信号
本页目录1. 分清源码、镜像和容器2. 隔离解决哪些问题3. 跟踪一次启动4. 主进程、信号与退出5. 容器消失后数据去哪里6. 验收与思考

你在自己的电脑上启动了 TicketDesk，同事却因为 Python 版本、系统库和工作目录不同而启动失败。把安装过程写成说明有帮助，但仍要每个人重新执行。镜像把应用及其运行所需的用户态文件组织成可分发的制品；容器则是基于这个制品启动的进程及其运行环境。

本章接在第 12 章之后。需要可用的 Docker Engine 或 Docker Desktop，以及 Compose v2。以下命令都在解压后的 ticketdesk/ 中执行，使用本机实验环境；完整容器流程尚未在本教程的编写环境执行，实际运行结果请记入环境记录。

1. 分清源码、镜像和容器#

源码描述你想让程序做什么，构建把源码和依赖转成镜像，运行时再把镜像变成容器。一个镜像能创建多个容器；停止某个容器不会修改镜像；重新构建镜像也不会自动更新正在运行的容器。

对象 TicketDesk 中的例子 常见误解
源码 app/main.py 修改本机文件就会改变已构建镜像
镜像 ticketdesk:dev 标签名称足以证明内容从未变化
容器 Compose 创建的 app 实例 容器停止等于镜像被删除
卷 PostgreSQL 的 ticket-data 数据一定和应用容器一起消失

镜像由文件系统层及配置构成。构建时的新增层复用已有层，运行时通常再增加可写层。本项目让应用容器根文件系统只读，把临时写入放到 /tmp；持久业务数据则写入独立数据库。

2. 隔离解决哪些问题#

Linux namespace 为进程提供独立的部分系统视图，例如进程编号、网络接口和挂载点。cgroup 用于统计和约束资源。容器内看起来拥有自己的文件系统和进程空间，但通常共享宿主机内核。

虚拟机通常包含自己的内核，容器通常共享运行容器的 Linux 内核。Docker Desktop 在部分桌面系统上借助 Linux 虚拟机提供这个环境，因此容器内的 Linux 与桌面宿主机不能简单视为同一操作系统。

共享内核意味着隔离仍有边界。不要因为“放进容器”就授予特权模式、挂载宿主机根目录或暴露 Docker socket。本例以普通数字用户运行、移除额外 capability，并限制端口只监听本机。它仍不是可以直接公开到互联网的完整安全配置。

3. 跟踪一次启动#

先让脚本完成构建、数据库启动、迁移和业务验证：

python3 scripts/lab.py doctor
python3 scripts/lab.py up
docker compose ps
docker compose images
docker compose logs --tail 30 app

预期 app 和 db 处于运行状态，app 健康检查通过，脚本打印包含 passed: true 的 JSON。不要把“命令返回了某个容器 ID”当成业务已经可用；进程可能在创建后立即退出。

检查进程和身份：

docker compose top app
docker compose exec app id
docker compose exec app python -c 'import os; print(os.getpid(), os.getcwd())'
docker stats --no-stream

exec 创建的是容器中的另一个进程，因此该 Python 命令输出的 PID 不一定是 1。应用的主进程由 Dockerfile 的 CMD 决定。资源使用量也只是一时的观察结果；没有设置 CPU 或内存上限，不代表容器自然获得了资源保护。

4. 主进程、信号与退出#

容器的生命周期通常跟随其主进程。主进程退出，容器停止；某个后台子进程仍在工作不一定能让容器存活。因此不要在 Dockerfile 中用 service ... start 然后让命令立即退出。

本例使用 JSON 数组形式启动 Uvicorn，不额外套一层 shell。停止时，运行时先向主进程发送终止信号，等待宽限期，再按需要强制结束。进程必须有机会停止接收新请求、处理已有请求并关闭资源。

docker compose stop -t 15 app
docker compose logs --tail 30 app
docker compose ps -a app
docker compose start app
python3 scripts/lab.py check

在日志中查找服务器关闭过程，记录退出状态和耗时。如果出现超时后被强制终止，继续检查主进程、阻塞操作和信号处理，不能只把宽限期无限延长。

5. 容器消失后数据去哪里#

创建一张工单并记下 ID。停止应用，再启动，查询同一个 ID；随后按第 15 章做保留卷的整体重建。两次实验验证的层次不同：前者只是同一容器重新启动，后者才涉及容器删除后重建。

数据位置 重启同一容器 删除容器再创建
容器可写层 通常保留 丢失
tmpfs 不应依赖其保留 丢失
独立命名卷 保留，除非另行删除 保留，除非另行删除
镜像中的文件 按镜像内容存在 按所选镜像内容存在

本项目的数据库目录位于命名卷，但卷不是备份。误删记录、错误迁移和存储损坏同样会作用于卷中的数据。第 19 章会把“持久存在”和“可恢复”分别验证。

6. 验收与思考#

提交一份实验记录：镜像名、容器状态、运行用户、主进程、停止日志，以及重启前后的同一工单内容。不要记录数据库密码或整个容器环境变量。

思考：为什么 docker compose exec app 执行成功不能证明数据库健康？为什么在本机修改 Python 文件后，容器仍返回旧行为？为什么把容器设成自动重启仍然不能修复错误的数据库地址？分别用进程、镜像和依赖这三个层次解释。
