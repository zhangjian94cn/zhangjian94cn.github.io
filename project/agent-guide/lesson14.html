第14课｜案例：研发的代码交付 Agent

建议学习 30 分钟（含练习） · 本课产出：可评审代码任务
返回课程总览14 / 16

用户故事：让一个 Issue 走到可评审的变更

作为研发工程师，我希望 Agent 根据一条明确 Issue 修改代码，运行相关验证，给出可审阅的差异与局限，以便我把时间放在设计和评审。交付物是可评审变更；是否合并由项目已有规则决定。

本课将公开的长期运行工程经验改编成一个教学仓库任务，未声称已经替任何真实项目创建 PR。

教学任务：给工单列表增加分类筛选

Spec 先写清：默认显示全部；可选择账号、设备两类；无匹配时显示空状态；刷新后是否保留选择要明确；筛选不能改变服务端权限。验收不应只有“增加筛选功能”，还应包含键盘操作、移动端布局和空结果。

一条典型执行路线是：读 Issue 与项目约定→定位代码→提出最小修改方案→修改→运行与变更相关的验证→检查差异→提交评审摘要。具体工具依项目而定，不必为每个动作都创建一个 Agent。

为什么工作目录与任务记录重要

代码 Agent 可以修改环境，环境也会反过来影响后续判断。若下一轮不知道上轮改过什么、测试是否真跑过，就容易重复修改或误报完成。

Anthropic 的长期任务文章展示了功能清单、进度文件、Git 历史和环境检查在跨会话交接中的作用。课程把这一思路改编为“每次交付一个可验收的增量”。长期任务公开实践。

课程建议的交接记录如下：

任务：工单列表增加分类筛选
已完成：筛选控件与空状态
变更：列表组件、筛选条件逻辑
已验证：全部/账号/设备/无匹配四个场景
未验证：真实服务端权限集成
当前阻塞：测试环境没有服务端凭证
下一步：由具备环境权限的人员执行集成验收

这是执行摘要，不能替代真实命令输出、差异和测试记录。不要让 Agent 仅通过修改“通过”字段完成验收。

哪些工作适合并行

可以让一个执行单元查相关实现，另一个查既有测试约定，最后由同一负责人合并理解。两个 Agent 同时修改同一组件，容易出现覆盖、冲突和风格漂移；即使使用不同分支或 worktree，也仍需集成评审。

如果任务必须先确定数据结构才能改界面，就有真实依赖，不宜为了并行而同时开工。给子任务的边界应写成“分析并返回建议”或“只修改指定测试文件”，而不是“尽力帮忙”。

代码权限与完成证据

可读文件范围、可写目录、可执行命令、网络访问与凭证注入，应由运行环境和仓库权限共同限制。提示词中的“不要动其他目录”是行为要求，不是安全隔离。地市人员可以在哪些目录工作，与后台 Agent 实际使用哪个凭证是两个需要分别验证的问题。

评审者应能看到：为什么改、改了什么、行为如何变化、运行了哪些验证、还有哪些未覆盖情况。截图能证明一个画面，不能证明所有业务路径。测试全部通过也要确认是否覆盖了本次验收，不能拿无关测试充数。

失败复盘：它说修好了，却没有保存文件

如果 Agent 在答案里贴出了正确代码，但工作区文件没改，任务仍未完成；如果文件已改，但没有启动真实页面，界面问题仍可能存在；如果测试失败被略过，评审者必须知道。完成状态应绑定可检查的交付物与验证结果。

工具错误时也不能无限重试。依赖安装受阻、缺少环境或无权限时，留下可复现的信息和下一步。绕过项目约定只为得到“绿色通过”，会破坏验收意义。

练习：改写一个含糊 Issue（20 分钟）

原 Issue：“工单页面不好用，帮忙优化。”请改为一个一天内可验收的小任务，补上范围、非目标、三项验收和一项失败出口。

展开参考答案 · 先试着自己回答

示例：增加账号/设备分类筛选，使用现有数据字段；不修改服务端接口、不重做整页设计。验收：默认全部；选择后结果正确且显示数量；无结果时可清除筛选返回全部。失败出口：发现现有数据没有稳定分类字段时，停止实现并提交字段缺口与建议，由需求负责人决策。加上权限与浏览器环境要求会使任务更完整。

研发的进阶路线

先读懂最小工具循环与轨迹；再写稳定的工具契约和失败测试；随后掌握上下文、检查点、幂等和隔离环境；最后才扩大到跨仓库、跨团队任务。能解释一次失败发生在哪一层，是比“能让 Agent 写代码”更有价值的能力。
