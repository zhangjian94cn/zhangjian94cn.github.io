第 7 课：真正难的是协作协议，不是给角色起名字

建议学习 30 分钟（含练习） · 本课产出：最小协作协议
返回课程总览7 / 16

场景：两个专家都说自己完成了，工单却错了

政策专家发现 IT-2048 缺少独立身份核验，写入“等待补充”。与此同时，设备专家认为旧认证器已不可用，把状态改成“可以重置”。主管最后读到了后者，于是草案错误地声称恢复条件已经满足。

这不是提示词不够长，而是多个执行者没有遵守同一份协作协议。可靠的多 Agent 系统首先也是一个软件系统：它需要明确状态、消息、版本、错误和责任。

共享事实，分开意见

共享状态应保存任务目标、已验证事实、证据引用、子任务状态、当前负责人和审批记录。每个 Agent 可以有自己的临时分析上下文，但不应直接覆盖其他角色负责的事实。

字段 内容示例 主要写入方
ticket_id IT-2048 工单系统
user_claims 用户称更换了手机 事实整理步骤
verified_facts 工单渠道身份已识别；恢复操作的独立核验尚未完成 核验服务或获授权人员
policy_ref KB-MFA-03，教学版本 v1 政策检索步骤
proposals 各专家建议及依据 各专家追加写入
approval_status 等待人工审批 审批服务
owner 身份服务流程 调度系统

“登录了工单系统”与“满足敏感账户恢复的身份核验条件”是两个不同事实。不要用一个模糊的 verified: true 混在一起。Agent 的建议也不能通过写共享状态，直接变成已经验证的事实。

给每次协作一份消息契约

下面是一条简化的专家结果消息。版本号、任务标识和证据范围，比长篇角色设定更能帮助系统稳定交接。

{
  "schema_version": "1.0",
  "ticket_id": "IT-2048",
  "run_id": "run-017",
  "task_id": "policy-check-01",
  "attempt_id": "attempt-02",
  "message_id": "msg-109",
  "in_reply_to": "msg-102",
  "based_on_state_version": 7,
  "status": "needs_input",
  "result": {
    "claim": "现有材料不足以支持敏感账户变更",
    "evidence_refs": ["KB-MFA-03@v1#recovery"],
    "missing_inputs": ["独立身份核验结果"]
  }
}

ticket_id 表示业务对象，run_id 表示这一轮处理，task_id 表示逻辑子任务。重试时保留 task_id，生成新的 attempt_id。message_id 用于识别重复投递，based_on_state_version 让接收方知道建议基于哪个状态快照。

收到消息后，程序先检查字段、枚举值、发送者身份和证据引用格式，再决定是否接收。字段合法只能证明消息符合格式，不能证明结论为真；证据与权限仍需独立校验。

重试、冲突和终止要写成规则

重试与幂等。 网络超时不代表远端操作失败。未来接入执行工具时，同一业务动作的多次尝试必须复用稳定的幂等键，例如 IT-2048:mfa-recovery:approved-plan-v3。计划改变则产生新键，且需重新检查审批是否仍覆盖该计划。服务端必须实际实现去重与结果复用；只把键写进提示词没有保护作用。

并发冲突。 专家基于状态版本 7 生成建议，而系统已经进入版本 9 时，接收方检查相关输入是否变化。身份状态或政策版本变化会使旧建议失效，应重新计算。不能简单采用“最后写入者获胜”。各专家尽量追加结果，由唯一状态管理器处理状态迁移。

终止规则。 每个任务应设置最大尝试次数、截止时间和 Token 或费用预算。满足验收条件就完成，缺证据就等待，遇到不可恢复错误就失败，用户取消则停止。达到预算不应被标记为成功。

责任规则。 每个活动任务有一个当前负责人。交接需要接收确认；超时未确认时原负责人或调度系统仍须处理。父任务结束后，取消不再需要的子任务，避免后台继续工作并回写过期结果。

本课产出：最小协作协议

团队至少应交付：共享状态字段表、消息 Schema、状态迁移表、重试与去重规则、冲突处理规则、预算及责任归属。建立这些约定后，再决定要创建几个 Agent。

练习：重复消息应该怎么办？

政策专家的同一条消息被送达两次；第二次送达时，工单已经使用了新版政策。你应该重复应用、直接丢弃，还是重做所有任务？

展开参考答案 · 先试着自己回答

先按 message_id 识别完全相同的重复消息，不重复应用已经处理过的结果。再确认当前任务是否仍引用旧政策：如果政策变化影响恢复条件，就将相关旧结论标记为过期，并只重新运行受影响的政策核对与下游草案检查。无需重做与政策变化无关的事实读取。

消息去重处理的是重复投递，版本检查处理的是过时结果，两者不能互相代替。如果远端操作是否成功未知，应查询操作记录或人工核对，不能贸然重发敏感动作。
