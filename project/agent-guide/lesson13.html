第13课｜案例：产品经理的证据型调研助手

建议学习 30 分钟（含练习） · 本课产出：一页决策简报
返回课程总览13 / 16

用户故事：明天要做决策，今天不能只收集链接

作为产品经理，我希望在两小时内拿到三种工单助手方案的对比，知道每条结论来自哪里、哪些条件尚未核实，以便决定下周验证什么。交付物是一份决策简报，而不是越长越好的研究报告。

本课包含一个公开实践和一份原创教学改编。公开实践来自 Anthropic 2025 年的多 Agent 调研系统文章；以下工单产品选型情境、分工和验收表均是课程设计，不是该公司的客户案例或实际效果数据。

公开实践给了什么启发

Anthropic 描述了由主 Agent 协调、子 Agent 并行研究、汇总证据的系统。他们同时强调提示词、工具设计、评估和成本取舍。适合借鉴的不是照搬角色数量，而是把相互独立的探索分开，再要求产物带证据返回。公开实践：多 Agent 调研系统。

不要直接引用某个厂商的内部提升比例来承诺自己的业务收益。任务、模型、基线和成本口径不同，数字无法直接迁移。

教学改编：三份证据卡，比三篇长文更有用

把任务限定为：“比较固定工作流、单 Agent、多 Agent 三种方案，判断第一期内部 IT 草案助手应该采用哪一种。”

执行单元 只回答什么 返回什么
业务研究 服务台最频繁且可验收的任务是什么 需求证据、用户故事、未证实假设
工程研究 哪些数据和工具已经可用 接入边界、权限、运维负担
评估研究 如何证明草案值得用 样本类型、评分规则、失败门槛
主负责人 当前应验证哪个最小方案 选型建议、证据冲突、下一步实验

这里的三项可以由人完成，也可以交给受限的 Agent。若资料只有三页，单 Agent 读完后按三栏整理可能更省事。多 Agent 的收益要由对照实验确认。

证据卡的字段

每条卡至少记录：结论、原始来源、来源日期、核查时间、适用范围、直接事实还是推断、反例或缺口。网页上的产品功能不等于你所在部署环境已经开放；没有找到某能力的说明，不等于该产品没有该能力。

教学示例：

{
  "claim": "第一版无需自动修改账户",
  "kind": "design_decision",
  "evidence": ["访谈样本：处理人员主要耗时在查政策和写草案"],
  "scope": "课程虚构的服务台场景",
  "unknown": "真实组织是否存在相同耗时分布",
  "next_check": "抽样20张已脱敏工单，记录各环节耗时"
}

这条结论属于设计判断，不能伪装成行业统计。它的价值在于指出下一步怎么验证。

主 Agent 不是把三份材料拼起来

主负责人应做四件事：去掉重复结论；显式保留矛盾；检查重要结论能否回到原文；把建议转成可执行验证任务。若业务研究说希望全自动，工程研究说只有只读工具可用，应给出“先验证草案模式”的方案及理由，不能在总结里把冲突抹平。

最终简报可控制在一页：目标与边界、三方案对比、当前建议、三个最大未知、下周验证计划。附件保留完整证据卡，不把全部检索过程塞进正文。

验收与失败信号

验收关注关键主张是否有支持、来源是否适用、矛盾是否呈现、建议是否落到行动。失败信号包括引用链接存在但不支持句子；把多个转载当成多个独立来源；把发布时间当成核查时间；为了形成明确建议而隐去缺失条件。

评估时随机抽取关键主张逐条打开来源，而不是只让另一个模型打一个总分。报告还需写出总检索次数、耗时和人工复核时间；如果人花了两小时纠正引用，“十分钟生成报告”并不代表节省时间。

练习：给不确定性一个位置（20 分钟）

给学员三张材料卡：A 表明服务台查资料耗时长；B 表明工单字段不统一；C 表明敏感操作只能由授权人员完成。请给出第一期目标、两项明确不做的事，以及两个必须验证的未知。

展开参考答案 · 先试着自己回答

第一期可做“把一张工单整理为带政策引用、缺失信息和下一步的处理草案”。不自动执行敏感账户变更，不追求一次覆盖全部工单类别。未知可以是检索结果是否足够准确、草案能否实际减少人工处理时间。验证应使用固定抽样与人工基线，而不是只演示最容易的一张工单。

产品经理的进阶路线

先能把需求写成用户故事和验收；再能分辨证据、推断和未知；随后设计小型评估集；最后再管理跨角色协作与迭代。掌握这些后，选择 Agent 框架才有明确依据。
