第15课｜案例：省市协作的工单智能体平台

建议学习 30 分钟（含练习） · 本课产出：分层职责与授权图
返回课程总览15 / 16

用户故事：统一能力，保留各地责任

作为省级平台负责人，我希望各地市使用统一的模型接入、工具与评估方式，同时只能处理自己有权访问的数据；作为地市业务人员，我希望在浏览器提交任务、查看依据、补充判断，并能知道当前该由谁处理。

这是原创参考架构，用于讲授协作边界；不是已部署产品，也不附带生产性能或成本承诺。

从业务动作开始画系统

地市人员提交工单或指定已有工单 ID。平台根据可信登录身份确定组织与权限，不接受模型自行声明的 city_id 作为授权依据。任务进入受限工作区，Agent 读取允许的数据、检索政策、输出草案。人工核验和审批由业务流程承接，结果回到任务记录。

层次 负责什么 关键可观察结果
浏览器工作台 提交、阅读草案、填写决策 用户看见输入、依据、待办与责任人
身份与任务服务 组织身份、授权、调度、任务状态 请求范围和状态迁移可追踪
Agent 运行环境 模型循环、上下文、预算、受限工具 工具轨迹、结果、停止原因
工具与数据服务 工单、政策、资产等系统访问 服务端再次校验权限并返回来源
人工流程与评估 核验、审批、抽检、回归测试 批准方案、验收记录、失败分类

模型网关可以统一用量记录和接入配置，但数据隔离不能只靠网关。缓存键、检索过滤、对象存储路径与日志访问都必须包含正确的租户作用域。

不同主体看到什么

地市处理人员看到本地任务和对应证据；地市负责人看到需要自己决策的事项；省级平台运维看到运行指标与脱敏错误；政策负责人维护适用范围和有效版本。是否允许省级人员查看完整工单，应由真实业务授权决定，不能因为角色叫“平台管理员”就默认可读一切。

工作台上的进展摘要可以来自 Agent 日志，但关键业务状态要由可信服务写入。模型生成“执行完成”不能直接变成事实字段。

MCP 和 A2A 放在什么位置

若多个 Agent 应用都需要接入同一政策工具，可以用 MCP 统一接入契约。若不同组织各自运行独立 Agent 服务，需要发现能力、委托任务与接收产物，可以评估 A2A。省内一个应用内的任务编排，可能只用普通服务接口就足够。MCP、A2A。

先建立身份、权限、任务与产物规则，再选择协议。协议不替代这些业务设计。

决策入口：建议、决定、执行分开记录

例如某地市的 IT-2048 缺少独立核验。工作台应显示：当前草案、缺失条件、政策依据、处理责任人。第二 AI 可以给出备用路径建议，但建议必须标明来源与时间。人工批准需要绑定具体计划、目标与有效期；若计划变化，则重新检查授权覆盖范围。

对负责人来说，“目前 80 个任务，其中 6 个等待我的决定”比一屏 Agent 对话更有用。每个待决策项应能跳转到证据和详细轨迹。摘要帮助理解，底层记录帮助核验。

分三步实施

第一步做只读草案：限定一类工单，收集人工基线，记录接受率和修改原因。第二步做有限写入：只开放可撤销、影响可控的动作，建立审批绑定与幂等。第三步再扩展多类别、跨组织协作和更长任务。每一步以评估结果决定是否继续，而不是按框架功能清单推进。

评价需要同时看业务与系统：草案合格率、人工处理时间、跨租户拒绝测试、政策引用有效性、P95 延迟、每成功任务成本、等待人工时间。等待人工和 Agent 计算耗时应分开，否则会误判性能瓶颈。

练习：找出跨地市数据泄漏的入口（20 分钟）

系统已经在提示词中写明“只能处理本市工单”。模型调用工具时却传入另一地市工单 ID；向量检索缓存也只按问题文本命中。请指出两处实际修改点，并写一个测试。

展开参考答案 · 先试着自己回答

修改点一：工单服务根据经过认证的调用主体与组织范围校验目标工单，而不是相信提示词或模型传来的 city_id。修改点二：检索和缓存按租户及授权范围隔离，缓存命中后仍保证结果可访问。测试：使用 A 市身份查询 B 市工单，以及提交会命中 B 市历史缓存的问题，均不得返回 B 市数据；拒绝记录应可审计但不泄露敏感内容。

负责人的进阶路线

从业务验收和角色责任入手，再学习权限与数据边界、评估成本、失败升级和变更管理。先让一个小流程可靠交付，比一次开放所有工具更容易判断价值。
