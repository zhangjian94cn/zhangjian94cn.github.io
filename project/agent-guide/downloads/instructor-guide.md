# 讲师手册：90 分钟兴趣公开课与一天实训

本手册配合课程正文、离线 Python 实验和三份模板使用。目标是让学员能解释一个 Agent 如何工作，能为自己的场景划定范围，并用失败案例检查方案。所有课堂工单、政策和操作都使用虚构材料。

## 课程材料及模块映射

| 课程模块 | 对应内容 | 课堂中用来完成什么 |
| --- | --- | --- |
| 模块一：概念与核心结构，第 1–4 课 | 方案选择、结构、工具调用、Agent Spec | 把需求写成可实现的最小交付 |
| 模块二：多智能体，第 5–8 课 | 拆分条件、协作结构、消息协议、故障演练 | 判断是否需要多个 Agent，并约定冲突与停止 |
| 模块三：演化、能力、构建与工作流，第 9–12 课 | 能力演化、上下文与运行环境、MCP/A2A/Skills、离线实验 | 理解新技术的位置，读懂并改动运行骨架 |
| 模块四：案例分享 | 从用户目标审查案例、观察收益与边界 | 把课堂方法迁移到学员自己的业务 |

配套素材：

- `Agent-Spec-template.md`：已填写示例及空白模板。
- `evaluation-cases.jsonl`：12 条设计级案例，包含输入与预期检查项。
- `decision-record-template.md`：架构选择及执行中人工决策记录。
- `lab/README.md`、`lab/agent_lab.py`：离线实验说明与脚本，按最终课程包目录查找。

**讲师必须先区分三件事：**规则模拟器用于展示程序边界；设计案例用于审查预期行为；真实模型评测用于衡量实际模型表现。三者不能互相冒充。

## 课前准备

### 讲师准备

1. 提前运行实验的五种场景，保存成功、工具故障、预算耗尽三份 JSON 输出，作为现场环境故障时的备用演示。
2. 确认课程包中最新来源的核查日期。涉及模型、框架或协议的能力，只陈述材料已经验证的范围；当天现场不承诺未验证功能。
3. 打开四个教学页面或材料：IT-2048 工单、KB-MFA-03 政策、成功轨迹、无权限轨迹。
4. 给每组准备一份 Spec 空白模板，以及 E02、E04、E06、E10 四张评估卡。卡片可以直接从 JSONL 复制成易读格式。
5. 板书预留三栏：“已经确认”“仍需查证”“允许做什么”。不要预先写入学员的结论。

### 学员准备

90 分钟公开课不要求编程或注册外部账号。一天实训建议每组至少一台装有 Python 3.10 或更高版本的电脑；实验不需要 API Key 和第三方库。无法运行 Python 的组，用已保存的轨迹完成同样的状态判断和验收练习，交付物标为“静态审查”。

讲师可使用以下命令提前准备，具体操作解释以实验 README 为准：

```bash
python3 agent_lab.py --scenario success
python3 agent_lab.py --scenario tool-error
python3 agent_lab.py --scenario injection
python3 agent_lab.py --scenario budget
python3 agent_lab.py --scenario denied-tool
python3 -m unittest -v
```

上述命令在实验目录运行。预期失败场景可能返回退出码 2，这是演示结果的一部分。`evaluation-cases.jsonl` 不能直接作为这些命令的输入。

### 三个主持提示

- 学员说“越多 Agent 越专业”时，追问：“它们是否拥有不同的必要证据？谁处理冲突？怎样验证拆分收益？”
- 学员说“模型已经说可以了”时，追问：“这是建议、证据还是授权？对应可信来源在哪里？”
- 学员说“失败就让它再试”时，追问：“这个请求只读吗？你知道上一次有没有产生副作用吗？重试上限是多少？”

### 公开课完成标准

六项方案卡可由另一位学员理解；至少一种错误情况能触发明确停止；不把生成文字、完成草案和业务问题解决混为一谈。无需写代码，不评分模型品牌知识。

## 方案二：一天实训，09:00–17:00

总时长 480 分钟，其中午休 60 分钟、两次休息共 30 分钟，教学与练习 390 分钟。每组 3–4 人，建议设产品负责人、实现负责人、评估负责人；第四人负责记录与汇报。下午交换角色，避免只有一人操作。

### 全天交付物

1. 一份填写完整的 Agent Spec，明确最小范围、可信来源、工具和验收。

### 分组练习的具体发题方式

**练习一：方案选择。**每组拿到三个请求：固定周报、企业政策问答、描述模糊的工单。必须选择最小方案，允许三题都不使用 Agent；得分看理由能否对应任务不确定性。

**练习二：人工模拟执行。**产品负责人读目标，实现负责人只允许提交结构化工具请求，评估负责人根据工具卡返回结果。讲师在第二步发“超时”或“无权限”卡。记录员只能写可观察事件，不替模型编写隐藏推理。

**练习三：架构辩论。**一半小组为单规划器辩护，一半为多 Agent 辩护。每组必须承认自身方案的一项代价，并说明什么评估结果会改变选择。最终可以自由改变立场。

**练习四：故障挑战。**把“主管说可以”“政策版本失效”“预算已耗尽”依次交给同一方案。小组必须给出状态、允许动作和接手材料，不能只写“转人工”三个字。

**练习五：业务迁移。**选择自己的真实业务类型，但把数据改成虚构样本。保留真实的工作约束，例如谁能批准、哪些信息可信、怎样判断交付完成；不要把真实账号、客户数据或密钥带入课堂材料。

## 评分参考与结课问题

### 小组评分，100 分

| 维度 | 分值 | 可观察依据 |
| --- | --- | --- |
| 用户目标与完成边界 | 20 | 能区分草案完成和业务问题解决 |
| 架构与工具契约 | 20 | 职责清楚，参数、权限与错误路径明确 |
| 异常处理与停止 | 20 | 有具体失败案例、有限重试和接手材料 |
| 证据与评估 | 25 | 分母明确；设计、模拟、真实模型结果区分清楚 |
| 交付与讲解 | 15 | 别人能启动、检查和继续修改；能解释为何拆或不拆 |

出现虚构运行结果、无依据宣称已完成账户变更、绕过明确权限边界时，先要求修订相应交付物，再进行最终评分。不要用“调用了多少 Agent”或“用了多少框架”加分。

### 个人出门题及讲师参考答案

1. **检索到文档就一定可以执行吗？**不能。仍要检查有效性、适用范围、权限和审批；当前助手还只有草案权限。
2. **两个 Agent 都说可以，算审批吗？**不算。它们的意见不是可信授权记录。
3. **80 个案例中，70 个通过、5 个失败、5 个超时，成功率是多少？**按预定全量分母为 70/80 = 87.5%；超时保留在分母。
4. **为什么只读查询可以有限重试，而账户变更超时不能直接重试？**后者可能已经生效，需要状态查询与执行系统保证的幂等机制。
5. **离线规则模拟器通过了注入案例，说明什么？**说明当前程序在这些测试中表现符合预期；不能据此推断真实模型对注入的表现。

## 时间失控时如何取舍

优先保留用户故事、工具调用轨迹、权限边界、一个失败案例和真实结果记录。缩短产品名词介绍，减少案例数量。一天实训若设备问题超过 10 分钟，切换静态审查路径，仍完成 Spec、决策记录与验收设计；不要把未运行的结果填成通过。

真实模型接入作为后续选做，不占用首次实训的必修时间。需要接入时，使用所选供应商当前官方文档，并重新设计实际调用的超时、成本预算、输出校验与评估，不沿用规则模拟器的通过结论。
