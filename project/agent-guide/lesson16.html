第16课｜结课项目：交付你的第一个可验收 Agent

建议学习 180 分钟（含练习） · 本课产出：六件项目交付物
返回课程总览16 / 16

挑战书：让别人能接手你的成果

你可以选择 IT 草案助手、产品证据调研助手或代码任务助手。课程建议首次项目沿用 IT-2048，避免同时引入未知业务和未知技术。

结课目标不是展示一个漂亮聊天窗口，而是交付一份别人可以运行、审查、复现失败并继续改进的作品。建议独立完成需要 3—5 小时；团队可以分成业务、实现、评估三个角色，轮流审阅。

第一步：冻结任务边界（30 分钟）

填写配套 Agent Spec：用户是谁、希望减少哪一步工作、输入来自哪里、可以调用哪些工具、明确不做什么、什么叫完成、什么情况下转人工、用什么样本验收。

写出一个正常故事和三个异常故事。异常故事至少覆盖缺信息、工具失败和越权请求。“异常时友好提示”不够具体，应说明保留哪些已完成结果、如何标记当前状态以及交给谁。

第二步：建立最小基线（30 分钟）

先用固定模板或人工处理十条样本，记录完成时间与结果。这样后面才知道 Agent 改善了什么。没有基线时，“一分钟生成草案”可能比原来复制模板还慢。

不要边改提示词边替换不容易通过的测试样本。开发集可以用于调试，冻结验收集用于比较版本。样本少时，报告实际个数，比夸张的百分比更诚实。

第三步：实现和观察（60—90 分钟）

从配套离线实验开始，读懂正常轨迹，再添加一个失败场景。研发读者可替换规划器接入真实模型；非研发读者可以设计完整状态与验收，让同组同学实现。

每次改动只回答一个问题：检索不准，是查询、数据还是权限过滤的问题？草案无依据，是模型编造还是完成校验太弱？循环太长，是任务没收敛还是停止条件缺失？根据失败层次修改，不要把所有问题都归因于提示词。

第四步：做一次同任务对照（30 分钟）

只有当存在可独立分工的任务时，才比较单 Agent 与多 Agent。固定输入、模型配置、工具集合与验收规则，至少保留每次运行的成本和耗时。多 Agent 版本可能更快，也可能更贵且错误更多；结论都可以成为合格项目，只要解释有证据。

本课不规定最低 Agent 数量，也不把使用更多框架视为加分。

第五步：提交六件交付物

交付物 最低内容
Spec 用户故事、范围、权限、验收、失败出口
系统图 模型、工具、状态、人工步骤和终止分支
可复现实验 启动方式、输入样本、明确依赖
轨迹证据 一次成功、一次失败、一次拒绝或停止
评估报告 样本与分母、实际结果、成本/耗时口径
交接说明 已验证、未验证、已知问题、下一步

如果使用真实模型，补充模型标识、调用日期、提示词版本和工具版本，但不要提交密钥、真实工单或敏感轨迹。

评分表：总分 100 分

维度 分值 达标表现
任务与 Spec 20 用户价值具体，范围与完成标准可检查
架构与工具契约 20 职责清楚，参数和错误路径明确
边界与失败处理 20 越权被执行层拒绝，预算与停止有效
证据与评估 25 结果可复现，有失败样本与真实分母
交付与讲解 15 别人能启动、检查、解释并继续修改

必过项：不能把模拟说成真实模型；不能伪造测试通过；不能用未授权动作换取任务成功。出现上述问题时，先修正作品，再评分。该评分表是教学标准，不是生产合规认证。

一份合格报告可以长这样

以下数字仅为报告格式示例，并非课程实际模型评测：

冻结验收集共 24 条，其中业务草案任务 20 条、独立越权测试 4 条。业务验收通过 17 条；3 条未通过中，2 条漏列缺失信息，1 条引用旧政策。4 条越权测试全部正确拒绝。业务草案合格率为 17/20，越权拦截通过率为 4/4；按第4课总体场景验收口径为 21/24。安全拒绝不能计作普通草案成功。正常任务延迟与失败任务延迟分别统计。当前仅完成离线模拟，未验证真实模型与生产数据权限。

“安全拒绝成功”和“业务任务完成”可以分别报告。不要把所有拒绝都纳入业务成功分子，从而让系统看起来准确率很高。

最后的课堂练习：三分钟作品答辩

请用三分钟回答：①替谁减少了什么工作？②最容易失败在哪里？③哪个约束由程序保证？④用什么证据证明结果？⑤下一版只改一件事，会改什么？

展开参考答案 · 先试着自己回答

好的回答具体到一类任务、一条失败轨迹和一项可检验改动。例如：“我们帮助服务台减少政策查找；过期政策是当前主要失败；执行器没有账户变更工具；报告保留 20 条固定样本与所有轨迹；下一版先加入有效期校验。”不需要承诺全自动，也不需要把未知包装成已经解决。

学完之后做什么

选一个工作中每周重复发生的小任务，写出 Spec，收集十条有代表性的脱敏样本，做出最小版本，用失败记录决定下一次改动。知识会在这个循环中变成可以交付的能力。
